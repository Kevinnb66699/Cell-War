## 〇、一句话结论

引擎（`scripts/core/`，19 个脚本）本来就是纯数据层：全是 `RefCounted`，一个 `Node` 引用都没有，服务器就是拿它无头跑的。
**「UI 和内核绑定」绑在三条线上**，都在核心之外或核心边缘，可以分阶段拆，不用重写规则：

| # | 绑在哪 | 量出来的数 |
|---|---|---|
| A | **演出穿透结算**：`CWBridge` 一个接口同时管「问决策」（`ask`）和「放演出」（10 个 `show_*`），引擎结算协程里 `await` 掷骰动画（`roll_shown`） | core 里 105 处 `await`（cw_actions 39 / cw_card_fx 37 / cw_world 16 / cw_game 13）；真正挂起点只有两个：`ask` 与 `show_roll` |
| B | **界面直接摸引擎的裸字典**：`game.tiles[c]["kind"]`、`game.cells[i]["energy"]` 这类读法 | 16 个 ui 文件、250 处；最多的是 `game.tiles` 24、`game.cells` 22、`game.tune` 16、`game.logs` 13 |
| C | **`CWMatch` 是上帝对象**：装配、每帧全量同步、九个 fx 模块、联机粘合、回放、聊天、教程聚光灯全在一个文件 | `match.gd` 1800 行；`_process` 每帧跑 12 个 `_sync_*` 再 `panel.refresh(game)`；`ui_bridge.gd` 955 行且**继承 AI 桥**（`CWUIBridge → CWMonteCarloBridge → CWHeuristicBridge → CWBridge`） |

**「除了 Fable 没人能维护」的根子不在代码分层，在三样东西的体量**：

| 东西 | 现状 | 后果 |
|---|---|---|
| `tests/headless_test.gd` | **16,714 行**、190 个测试、2,745 个 `check()`，一个文件，按下标分片 | 谁也不敢动、找不到该改哪条 |
| `docs/架构说明书.md` | 605 行却 **169 KB**（表格里一格就是三五千字的沿革），25 条约定分两段各自从 1 编号 | 读不完，也不知道哪句是「现在」哪句是「过去」 |
| 操作知识 | 热更三条禁忌（补丁不能带新 `class_name`、改规则要升 `NET_VERSION` 并重部署、新类要先 `--import`）、PRD 在仓库外、`prd_crosscheck`、出图流程 …… 散在架构说明书的表格深处和 **Fable 的会话记忆里** | 换一个人 / 一个 AI 接手，第一天就踩坑 |

所以方案是**两条腿**：解耦（阶段 1–3）与交接体系（阶段 0、4）。**如果只能做一件，先做阶段 0 + 阶段 4 的文档部分**，它们对「别人能不能维护」的贡献比解耦大。

## 一、现状：引擎已经有的好东西（重构要靠它们兜底）

- **流程是数据，推进是函数**：`CWGame.pending()` / `step()` / `advance()` 状态机，`flow` 字典记着「跑到哪」；快照永远取在 `pending()` 边界（那时没有悬着的协程）。AI 的推演（MCTS / 蒙特卡洛桥）就是「快照 → step → 回滚」几千次。
- **决策只有一个通道**：`CWGame.ask()` 是引擎与决策者之间的唯一入口，人类 / AI / 联机 / 代打全从这儿过；回放（`CWReplay`）就录这里的下标，`t_determinism` 钉着同种子同哈希。
- **快照与哈希**：`CWStateCodec` 是唯一编码器，联机靠 `state_hash` 逐字节对齐。
- **联机已经是事件流**：服务器侧 `CWNetBridge` 把每个 `show_*` 变成一条报文（`roll` / `result` / `card_played` / `event_drawn` / `world_event` / `notice` / `beam` / `erosion` / `fx` 九种），客户端 `match.gd:930` 那一段再一条条回放给本地桥。**这九种报文就是现成的事件 schema**，重构只是把它提升为引擎的原生输出。
- **表现层已有铁律**（架构说明书约定 #15 / #16 / #19）：表现层不存坐标、不决定结果、随机先由引擎掷出再经桥演出。

## 二、目标架构

```
            决策者 CWDecider（只有 ask）                     观众（只消费事件，从不被 await）
   人类输入 CWUIDecider ─┐                              ┌─ CWFxQueue（客户端演出队列，本地局 / 联机局同一条）
   启发式 / MCTS 桥      ├──► CWGame（core，纯数据） ──► events_out ──┤─ CWNetBridge（服务器：原样广播，即现在的九种报文）
   联机桥 / 回放桥 / 测试桥 ┘         │                                └─ 日志 / 出牌列 / 统计
                                     ▼
                              CWGameView（只读查询）
                                     ▼
              CWMatch（装配 + 生命周期）→ CWMatchMirror（棋盘 / 细胞 / 手牌镜像，按脏标记刷）
```

| | 现在 | 目标 |
|---|---|---|
| 引擎挂起点 | `ask`（决策）+ `show_roll`（动画） | **只剩 `ask`** |
| 桥 | `CWBridge` = ask + 10 个 show_* | `CWDecider` = ask；演出改为 `events_out` 事件列表 + 信号 |
| 演出时序 | 引擎停在骰子动画上等它播完 | 引擎一口气算完；客户端队列播事件，**播放期间冻结镜像**，播完再同步 → 玩家看到的顺序不变 |
| 界面读状态 | 250 处直接索引字典 | 全走 `CWGameView` 查询函数；护栏禁止 ui/ 直接 `game.tiles[` / `game.cells[` |
| UI 桥 | 继承 AI 桥（四层） | `CWUIDecider` 组合一个 AI 决策者（现在 mcts 已经是组合，照那条路） |
| 联机演出 | 客户端 `match.gd` 手写一段报文分发 | 报文 = 事件，客户端与本地局共用 `CWFxQueue`，那段分发消失 |
| `CWMatch` | 1800 行 | 装配 ≤ 400 行 + 镜像 + 演出队列 + 联机粘合 + 回放控制，各 ≤ 500 行 |
| 测试 | 一个 16,714 行文件 | `tests/unit/<模块>_test.gd` 十来个文件 + 一个 runner；分片逻辑在 runner |
| 文档 | 架构说明书 169 KB 沿革表 | 「现在是什么」≤ 40 KB + `docs/decisions/` 决策记录 + 每目录 README + `新人上手.md` |

## 三、分阶段方案

每个阶段独立可上线、测试全绿再进下一阶段；阶段之间可以停。上线方式标了「热更」还是「全量发版」（补丁包带不了新 `class_name`）。

### 阶段 0 · 护栏与安全网（估 2–3 天）

先把「引擎行为一丝不变」变成可以机器证明的事，再动刀。

1. **拆测试文件**：`headless_test.gd` 按现有的 `# ---- 分节` 切成 `tests/unit/*_test.gd`（core / cards / world / ai / net / ui / hot_patch …）；新 runner `tests/run.gd` 收集各文件的 `t_*`，分片与 `user://` 隔离逻辑搬进 runner；`tools/run_tests.sh` 命令不变。验收：3,182 项一个不少，两片并行时间不变。
2. **黄金回放**：录 6–10 局（四人 / 六人、四种癌、含教程一关、含中途选择的卡）存 `tests/golden/*.cwr` + 终局 `state_hash`；`t_golden` 用 `CWReplay.build()` 重放核哈希。阶段 1–3 每一步都拿它证明「规则没变」。
3. **架构护栏 `t_arch`**（源码扫描，跟 `t_hot_patch` 一个路数）：
   - `scripts/core`、`scripts/ai` 不得出现 `res://scripts/ui`、不得引用任何 UI 类名（白名单校验）；
   - core 里 `await` 的函数名单以现状为基线，**只减不增**；
   - 文件行数：新文件 ≤ 600 行；现有超标的 7 个文件登记在案，只减不增；
   - ui/ 不得直接索引 `game.tiles[` / `game.cells[`（阶段 2 结束时打开）。
4. **`docs/新人上手.md`**：装 Godot → 跑 → 测 → 出图 → 发版 → 热更三条禁忌 → 联机版本与服务器 → PRD 在哪、两个核对脚本。把散在会话记忆里的操作知识全部落进仓库。
5. **对照队友的 AI 报告**：拿到原文后逐条标到本方案的 A / B / C 或「不成立」。

上线：无（只加测试与文档）。热更可发。

### 阶段 1 · 桥拆二：决策者 / 事件流（估 1 周）

这是解耦的主刀。

1. `CWGame` 新增 `events_out: Array`（每次 `step()` 开头清空）与信号 `presented(ev)`；事件用字典，schema 直接沿用 `CWNetBridge` 的九种报文（`{"t": "roll", "reason", "value", "sides", "pid", "at"}` …），另加 `{"t": "state", "seq"}` 标记「这一步算完了」。
2. `roll_shown()` 不再 `await`：掷骰 → 追加 `roll` 事件 → 返回值。`announce()` 与 `broadcast_*` 同改。`CWBridge` 只剩 `ask()`，改名 `CWDecider`，保留 `CWBridge` 空壳一版过渡。
3. 引擎里凡是**不经过 `ask`** 的函数去掉协程化（105 处 `await` 预计过半是纯演出链；黄金回放证明每一步）。
4. 决策者各就各位：启发式 / MCTS / 联机 / 回放 / 测试桥只实现 `ask`；`CWUIBridge` 拆成 `CWUIDecider`（人类输入部分，≤ 400 行）+ 组合一个 AI 决策者，**不再继承** `CWMonteCarloBridge`。
5. 客户端新 `CWFxQueue`：从 `events_out` 取事件排队播（骰子 / 通报 / 侵蚀 / 光束 / fx），**播放期间冻结镜像**（不跑 `_sync_tiles / _sync_cells / _sync_hand`），队列空了再同步 —— 「先见骰子后见结果」的节奏不变；热座共用桥的去重规则搬到事件层（同一事件只播一次）。
6. 联机：服务器把 `events_out` 原样广播；客户端同一条 `CWFxQueue` 消费，`match.gd:930` 那段手写分发删除。

验收：黄金回放哈希不变、`t_determinism` 不变、所有 `preview_*` 出图不变、真机走一局四人局 + 一局联机局 + 教程前三关。
上线：**全量发版**（新 `class_name`）。协议：报文形状不变则 `NET_VERSION` 不动；服务器仍要随引擎一起重部署。
风险：演出与状态的时序靠「冻结镜像」兜，要真机验；教程的 `check_progress()` 靠读引擎状态翻页，冻结期间要用「播完再判」。

### 阶段 2 · 只读视图：界面不再摸裸字典（估 1 周）

1. `CWGameView`（或直接挂在 `CWGame` 上的查询区）：`tile(c)` / `cell(id)` / `cells_of(pid)` / `hand(pid)` / `level_info()` / `feed_since(seq)` / `logs_for(viewer)` / `income_preview(cell)` …… 现有的 `cell_of / cells_at / count_tissue / living_cells / is_cancerous / pressure_at / aerobic_income` 已经是这一层的一半。
2. ui/ 的 250 处直接读全部改走查询；`t_arch` 第 4 条打开。
3. `docs/状态字典.md`：把 `make_cell` / `make_tile` / `req` / `options` 的键与含义写成一页（从现有注释搬），这是「AI 能读懂状态」的最低门槛。
4. **不做**字典 → 类的大爆炸：`cell["energy"]` 这类访问在 core 里成百上千处，改了收益不抵风险；留作可选阶段 5。

验收：ui/ 里 `game.tiles` / `game.cells` 直接索引归零；测试与出图不变。
上线：只加函数不加类 → 热更可发。

### 阶段 3 · 拆 `CWMatch`（估 1–2 周）

1. `match.gd` 1800 行 → `match.gd`（装配 + 生命周期 `teardown`，≤ 400）、`match_mirror.gd`（棋盘 / 细胞 / 手牌镜像，按 `state.seq` 脏标记刷新，不再每帧全量）、`fx_queue.gd`（阶段 1 已有，九个 fx 模块挂它）、`match_online.gd`（联机客户端粘合）、`match_replay.gd`（回放控制）。
2. `_process` 只剩动画推进；`panel.refresh(game)` / `log_panel.refresh(game)` 改为事件触发。
3. 教程（`guide.gd` / `spotlight`）深度依赖 `CWMatch` 内部（`highlight_flag` / `check_progress`），放这一阶段最后收口。

验收：`t_match_*` 全部照跑；`screenshot.gd` 固定流程逐屏比对；真机走完 16 关教程。
上线：全量发版。

### 阶段 4 · 交接体系（贯穿，每阶段收尾时做一部分）

## 八、与《离散事件架构：三层设计》的关系

09-12 03:15 `docs/` 里出现了一份 `离散事件架构_三层设计.md`（19 KB，不是我写的，09-12 Kevin 定入库；它引用的《架构重设计_2026-09-12》我没有）。
那是另一条路线：**在现有引擎旁边新建一个离散事件运行时**（Runtime / State Store / Observation / Session / Rules 五个模块；逻辑时序最小堆、
同刻 LIFO 连锁、事务化版本、多世界分叉），拿现在的 GDScript 当黄金真相对拍，覆盖后再谈切换。它没写时间与人力。

**两边一致、可以直接吸收的**：
- 核心从不等动画（它的 §3.5 ＝ 本方案阶段 1）；
- 输入等待不靠调用栈（它的 InputBarrier + continuation；现引擎顶层的 `pending / step` 已经是，缺的只是**结算中途**的 `ask` —— 它的
  PaymentPending / Reservation「显式 resolution 状态」说的是同一件事，本方案留作可选阶段 5）；
- 观察层只读、按版本对齐（它的 Observation ＝ 本方案阶段 2 的 `CWGameView` + 现有 `view_for`）；
- 事实 / 事件带稳定顺序（它的 FactBatch ＝ 本方案的 `events_out` 与九种报文）；
- 先冻结黄金样本再动（它的 §4 ＝ 本方案阶段 0）。

**分歧与顾虑**：
1. **体量**：那是新写一个引擎。core 19 个脚本约 1.1 万行规则要按 7 个所有者重铸成事件处理器，3,182 项测试重定向，联机哈希 / 回放 / 存档 / 热更全部重来。
   以这个团队的节奏这是季度级，和 09-11 晚拍板的「不换语言、部分重构」对不上。
2. **结算顺序的来源变了**：现在 `e_phase` 逐条照抄 PRD 步骤号，顺序是**写死的数据**；最小堆 +「同刻顺序由规则声明」等于把顺序重新推导一遍。
   黄金回放能抓到差异，但长尾会很长 —— 规则电子化说明里有 90 多条口径是引擎自己定的，每条都要在新调度语义下重新落地。
3. **AI 推演性能**：它首版「每个事件事务完整 WorldImage 深复制」。MCTS / 蒙特卡洛桥每步决策要 `step` 几千次，现在是每步一份快照；
   改成每事件一份深复制会慢一到两个数量级，平衡扫描先受不了。它自己也写了「后续按剖析改分区写时复制」—— 那是第二个工程。
4. **双真相期**：新旧引擎并存时规则改动要改两份（PRD 还在周更），谁保证同步？
5. **缺件**：《架构重设计_2026-09-12》和队友 AI 的检查报告我都没有，没法逐条对。

**建议**：把它当**阶段 5 的候选**，不当现在的起点。本方案的阶段 0–2（黄金回放、事件流、只读视图、测试拆分）是两条路线共同的前置；
做完之后，上不上离散事件运行时可以拿真实数据（AI 推演耗时、规则漂移条数）再定。若 Kevin 决定走那条路，也请先定：谁写、多久、
GDScript 版冻结到哪一版、切换判据是什么。**这是第 9 条要拍板的事。** （那份文档 09-12 已按 Kevin 的话入库。）
