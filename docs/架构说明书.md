### 免疫普通攻击演出（2026-09-13）

合入时补的（2026-09-13）：护栏 `t_attack_fx`（演出层登记 / 连打接管 / 退场 / 拆局清空 + 引擎报文齐全、巨噬只报 `chomp` 不叠冲撞）；放大看图 `tests/preview/preview_attack_fx.gd`（两行三列：目标活下来 / 被打死各三拍）。报文里的 bool 走 `var_to_bytes` 过网，协议没动。**2026-09-19 修**：拆局的 `_clear_board_fx()` 把演出层 `visible = false`，这一层的 `play()` 原来不亮回来 ⇒ 同一次启动里第二局起普通攻击一次也不演（Kevin 报「联机里攻击 AI 癌细胞动画消失」，不是线程）；现在 `play()` 自己 `visible = true`，护栏 `t_attack_fx` ③b + `t_settle_screen` 拆局重开那段。

### 原贴图卡牌预览（2026-09-12）

`tools/art-preview/card-catalog.js` 提供 16 张卡牌的推荐理由及演出边界，`card-effects.js` 复用 `draw.js` 的游戏贴图加载与格子定位。`registry.js` 合并卡牌项目；`?card=card_radiation` 打开卡牌入口，`cards.css` 使用游戏字体与 DESIGN 配色。组织、细胞及固化层引用 `game/assets/art` 原 PNG，仅粒子为新增绘制。Bun 服务支持 `ART_PREVIEW_PORT`，允许读取游戏字体，不接入对局逻辑。

## 项目是什么

### 2026-09-09 悬浮查询与开始入口

主菜单「开始对局」统一打开 `CWConfigPanel`，标准 / 自定义在面板的「对局类型」中切换；默认焦点仍在人数，上键可到模式选择。自定义才向配置输出 `cancer_types`，热座席位设置及返回主菜单流程不变。

主动技能的实时详情由 `CWCardInfo.describe_act_for()` 生成：行动栏与右栏共用 `CWActions.cost_effects_for()`，读取 `CWCost.quote()` 的纯查询 breakdown，不执行付款。移动类按合法目的地聚合影响，注明部分目标范围。自由详情缓存包含完整内容，防止同名技能的效果更新后仍复用旧文字。

细胞格子悬浮由 `CWTileInfo.describe()` 调用 `CWDamage.status_rows()`，按当前标记、护盾、护甲已用状态和组织条件给出易伤 / 减伤；只描述，不构造或提交伤害事件。

《Cell War》桌游（免疫细胞 vs 癌细胞）的电子化新版工程。**规则已修改，从零重建，不继承旧版代码**；引擎 Godot 4（GDScript）。

- 规则原文（PRD）：`Cell_War_玩法PRD.md`（2026-09-11 起用这个名；在仓库外，队友随时改，动规则相关代码前先重读比对；旧的《Cell War新版规则.md》已删除——2026-08-28 团队决定，它停在 61 格版）

### 三、AI —— 三步走完成两步半（2026-08-29 深夜）

1. ✅ **会用卡**（启发式桥）：出牌免费所以只评「时机」——直接效果有目标就打、
   增益看马上用不用得上；代谢耦联/选格子等中途询问给出真答案，不再一律答 0 弃权
2. ✅ **静态估值函数**（`cw_eval.gd`）：地盘按胜利判据口径加权是主导项，
   另计固化进度、能量、手牌/装备、记忆/等级、战线距离。零和（免疫视角=取负）
3. ✅ **扁平蒙特卡洛**（`monte_carlo_bridge.gd`）：逐候选「快照→试走→粗跑→估值→回滚」。
    `max_sim_steps` 是确定性总预算（0 = 不限）；**已接进真对局**：
    对局配置面板的「AI 强度」：**较强** = CWUIBridge 开推演闸并固定 192 个模拟 step；**树搜索** = 另挂一只 `CWMCTSBridge`（`bridge.mcts`，**组合不是继承** —— CWUIBridge 已继承扁平 MC，而 MCTS 桥是与它并列的另一棵；预算 160 迭代 / 深度 12 / 384 step，**这三个数没有对局数据支撑**），
    本机早/中/晚局面实测 51.5/52.7/58.8 ms（无限预算为 187.5/194.2/195.2 ms）
4. ✅ **蒙特卡洛树搜索**（`mcts_bridge.gd`）：独立的 UCT 树搜索桥，目标是「比更强还要强」的第三档 AI ——
    与扁平 MC（平衡标尺）**并列、互不继承**。维护一棵 UCT 树，把算力聚焦到反复证明更好的分支；
    只接管 action 顶层询问，其余回落启发式。全程在独立副本上跑、推演流由「快照 rng + 迭代号」派生、
    树内边状态由 `hash([父边种子, 动作号])` 确定性重演 → 同种子同局面同答案。`iterations`/`horizon`/`ucb_c`
    是预算与探索参数，`max_sim_steps` 仍是确定性总预算（0 = 不限）。可副线程。**本版为纯增量**：
    未接任何 UI/联机档位，标尺与以它为基准的平衡表全部不受影响。
5. 真要更强再上 **ISMCTS**（手牌是隐藏信息，要 determinization；骰子/抽卡要机会节点；
    4~6 人不是两人零和）

**注意**：平衡测试用的 AI 要**快且一致**（用启发式桥或调小蒙特卡洛参数），
人机对战用的 AI 可以慢。两者不必是同一个 —— 硬要用一个只会两头不讨好。

## 核心设计：问答桥

引擎**不知道**谁在做决定。需要玩家抉择时，引擎调 `game.ask(pid, req)` 抛出一个「问题 + 选项列表」，由**桥**（`CWBridge` 子类）返回选中的下标。

```
CWGame ──ask(req)──────> CWBridge ──> 启发式 AI / 蒙特卡洛 AI / 人类 UI / 将来的联机对端
       <──选项下标──
       ──show_roll(…)──> CWBridge ──> 掷骰动画（引擎 await 到播完）
       ──show_result(…)─> CWBridge ──> 一句话通报（不 await，提示自己淡掉）
```

`show_roll()` 是同一条桥上的**单向通知**：引擎先用 `rng` 掷出结果，再把结果送给表现层去演，
并 `await` 到动画播完才继续结算。**表现层无权决定结果**，这是约定 #11。
它**广播给所有桥并按对象去重** —— AI 掷的骰旁观者也得看见，热座共用一个 UI 桥时只演一次。

签名：`show_roll(reason, value, sides, pid, at)`。`at` 是这次掷骰指向的格子
（攻击给目标格，突变/抗体给发动者所在格）—— 骰子要落在棋盘上那一格旁边，
坐标只有引擎知道。`pid` 可用于显示「谁掷的」，**但不用来给骰子染色**：
骰面颜色已经表示结果档位，再叠阵营色会两套语义打架（决策「甲」）。

`show_result(text, at)`（由 `CWGame.announce()` 广播，同样按对象去重）是掷骰的**结算说明**——
"攻击大成功"、"突变：无事发生"。**文字由引擎给**：点数怎么判读是规则，
表现层照着点数自己再判一遍等于把规则抄了第二份，改一处就会对不上。
不 `await`，因为提示自己会淡掉，不该卡住结算。

这样同一套规则代码可以驱动 AI 互搏、人机对战、热座、联机，互不干扰。**新增交互时不要在引擎里直接读 UI，一律走 ask()。**

`req` 的形状：`{ kind, pid, prompt, options: [{label, data}], (tag) }`
`kind` 取值：流程状态机的顶层询问 `setup_place` / `immune_revive` / `revive` / `action`，
加上卡牌结算的**中途选择**（2026-08-29 随「需中途选择」批引入，tag=卡名）：
`free_move`（走一步/停）/ `pick_cell`（选细胞）/ `pick_tile`（选格）/ `pick`（按钮多选一）。
中途选择里「可以不做」的询问**下标 0 恒为停止/放弃**——基类桥永远答 0，天然安全。
由此抽卡链路是协程：`draw → resolve_event → enter_tile → collect_special` 一路 await
到 `pending()`/`step()`；**漏 await 的调用会脱离结算顺序**，复现测试会当场炸
（各文件头注有清单，新调用点照抄 await）。

## 核心设计：流程状态机（2026-08-28）

**对局推进到哪一步是数据，不是调用栈。**

```
game.pending()          # 返回「轮到谁、要做什么决定、有哪些选项」；空 = 对局结束
game.step(choice)       # 落子并推进到下一个决策点
game.snapshot()         # 整份状态（含 rng.state）
game.restore(snap)      # 原样放回去
```

`pending()` 和 `step()` 都是协程，但**只在两种情况下真正挂起**：表现层要演出（掷骰动画），
或卡牌结算中途经 `game.ask` 追问且作答的是人类桥。同步桥（AI/测试）下 await 立即完成，
快照→落子→回滚的评估循环依旧零挂起。

**为什么要这样。** 原来的写法是 `run_game()` 一个循环跑到底，中间 `await bridge.ask()`。
那样「现在推进到哪儿」存在**调用栈**里（哪个函数、循环跑到第几个玩家），而调用栈没法快照。
AI 要评估「我走这一步会怎样」，需要的是：快照 → 落一步 → 继续跑几步 → 回滚，反复几千次。
所以流程位置必须搬进 `flow` 这个字典，推进必须是一次函数调用。

**三条随之而来的约定（2026-08-29 随「需中途选择」批修订）：**

1. **行动的入口全是顶层选项。** 分化、裂解（要不要顺带净化）、血行转移落点、跃进方向
   全摊平成独立选项，参数直接写在 `data` 里——AI 选行动时看到的就是原子行动。
   少数卡在**结算里**的后续决定（趋化募集的走位、代谢耦联的数额……）经 `game.ask` 追问；
   「可以不做」的追问下标 0 恒为停止/放弃，基类桥答 0 天然安全。
2. **`advance()` 路上不掷骰、不演出。** 唯一可能挂起的是自动结算连锁里的中途询问
   （踩骨髓抽到要选择的事件卡这类），且只有人类桥作答时真挂起。
3. **随机数发生器的 state 属于快照。** 少了它，同一步走两遍会掷出不同的骰子，推演就没有意义。
   挂起只发生在等人类作答的那一瞬，快照永远取在 pending 边界上——那时没有悬着的协程。

`run_game()` 退化成一个薄壳：`while pending(): step(await ask(...))`。
AI 互搏、平衡模拟、无头测试都只要「跑完一局」，用它就够。

实测：单步 **0.106 ms**，一局 4 人局约 292 步 / 31 ms。3 秒的思考预算约合 **2.8 万步推演**。
`snapshot()` 深拷贝一次约 **0.16 ms** —— 真要跑到十万次量级时，
这里应该换成「落子 / 悔子」（make-unmake）而不是整份复制，但那要先有回滚日志。

`stop_at` 字段可以让 `advance()` 在某个阶段开头停下（测试和工具用，`""` = 不停）。

## 关键约定（改代码前必读）

1. **能量用「十分能量」整数存储**：`30` = 3.0 能量。避免浮点误差，保证回放/联机确定性。显示用 `CWData.fmt()`。
2. **所有随机数必须走 `game.rng`**。用了别的随机源，确定性测试（同种子两局哈希一致）会立刻抓到。
3. **不要给 `CWGame` 加名为 `log` 的方法**——GDScript 的内置数学函数 `log()` 不能被覆盖，会导致整个类编译失败。日志方法叫 `log_msg()`。
   连续的同类行（一步一步走出来的【定殖】/【净化】）走 `log_run(key, item, prefix, suffix)`：同 key **且紧挨着上一条**就并进去、**就地改写最后一条**。
   因此「日志只增不改」这条假设 2026-09-07 起不成立了——渲染侧的折行缓存必须让末条每帧重折（`CWLogPanel` / `CWLogHint` 已改）。
4. **新增 `class_name` 脚本后必须先 `--import` 再跑测试**，否则报 "Identifier not declared"。
5. **进入一格的所有效果都在 `CWActions.enter_tile()` 里**（定殖/净化/特殊组织收取/标记刷新）。移动、血管传送、复活落位共用它——加新效果加在这一处，不要散落各处。
6. **新增规则状态字段时，要同步更新 `CWStateCodec` 的快照/规范化编码边界**，否则确定性测试会漏检。
   2026-08-30 就踩了一次：口径 #73 把 `mods[].seq` / `equip_seq` 变成规则相关数据
   （移动费链按它排序），哈希却没跟上，于是两个**结算结果不同**的局面算出同一个哈希。
   反过来也有个坑：`cell["play_n"]` 这类**只增不减的计数器不要进哈希**——绝对值不影响
   任何结算（只有相对先后有意义，那已被各条目的 seq 记住），塞进去会打破
   「挂上修饰 → 消耗掉 = 回到原状态」这条测试地基。
7. **费用一律走 `CWCost`，报价与扣费分开**（口径 #79）。新卡要改费用，只在
   `CWCost.TEMPLATES` 里登记一条 `CostModifier`（语义阶段 + 条件 + 消耗策略），
   **不要**回到 `CWActions` 里手写 if。两条铁律：
   `quote()` 是**纯查询**——不扣能量、不消耗修饰、不烧闸门、不写日志、不碰 rng，
   所以 UI 每帧刷新、AI 枚举、快照推演都可以随便调；要写的闸门记进 `usage_marks`，
   等 `commit()` 才落笔。`commit()` 先**复验合法性**（`ctx["validate"]`，由动作层给，
   且必须与选项生成用的是同一份谓词），再按当前状态重新报价——调用方存的旧价钱只用来核对。
   **从复验到扣费之间不许出现 `await`**，否则中间的挂起会让复验白做。
8. **范围伤害必须走 `immune_hit_area()` / `cancer_hit_area()`**，不要自己 for 循环逐个
   调 `immune_hit`/`cancer_hit`。批次由事件的 `simultaneous_group` 决定，**不是**
   由「调用方碰巧塞进同一个数组」决定：`group == 0` 每个事件自成一批；批次号在**循环外**
   取一次给全体目标；主攻击与它的次级伤害（T 细胞无视减伤那一下）**必须同批**，
   拆开会让 BCL-2 先把能量拉回分期值、次级伤害再补一刀反而绕过免死。
9. **死亡只在死亡阶段发生，伤后效果一律进触发队列**（设计 §5.6/§5.7）。
   `_resolve_deaths()` 分三遍走：挑濒死 → 死亡替代（BCL-2）→ 批量宣死，
   中间不许穿插别的效果。想在「造成伤害后 / 击杀后 / 死亡后」做事，
   用 `_enqueue(Trigger.XXX, Rank.XXX, …)`，**别在攻击流程里另起一刀**
   ——【吞噬体成熟】原先就那么写，等于绕开了「死亡只在死亡阶段发生」这条约定。
   队列按「类别 → 来源层级 → 入场顺序」稳定排序，加新触发不用再推理它会被谁抢先。
10. **跑测试用 `tools/run_tests.sh`，别只看「全部测试通过」那一行。**
    `headless_test.gd` 只统计**断言**；GDScript 的运行时错误（空引用、数组越界、
    调用不存在的函数）只打印一行 `SCRIPT ERROR`，**不影响退出码**。
    2026-08-31 一天内踩到两次，两次都显示「全部测试通过」。脚本会把它们也算作失败。
11. **伤害一律走 `CWDamage`，读 `actual` 不读理论值**（口径 #80）。业务代码**不许**自己
   `target["energy"] -= v`——「无视减伤」也不行，那是带 `UNPREVENTABLE` 标签的伤害事件；
   自己扣的话，日志、BCL-2、死亡检查与统计会立刻分叉成两套。范围伤害必须走
   `game.immune_hit_area()` / `cancer_hit_area()` **整批提交**，边遍历边扣能量会让
   数组顺序改变结果。吸血、「造成 X 伤害后」、斩杀一律读 `DamageResult.actual`
   （目标实际失去多少），读理论伤害会在残血目标身上多回整整 1.0。
12. **平衡数值改动走 `CWTuning`**，不要直接改 `CWData` 常量——`CWData` 是规则原文的记录。
13. **不要在代码或测试里写死棋盘尺寸**（`61`/`127`/`41`……）。一律引用 `CWData.TOTAL_TILES`、
    `CWData.BOARD_RADIUS`、`CWData.CANCER_WIN_WEIGHTED` 等常量。2026-08-27 从 61 格换到 127 格时，
   4 处写死的数字全部变成了假失败，排查成本远高于一开始就引用常量。
14. **改棋盘尺寸后必须重跑平衡**：收入公式挂钩「健康组织格数」，棋盘面积一变，
    低保/封顶的相对位置就全变了——61 格调好的数值搬到 127 格会让癌胜率从 51% 掉到 10%。
15. **表现层不许自己存一份棋盘坐标**。规则层用轴坐标 `(q,r)`，渲染层用「行,列」下标，
    两套坐标之间只有 `board.gd` 的 `axial_to_rc()` 一个转换点，源头永远是 `CWData`。
    2026-08-27 合并渲染代码前，渲染层自己抄了一份特殊组织下标，地图改到第三版时没跟上——
    画出来还是 5 个骨髓、代谢核心还在半径 4。`headless_test.gd` 的 `t_board_view()` 专门防这个。
16. **表现层不许决定结果**。所有随机由引擎的 `rng` 先掷出，再经 `CWBridge.show_roll()`
    送给表现层去演；动画只能演到那个数上，不能反过来决定它。
    掷骰动画的翻滚随机走节点自己的 `randf()`，**绝不碰 `game.rng`**。
    `headless_test.gd` 的 `t_roll_hook()` 会把钩子收到的点数和日志里实际结算用的点数逐次交叉核对。
17. **界面的设计分辨率是 960×540，不要改**。它和界面原型的画布同尺寸，
    原型里的 `1cqw` 正好换算成 `9.6px`，所有定稿坐标能直接乘过来；
    而且 1080p 全屏恰好是整数 2 倍，点阵字和像素贴图都能整数放大不糊。
    拉伸模式是 `canvas_items` + `keep`。
18. **点阵字号只能取字体网格的整数倍**：中文（缝合像素 10px）取 10 / 20 / 30 / 40，
    Logo 用的 Silkscreen 取 8 的倍数。取别的值会被重采样磨出灰边。
    同理，20px 字号下 1 个字模像素 = 2 屏幕像素，**字间距和位移也要取 2 的倍数**。
    `headless_test.gd` 的 `t_main_menu()` 会扫描场景里所有 Label 盯住这一条。
19. **要不要给某个随机加动画，是纯表现层决定**。静默用 `roll_d6()/roll_d3()`，
    带演出用 `roll_shown(sides, reason, pid)`；两者消耗的 rng 完全相同，可随时互换，
    不影响同种子可复现。**不要为了加动画去改 `roll_d6/roll_d3` 的签名** ——
    GDScript 的 `await` 会沿调用链往上传染，那样每个既有调用点都得跟着改。

20. **初始癌组织格数按人数分档，取值必须走 `CWData.init_cancer_tiles(n)`**（口径 #82）。
    `CWData.INIT_CANCER_TILES` 现在是一张**字典**（`{2: 15, 4: 15, 6: 21}`），不是整数 ——
    当成整数用会静默算错。`CWTuning.init_cancer_tiles` 的默认值是 **`-1` = 按人数表**，
    只有平衡测试要把所有人数钉成同一个数时才设具体值。
    为什么要分档：免疫方阵营总收入随人数线性增长（有氧每细胞各拿全额、**不**均分），
    癌方不随人数变（无氧按块内癌细胞数**均分**），人越多免疫越强，用开局布局补回来；
    2026-09-05 起有氧基数也按人数分档（四人 2.0 / 六人 1.8，`AEROBIC_LEVEL_BASE_BY_PLAYERS`），同一个思路的第二处。

21. **在跨局复用的节点上建补间，必须留句柄并在开新局时杀掉。**
    `board` / `_cells_root` / HUD 这几个节点 `teardown()` **都不销毁**，
    所以绑在它们身上的补间会**活过拆局、跑进下一局**继续改属性。
    2026-08-31 同一个函数（`CWMatch.fade_out`）里踩了两次：
    ①「细胞不显示」—— 淡出补间把新局刚设回 1.0 的细胞 alpha 又拉向 0；
    ②「格子错刷成健康」—— `board.fade_to_healthy()` 的过渡叠层不在 `set_marks` 管的表里、
    清不掉，回调在新局里把格子刷成健康贴图，而贴图只在 `set_tissue()` 时更新、
    **不是每帧重刷**，那一格会一直错到下次变状态为止。
    **两者触发条件相同：玩家点击跳过返场过场** —— 跳过只快进了相机补间
    （`main.gd` 的 `_tween`），别的没人管。HUD 那几条只有 0.6 倍时长，通常先跑完了，
    所以症状看起来只有细胞中招。
    现在 `CWMatch.start()` 统一收尾：杀 `_fade_tws`、调 `board.cancel_fade()`。
    ⚠ 写这类测试时**节点必须 `root.add_child()` 进场景树** ——
    不在树里的节点补间根本不跑，测试会无论修没修都是绿的（已实测踩过一次）。

22. **一局专属的状态，`teardown()` 里必须逐个撒手 —— 补间之外，字段和常驻控件同样跑得进下一局。**
    #21 说的是补间，这一条是它的另一半：`CWMatch` 是**跨局复用的同一个节点**，
    字段不置空就带着走。2026-09-10 逮到回放那三个：`replay`（播放器）、`_replay_bar`（控制条）、
    `pause_menu.online`（菜单形制，复位写在 `if online:` 里面，而回放局 `online` 是 false）。
    后果不是「有点脏」：控制条挂在下一局屏幕上（Kevin 那张联机局的图，底下正写着「0 / 133 · 4x」），
    而 `_unhandled_input` 见 `replay != null` 就把方向键和空格当播放键吃掉 —— **空格是「结束回合」**。
    **判据**：`start_xxx()` 里赋过的字段，`teardown()` 里都要有对应的一行；
    菜单/HUD 这类**形制开关**则统一在 `_prepare_ui()`（三条 start 的公共入口）先还原成默认档，
    别指望某一条拆局路径记得复位。
    ⚠ 撒手之后**跑着的协程要重新确认**：`_replay_loop` 每次 `await` 之后都重判
    `_loop_id` 与 `replay != null` —— 拆局完全可能正好落在那一帧里。
    「重启游戏后就正常了」是这类进程内残留的指纹。


## 关键决策记录

决策的时间线见 [开发日志](开发日志.md)；本节只保留「现在为什么是这样」的最终结论。

- **引擎与 UI 用问答桥解耦**：旧版验证过的架构，同一套规则可驱动 AI/人机/联机。
- **平衡数值抽成 CWTuning 旋钮**：规则平衡有大量未定项，需要不改代码就能批量试方案。默认值保持规则原文，让「按规则跑」永远是一行代码的事。
- **规则歧义处一律先拍临时决策、记进文档再实现**：见 [规则电子化说明](规则电子化说明.md)，每条都标了待团队确认。
- **确定性优先**：所有随机走 `game.rng` + `state_hash()` + 同种子重放测试。这是将来做联机（确定性锁步）和 AI 模拟打分的前提，代价很小但补不回来。
