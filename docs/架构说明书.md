## 项目是什么

《Cell War》桌游（免疫细胞 vs 癌细胞）的电子化新版工程。**规则已修改，从零重建，不继承旧版代码**；引擎 Godot 4（GDScript）。

- 规则原文（PRD）：`Cell_War PRD.md`（在仓库外，队友随时改，动规则相关代码前先重读比对；旧的《Cell War新版规则.md》已删除——2026-08-28 团队决定，它停在 61 格版）
- 旧版 demo（旧规则，可作实现思路参考）：https://github.com/Kevinnb66699/SpringSense-2026-2027-Cell-War

同步 apply 核心已经就位，**地基不缺了**。往下是：

## 核心设计：问答桥

引擎**不知道**谁在做决定。需要玩家抉择时，引擎调 `game.ask(pid, req)` 抛出一个「问题 + 选项列表」，由**桥**（`CWBridge` 子类）返回选中的下标。

```
CWGame ──ask(req)──────> CWBridge ──> 启发式 AI / 将来的 UI / 将来的联机对端
       <──选项下标──
       ──show_roll(…)──> CWBridge ──> 掷骰动画（引擎 await 到播完）
       ──show_result(…)─> CWBridge ──> 一句话通报（不 await，提示自己淡掉）
```

`show_roll()` 是同一条桥上的**单向通知**：引擎先用 `rng` 掷出结果，再把结果送给表现层去演，
并 `await` 到动画播完才继续结算。**表现层无权决定结果**，这是约定 #11。
它**广播给所有桥并按对象去重** —— AI 掷的骰旁观者也得看见，热座共用一个 UI 桥时只演一次。

签名：`show_roll(reason, value, sides, pid, at)`。`at` 是这次掷骰指向的格子
（攻击给目标格，突变/抗体给发动者所在格）—— 骰子要落在棋盘上那一格旁边，
坐标只有引擎知道。`pid` 可用于显示「谁掷的」，**但不用来给骰子染色**：
骰面颜色已经表示结果档位，再叠阵营色会两套语义打架（决策「甲」）。

`show_result(text, at)`（由 `CWGame.announce()` 广播，同样按对象去重）是掷骰的**结算说明**——
"攻击大成功"、"突变：无事发生"。**文字由引擎给**：点数怎么判读是规则，
表现层照着点数自己再判一遍等于把规则抄了第二份，改一处就会对不上。
不 `await`，因为提示自己会淡掉，不该卡住结算。

这样同一套规则代码可以驱动 AI 互搏、人机对战、热座、联机，互不干扰。**新增交互时不要在引擎里直接读 UI，一律走 ask()。**

`req` 的形状：`{ kind, pid, prompt, options: [{label, data}] }`
`kind` 取值：`setup_place` / `immune_revive` / `revive` / `action`

## 核心设计：流程状态机（2026-08-28）

**对局推进到哪一步是数据，不是调用栈。**

```
game.pending()          # 同步。返回「轮到谁、要做什么决定、有哪些选项」；空 = 对局结束
game.step(choice)       # 落子并推进到下一个决策点。只在表现层要演出时才挂起
game.snapshot()         # 整份状态（含 rng.state）
game.restore(snap)      # 原样放回去
```

**为什么要这样。** 原来的写法是 `run_game()` 一个循环跑到底，中间 `await bridge.ask()`。
那样「现在推进到哪儿」存在**调用栈**里（哪个函数、循环跑到第几个玩家），而调用栈没法快照。
AI 要评估「我走这一步会怎样」，需要的是：快照 → 落一步 → 继续跑几步 → 回滚，反复几千次。
所以流程位置必须搬进 `flow` 这个字典，推进必须是一次函数调用。

**三条随之而来的约定：**

1. **所有决定都是顶层选项。** `execute()` 内部**不许再发问** —— 一个行动就是一个原子。
   分化、裂解（要不要顺带净化）、血行转移落点、跃进方向，原来都是「先选行动、再问一次细节」，
   现在全部摊平成独立选项，参数直接写在 `data` 里。
2. **`advance()` 全程同步。** 从一个决策点走到下一个决策点的路上不掷骰、不演出。
   会掷骰的只有 `step()` 里执行行动那一段。
3. **随机数发生器的 state 属于快照。** 少了它，同一步走两遍会掷出不同的骰子，推演就没有意义。

`run_game()` 退化成一个薄壳：`while pending(): step(await ask(...))`。
AI 互搏、平衡模拟、无头测试都只要「跑完一局」，用它就够。

实测：单步 **0.106 ms**，一局 4 人局约 292 步 / 31 ms。3 秒的思考预算约合 **2.8 万步推演**。
`snapshot()` 深拷贝一次约 **0.16 ms** —— 真要跑到十万次量级时，
这里应该换成「落子 / 悔子」（make-unmake）而不是整份复制，但那要先有回滚日志。

`stop_at` 字段可以让 `advance()` 在某个阶段开头停下（测试和工具用，`""` = 不停）。

## 关键约定（改代码前必读）

1. **能量用「十分能量」整数存储**：`30` = 3.0 能量。避免浮点误差，保证回放/联机确定性。显示用 `CWData.fmt()`。
2. **所有随机数必须走 `game.rng`**。用了别的随机源，确定性测试（同种子两局哈希一致）会立刻抓到。
3. **不要给 `CWGame` 加名为 `log` 的方法**——GDScript 的内置数学函数 `log()` 不能被覆盖，会导致整个类编译失败。日志方法叫 `log_msg()`。
4. **新增 `class_name` 脚本后必须先 `--import` 再跑测试**，否则报 "Identifier not declared"。
5. **进入一格的所有效果都在 `CWActions.enter_tile()` 里**（定殖/净化/特殊组织收取/标记刷新）。移动、血管传送、复活落位共用它——加新效果加在这一处，不要散落各处。
6. **新增规则状态字段时，要同步更新 `CWGame.state_hash()`**，否则确定性测试会漏检。
7. **平衡数值改动走 `CWTuning`**，不要直接改 `CWData` 常量——`CWData` 是规则原文的记录。
8. **不要在代码或测试里写死棋盘尺寸**（`61`/`127`/`41`……）。一律引用 `CWData.TOTAL_TILES`、
   `CWData.BOARD_RADIUS`、`CWData.CANCER_WIN_WEIGHTED` 等常量。2026-08-27 从 61 格换到 127 格时，
   4 处写死的数字全部变成了假失败，排查成本远高于一开始就引用常量。
9. **改棋盘尺寸后必须重跑平衡**：收入公式挂钩「健康组织格数」，棋盘面积一变，
   低保/封顶的相对位置就全变了——61 格调好的数值搬到 127 格会让癌胜率从 51% 掉到 10%。
10. **表现层不许自己存一份棋盘坐标**。规则层用轴坐标 `(q,r)`，渲染层用「行,列」下标，
    两套坐标之间只有 `board.gd` 的 `axial_to_rc()` 一个转换点，源头永远是 `CWData`。
    2026-08-27 合并渲染代码前，渲染层自己抄了一份特殊组织下标，地图改到第三版时没跟上——
    画出来还是 5 个骨髓、代谢核心还在半径 4。`headless_test.gd` 的 `t_board_view()` 专门防这个。
11. **表现层不许决定结果**。所有随机由引擎的 `rng` 先掷出，再经 `CWBridge.show_roll()`
    送给表现层去演；动画只能演到那个数上，不能反过来决定它。
    掷骰动画的翻滚随机走节点自己的 `randf()`，**绝不碰 `game.rng`**。
    `headless_test.gd` 的 `t_roll_hook()` 会把钩子收到的点数和日志里实际结算用的点数逐次交叉核对。
12. **界面的设计分辨率是 960×540，不要改**。它和界面原型的画布同尺寸，
    原型里的 `1cqw` 正好换算成 `9.6px`，所有定稿坐标能直接乘过来；
    而且 1080p 全屏恰好是整数 2 倍，点阵字和像素贴图都能整数放大不糊。
    拉伸模式是 `canvas_items` + `keep`。
13. **点阵字号只能取字体网格的整数倍**：中文（缝合像素 10px）取 10 / 20 / 30 / 40，
    Logo 用的 Silkscreen 取 8 的倍数。取别的值会被重采样磨出灰边。
    同理，20px 字号下 1 个字模像素 = 2 屏幕像素，**字间距和位移也要取 2 的倍数**。
    `headless_test.gd` 的 `t_main_menu()` 会扫描场景里所有 Label 盯住这一条。
14. **要不要给某个随机加动画，是纯表现层决定**。静默用 `roll_d6()/roll_d3()`，
    带演出用 `roll_shown(sides, reason, pid)`；两者消耗的 rng 完全相同，可随时互换，
    不影响同种子可复现。**不要为了加动画去改 `roll_d6/roll_d3` 的签名** ——
    GDScript 的 `await` 会沿调用链往上传染，那样每个既有调用点都得跟着改。


## 关键决策记录

决策的时间线见 [开发日志](开发日志.md)；本节只保留「现在为什么是这样」的最终结论。

- **引擎与 UI 用问答桥解耦**：旧版验证过的架构，同一套规则可驱动 AI/人机/联机。
- **平衡数值抽成 CWTuning 旋钮**：规则平衡有大量未定项，需要不改代码就能批量试方案。默认值保持规则原文，让「按规则跑」永远是一行代码的事。
- **规则歧义处一律先拍临时决策、记进文档再实现**：见 [规则电子化说明](规则电子化说明.md)，每条都标了待团队确认。
- **确定性优先**：所有随机走 `game.rng` + `state_hash()` + 同种子重放测试。这是将来做联机（确定性锁步）和 AI 模拟打分的前提，代价很小但补不回来。
