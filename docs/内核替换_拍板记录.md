## 二、`UNDEFINED` 四项的裁决

两份 PRD 都没写明、必须拍板的四项，Kevin 09-15 裁决：

1. **2 人局全部数值** → **暂不在考虑范围内**。
   ⇒ 不实现、不测、对拍里标 `OUT_OF_SCOPE` 而不是 `UNDEFINED`。
2. **负数半值的舍入方向** → **参考 GDScript 当前实现**。
   ⇒ 即 `CWData.round_tenth(num, den) = (num + den/2) / den`（**纯整数运算**）。

   **实测（Godot 4.5，别凭印象）**：GDScript 的整数除法对负数**向零截断**
   （`-7 / 2 = -3`，不是 -4），于是这个「四舍五入」公式在负数上**系统性偏向零**：

   | 调用 | 实际 | 数学四舍五入 | |
   |---|---|---|---|
   | `round_tenth(-24, 10)` | **-1** | -2 | ❌ 差 1 |
   | `round_tenth(-26, 10)` | **-2** | -3 | ❌ 差 1 |
   | `round_tenth(-55, 100)` | **0** | -1 | ❌ 差 1 |
   | `round_tenth(25, 10)` | 3 | 3 | ✅ 正数没问题 |

   **但这条目前是空的**：四个调用点（`cw_cost.gd:515`、`cw_world.gd:443/567/1120`）
   实参**全都非负**，其中 `cw_world.gd:1120` 还显式写了 `maxi(raw, 0)`。
   ⇒ 所以它是一颗**没被踩响的雷**，不是现行差异。迁移时照抄公式即可；
   真要改成数学上更对的版本，单独立项 —— 别混在迁移里，否则分不清哪次漂是谁造成的。

   ⚠ **C# 侧和我们不一样，而且差两处**（`Settlement.cs:83`）：
   ```csharp
   public static int RoundTenth(double valueInTenths)
       => (int)Math.Round(valueInTenths, MidpointRounding.AwayFromZero);
   ```
   * **(一) 负数方向不同**：`AwayFromZero` 对 -2.4 给 -2，我们给 -1。（同为空雷，但雷不一样。）
   * **(二) 它收 `double`。** C# 侧能量是**浮点流过管线、末尾才舍入**
     （`RulePolicies.cs:22` `Round(double energyUnits)`、`:274` `income * 0.5`、
     `BoardRules.cs:85` `Math.Max(0, pressure) * 10.0 / 4`）。

   > 🔴 **更正（2026-09-15 晚）**：这里原来写「我们是全程整数、一个浮点都没有」——
   > **那是错的，我没查就写了**。实测内核**早就在用 `pow()`**（`cw_world.gd:805`）：
   > ```gdscript
   > var exp_term := pow(float(plain), exp_pct / 100.0) if plain > 0 else 0.0
   > ```
   > `_anaerobic_pool()` 返回 `float`，`_split_share(pool: float, count)` 里
   > `int(round(scaled / float(count)))` 落回十分位。
   > **也就是说【无氧呼吸】这条路上，两边是同一个形状**（浮点算、末尾 round）。
   >
   > **注意这个更正框本身也不够准**（09-15 深夜第三次修）：我们不止这一条路是浮点（共四座岛），
   > C# 的能量状态也是**整数**十分位、只有五个算式点用 `double`。
   > **以 §三·新三那张表为准**，那是逐行扫出来的。
3. **骰面值域** → **6 面骰子**（1..6）。
   ⇒ 这一条直接判定了 C# 的现成 bug：`CellRules.cs:194/205` 的 `rng.NextInt(6)` 产出 **0..5**，
   而 `RulePolicies.cs:326` 判 `roll == 6` 为暴击 ⇒ 实测 60000 次 **crit 0%**（应 16.7%）。
   **按本条裁决，这是 C# 的 bug，照修。**
4. **11 个特殊格坐标** → **按当前实现**。
   ⇒ 已逐个核对：`cw_data.gd:517-522` ↔ `MatchSetup.cs:15-20` **两边一致**，这条不用动。

## 三、两个新问题（由上面的拍板引出，之前没问过）

### 新一：桌面端怎么带 .NET 运行时？

决策 1 选了本地 sidecar，于是桌面客户端必须能跑 .NET。两条路：

* **(a) 自带（self-contained 发布）** ← **推荐**。玩家零安装，双击就能玩。
  代价：客户端体积 **+60~70 MB**（.NET 运行时本体）。
* (b) 要求玩家自行安装 .NET 运行时。体积省了，换来一道安装门槛和一类新的支持问题
  （「我装了怎么还是打不开」）。

推荐 (a)。这个游戏的玩家不是开发者，安装门槛的代价远大于几十 MB。

> ⚠ 注意 (a) 与**增量更新**的张力：self-contained 会把运行时和宿主打成一坨。
> 但**规则 dll（`CellWar.Core.dll`）仍然是独立文件**，所以「换规则」照样只发那一个 dll。
> 只有「换宿主 / 换运行时」才要全量发版 —— 那本来就该全量发。

> 不是并行模拟。
>
> ⇒ **决策 2 的代价大幅下降**：不是「新建服务端权威」，而是

### 新三：浮点允许出现在哪里？（本节 09-15 晚按实测重写过）

**先把事实摆正**（**这一节我改过两次，前两版都不准，以下是逐行扫出来的**）：

**两边都是「整数状态 + 局部浮点算式」**，不是两种数值模型 ——
C# 的能量同样是整数十分位（`WorldState.cs:240` `public required int Energy` 注释原文
「整数十分能量，如 3.0 = 30」）。

| | 浮点算式出现在哪（剥掉注释逐行扫） |
|---|---|
| **我们：四座岛** | ① 无氧 `cw_world.gd:805-806/822-823`（`pow` + `int(round)`）② 过载 `:471-472`（`pow` + `int(round)`）③ 瓦伯格 `:752` 与 `:1029`（`int(ceil(gain * WARBURG_PERCENT / 100.0))`）④ 吞噬吸血 `cw_damage.gd:558`（`int(ceil(actual / 2.0))`） |
| **C#：五个算式点** | `Settlement.RoundTenth(double)`、`RulePolicies.cs:22/260/274`、`BoardRules.cs:85/98` |

> 此前这张表写的「我们只有【无氧呼吸】这一条路」「C# 是整条管线都收 double」**两头都不准**，
> 而且 `cw_world.gd:749` 那个行号也错了（pow 在 `:805`）。
> 我连着写错两版，根因是同一个：**没有逐行扫就下了全称判断。**

所以不是「整数 vs 浮点」的二选一，而是**「浮点允许出现在哪里」的边界该划在哪**。

### 🔴 真正的浮点差别只有一处，而且是 blocking

**【E-增生】的概率判定**：我们是**纯整数千分位掷点**
（`cw_world.gd:708-720` 算出千分数，再拿 `randi_range(1,1000)` 比），
C# 是 `BoardRules.cs:97-98` 的 `rng.NextDouble() < adjacent.Length * rate`（`rate` 是 `double`）。

这既是跨平台确定性风险，**也是对拍 L1 的硬阻塞** ——
`docs/对拍规格_CWX.md` 已实测：不改这一行，2 人局跑 40 步就撞 **64 条** `RNG_NO_COUNTERPART`，
因为浮点抽取在我们的带子上**没有任何对应物**。E 阶段 100% 走它、每回合约 27 次。
⇒ **这条要排在所有对拍工作之前**。

**推荐：把边界划在「真幂运算」上 —— 只有幂允许浮点，其余全整数。**
理由按重要性：

1. **这正是我们现在的做法**，而且它已经被 3502 项检查盯了几个月。
   照搬一个在跑的口径，比发明一个新的安全。
2. **对拍成本**。整数对整数逐位比；浮点对浮点只能带容差比，
   而「容差内」会吞掉真实的 off-by-one 规则差异 —— 那正是对拍要抓的东西。
   把浮点收窄到两处，就只有那两处需要容差。
3. **神经网络训练要可复现**（决策 7）。浮点在不同 CPU / JIT 上有末位差异。
   收窄到两处之后，要不要再把这两处也查表化，可以**单独**评估，
   不必让整条管线陪着一起改。——**这一条是决策 7 引出来的，之前没人提过。**

**两处真幂运算**：【无氧呼吸】的 `^0.3`（两边都已实现）、
【S-过载】的 `^1.18`（2026-09-15 落进 GDScript，C# 侧待补）。

> 关于这两处要不要预计算查表：**先不做**。
> GDScript 侧 09-15 落地时就是直接 `pow()`，理由是**照抄已有先例**而不是新开一种口径 ——
> 内核里本来就有 `pow()`，为新规则单独发明查表反而会让同一个内核里出现两套数值口径。
> 真要查表，应该**两处一起、两边共用同一张表**（那张表本身就是最强的对拍锚点），
> 作为一个独立议题推进，不要夹在换内核里做。

## 七、2026-09-15 深夜：压测推翻了我给 Kevin 的四条

七路调研之外又跑了一次专项压测（四路取证 + 三路证伪）。以下四条是**我自己说错的**，
以压测实测为准。

### ① 「C# 的 `MatchSetup.BoardRadius` 是 const 6，要新开任意棋盘入口」——**错**

`MatchSession(WorldState initial, ulong seed = 12345)` 是 **public 构造函数**，收任意 `WorldState`；
`MatchSetup.Create` 只是 `Start()` 的便利包装。`BoardRadius` 全仓只有 3 个引用、全在
`MatchSetup.cs` 内部，其余一律读实例字段 `s.Board.Radius`。
⇒ **决策 10 要的「直接灌一个盘面」入口已经存在，不用开。**

### ② 教程的结论对，但**理由要换**，而且方向比我说的更强

我给的理由是「教程留 GDScript 会让内核永远删不掉」。压测判定：**作为技术判断不成立** ——
逐条对照 `guide_director.gd` 那 78 行，C# 只差三样（关胜负判定、观测补 `PlayCounter`、
一个对活对局的受控写入入口），前两样是小时级。

**真正的理由是新 PRD 第一关 GDScript 根本做不出来**：它要「两个横向连接的健康组织」= 两格棋盘。
* **C# 零改动就能跑**（实测：两格 `WorldState` 构造成功、`(0,0)` 在盘邻居数 = 1、
  `QuoteMove` 报 0.5、`MatchSession` 起步给出含 `Move` 的 4 个合法选项）——
  因为 C# 的棋盘形状**就是 `Board.Tissues` 这个字典**。
* **GDScript 做不到**：邻接由**标量半径**算出（`cw_game.gd:34/39`），与 `game.tiles` 解耦；
  `build_board(radius)` 只能整圈铺，最小 radius 1 = **7 格**，没有「两格」这个概念。

而**真正的风险也不是「删不掉」，是「教错规则」**：教程挂在一个正在退役、
