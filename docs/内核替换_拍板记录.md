## 二、`UNDEFINED` 四项的裁决

两份 PRD 都没写明、必须拍板的四项，Kevin 09-15 裁决：

1. **2 人局全部数值** → **暂不在考虑范围内**。
   ⇒ 不实现、不测、对拍里标 `OUT_OF_SCOPE` 而不是 `UNDEFINED`。
2. **负数半值的舍入方向** → **参考 GDScript 当前实现**。
   ⇒ 即 `CWData.round_tenth(num, den) = (num + den/2) / den`（**纯整数运算**）。

   **实测（Godot 4.5，别凭印象）**：GDScript 的整数除法对负数**向零截断**
   （`-7 / 2 = -3`，不是 -4），于是这个「四舍五入」公式在负数上**系统性偏向零**：

   | 调用 | 实际 | 数学四舍五入 | |
   |---|---|---|---|
   | `round_tenth(-24, 10)` | **-1** | -2 | ❌ 差 1 |
   | `round_tenth(-26, 10)` | **-2** | -3 | ❌ 差 1 |
   | `round_tenth(-55, 100)` | **0** | -1 | ❌ 差 1 |
   | `round_tenth(25, 10)` | 3 | 3 | ✅ 正数没问题 |

   **但这条目前是空的**：四个调用点（`cw_cost.gd:515`、`cw_world.gd:438/511/1064`）
   实参**全都非负**，其中 `cw_world.gd:1064` 还显式写了 `maxi(raw, 0)`。
   ⇒ 所以它是一颗**没被踩响的雷**，不是现行差异。迁移时照抄公式即可；
   真要改成数学上更对的版本，单独立项 —— 别混在迁移里，否则分不清哪次漂是谁造成的。

   ⚠ **C# 侧和我们不一样，而且差两处**（`Settlement.cs:83`）：
   ```csharp
   public static int RoundTenth(double valueInTenths)
       => (int)Math.Round(valueInTenths, MidpointRounding.AwayFromZero);
   ```
   * **(一) 负数方向不同**：`AwayFromZero` 对 -2.4 给 -2，我们给 -1。（同为空雷，但雷不一样。）
   * **(二) 更要紧：它收 `double`。** C# 侧能量是**浮点流过整条管线、末尾才舍入**
     （`RulePolicies.cs:22` `Round(double energyUnits)`、`:274` `income * 0.5`、
     `BoardRules.cs:85` `Math.Max(0, pressure) * 10.0 / 4`），
     我们是**全程整数、一个浮点都没有**。
     这不是口径差异，是**两种数值模型**，边界上必然对不齐。迁移时必须整条管线一起定，
     不能只改 `RoundTenth` 一个函数。见 §三·新三。
3. **骰面值域** → **6 面骰子**（1..6）。
   ⇒ 这一条直接判定了 C# 的现成 bug：`CellRules.cs:194/205` 的 `rng.NextInt(6)` 产出 **0..5**，
   而 `RulePolicies.cs:326` 判 `roll == 6` 为暴击 ⇒ 实测 60000 次 **crit 0%**（应 16.7%）。
   **按本条裁决，这是 C# 的 bug，照修。**
4. **11 个特殊格坐标** → **按当前实现**。
   ⇒ 已逐个核对：`cw_data.gd:500-505` ↔ `MatchSetup.cs:16-22` **两边一致**，这条不用动。

## 三、两个新问题（由上面的拍板引出，之前没问过）

### 新一：桌面端怎么带 .NET 运行时？

决策 1 选了本地 sidecar，于是桌面客户端必须能跑 .NET。两条路：

* **(a) 自带（self-contained 发布）** ← **推荐**。玩家零安装，双击就能玩。
  代价：客户端体积 **+60~70 MB**（.NET 运行时本体）。
* (b) 要求玩家自行安装 .NET 运行时。体积省了，换来一道安装门槛和一类新的支持问题
  （「我装了怎么还是打不开」）。

推荐 (a)。这个游戏的玩家不是开发者，安装门槛的代价远大于几十 MB。

> ⚠ 注意 (a) 与**增量更新**的张力：self-contained 会把运行时和宿主打成一坨。
> 但**规则 dll（`CellWar.Core.dll`）仍然是独立文件**，所以「换规则」照样只发那一个 dll。
> 只有「换宿主 / 换运行时」才要全量发版 —— 那本来就该全量发。

### 新二：服务端权威之后，服务器要真的跑对局

现在服务器只**转发消息**（客户端各自算）。改成权威之后，**服务器要跑真实对局**：
每局一份世界状态、每步都要算。负载性质完全变了。

要定的是「先按多少并发设计」。**推荐：先不设计，按单机一进程做，测出来再说。**
理由：C# 内核是纯函数 + 结构共享，单局开销极低；现在连真实并发数都不知道，
提前设计容量是凭空想象。**但要在第一版就把「一局 = 一个可序列化的 checkpoint」做对**，
那是以后横向扩容的唯一前提。

### 新三：整数管线 还是 浮点管线？（我推荐整数，理由在第 3 条）

两边现在是两种数值模型：**我们全程整数十分位**（内核里一个浮点都没有），
**C# 浮点流过、末尾 `RoundTenth(double)` 才落地**（见 §2.2）。替换时必须二选一。

**推荐：把 C# 侧改成整数管线**，理由三条，按重要性排：

1. **神经网络训练要可复现**（决策 7）。浮点在不同 CPU / 不同 JIT 版本上会有末位差异，
   一旦进了状态，同一条轨迹重跑就不一定还原。整数没有这个问题。
   ——**这一条是决策 7 自己引出来的，之前没人提过。**
2. **对拍的成本差一个数量级**。整数对整数可以逐位比；浮点对整数只能带容差比，
   而「容差内」这三个字会吞掉真实的 off-by-one 规则差异 ——
   那正是对拍要抓的东西（参见【S-过载】的 `^1.18`）。
3. **不是重构，是删代码**。整数管线比浮点管线简单：没有舍入时机问题、
   没有「在哪一步落地」的选择、没有 `0.1 + 0.2` 那类惊喜。
   而且我们这边 9405 行已经证明整条规则集**可以**纯整数实现。

**唯一的例外要单独处理**：【S-过载】的 `^1.18` 和【无氧呼吸】的 `^0.3` 是真幂运算。
这两处用**预计算查表**落成整数（能量与块大小的取值都有限），而不是在运行时调 `pow()`。
表可以由脚本生成并进仓库，两边共用同一张表 —— **那张表本身就是最强的对拍锚点**。
