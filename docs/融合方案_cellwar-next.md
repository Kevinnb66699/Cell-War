## 二、三条硬冲突（必须先说）

**你的三条保留要求，和「把 C# 内核搬进当前项目」目前是互斥的。** 不是难做，是方向相反：

### ① 网页版会当场死

Godot 的 **.NET 版没有 Web 导出**（4.x 全系至今如此）。我们今天才把网页版发上线、
证书和 wss 反代都配好了。内核一旦要求 .NET 运行时，网页版就不存在了。

⚠ **这一条要实测确认再定生死**：新仓库的 `project.godot` 写着 4.7，而交接文档实测的是
4.4.1 mono。如果 4.7 的 .NET 真加了 web 导出，这条会松动 —— 但那要拿真的 4.7 .NET 构建
导一次才算数，不能靠说法。

### ② 热更新会死

我们的热更是「下载 `.pck` → `load_resource_pack` → 覆盖包里的**纯文本** `.gd`」。
**C# 编译进程序集，补丁包换不动它。**

也就是说：规则一旦搬进 C#，**规则改动就再也不能热更**。而规则正是改得最频繁的那部分 ——
光今天就发了四个补丁，其中三个是规则或美术。以后每改一条规则都要全量发版、玩家重新下载
整个客户端。

### ③ 规则和联机是**倒退**，不是升级

新内核自己写着「当前规则为基础切片」。搬过来意味着要重新补上：约 31 张卡的效果、
类型技能、修饰器、骨髓抽牌、高级 E 类效果；联机整套（房间 / 观战 / 投降 / 回放 / 断线）
要从零做。而这些在我们这边是**跑在线上、有 3479 项检查盯着**的。

## 三、那新内核什么值得要？

**不是规则**（规则我们更全、更实），是**架构**：

- **结构共享** `PagedMap` **+ 事务 + fork** —— 同一个世界开分支几乎免费。
我们现在的 MC / MCTS 是「深拷贝整局再模拟」，那是最贵的做法。
- **checkpoint / 恢复** —— 失败处理冻结执行前 checkpoint，能真恢复领域与调度状态。
- **输入屏障** —— 输入必须匹配 request + revision + 合法选项，从机制上堵死非法输入。
- **确定性 xoshiro + 版本保留** —— 服务端权威重放、RL 训练都要这个。

这几样对**强化学习训练**和**服务端权威**的价值，比对「玩家现在能不能玩」的价值大得多。
换句话说：**它是给未来的训练/服务端准备的地基，不是给今天的客户端准备的替换件。**

## 拍板（2026-09-15）

**Kevin 定了：走路线 A —— C# 内核放到进程外，客户端保持标准版 Godot + 纯 GDScript。**

确认过的口径：「把新仓库的内核迁移过来、UI 什么的都用原来的」——方向一致。
但那句话**区分不了同进程与进程外**（队友的 `godot-client` 也是 GDScript UI），
所以特意问了一次，答案是**进程外**。于是：

* 网页版活着、`.pck` 热更活着、UI 与外围功能全留
* 单机要在本机起一个 C# sidecar 进程；网页版的单机另议（见路 A 那条的 ❌）
* 本地 sidecar 自己怎么热更 → `docs/路线A_内核热更方案.md`（结论：`CellWar.Core.dll`
  压进现有 .pck 补丁包，走同一个 build、同一份签名、同一次 quarantine）

⚠ **「UI 保留」不等于零成本**，量过：UI 层 53 个文件 19192 行，对内核有约 **740 个耦合点** ——
271 次直接读 `game.*`（`tiles`/`cells`/`round_no`/`tune`/`logs`），472 次 `CWData.*`。
后者里约 59% 是词汇表（`fmt` 92 / `Faction` 84 / `Tissue` 30 / `Special` 29 / `CancerType` 23 /
`ImmuneType` 21），可以原样留在 GDScript 侧；**剩下 41% 是规则数值**
（`ANAEROBIC_CELLS_K`、`AEROBIC_LEVEL_BASE_BY_PLAYERS`、`ANTIBODY_DAMAGE`、`TOXIN_COST`、
`LEVEL_MIN_MEMORY_BY_PLAYERS`、`HAND_MAX`…），UI 拿它们来**显示**右栏预计收入、技能费用、
等级门槛、卡面数字。

换内核之后这些会变成**两份**：今天它们必然一致（同一个 `CWData`），换成 C# 之后一边一份 ——
而 `ANAEROBIC_CELLS_K` 在 C# 里**压根不存在**。于是 UI 显示「×120%」、内核按没有 k 算，
**不报错，玩家只觉得数字对不上**。这就是「两套实现要落两遍」的具体形状，
也是为什么对拍必须先行。

## 四、四条路





### 路 A：内核放到进程外，客户端一行 C# 都不引入 ★目标形态

把 `CellWar.Core` 做成**权威服务端**（新仓库已经有 `CellWar.Server` 这个壳），
我们的 Godot 客户端**保持纯 GDScript**，通过 WebSocket 说话 —— 和现在的联机路径一模一样。

- ✅ **网页版活着**：客户端仍是标准 Godot 4.5，照常导 web
- ✅ **热更活着**：客户端仍是 `.gd`
- ✅ **UI 全套原样**
- ✅ **联机天然**：本来就是服务端权威，比现在的「客户端跑影子对局」更干净
- ❌ **单机也要连服务器**。桌面可以本地起一个 C# 进程；**网页版的单机就没了**
（除非把 C# 编到 WASM —— Blazor / NativeAOT-LLVM，代价很大，另评估）
- 工作量：把现有 `CWNetClient` / `cw_net.gd` 的报文对到新内核的 observation / input 协议



### 路 B：全面倒向 Godot .NET 客户端

- ❌ 网页版、热更、完整规则、联机 —— **四样全丢**，然后重建
- 只有在「以后不做网页版、也不要热更」的前提下才成立



### 路 C：不搬内核，搬架构

在现有 GDScript core 上自己实现结构共享 / 事务 / checkpoint。

- ✅ 三样全保
- ❌ 工作量巨大，而且 GDScript 做结构共享，性能远不如 C#



### 路 D：先对拍，不融合 ★**第一步，且是任何一条路的前置**

不动任何东西，先让两个内核**在同一份输入下对拍**：

- 我们有 `CWStateCodec.state_hash()`（逐位状态哈希）和 `CWReplay`（种子 + 作答下标串）
- 新内核有 checkpoint + 确定性 RNG
- 拿**同一个种子 + 同一串作答**，逐步比世界状态

产出是一张**「新内核到底差什么、差多少」的确切清单**。
现在「基础切片」只是一句话；对拍给出的是可执行的差异表。

**没有这张清单，「融合」等于拿已验证的规则去换未验证的。**

> **2026-09-15 更新：规格已出 → `docs/对拍规格_CWX.md`（方案，未拍板）。**
> 结论与这一节的设想有三处不同，都是实测逼出来的：
> * **不是一套，是三层**：L0 契约靶场（1.2 秒、两边零改动）/ L1 教师强制单步重放 / L2 整局闸门（阶段 0 不做）。
> * **不走 `state_hash()` 跨语言比**，也不走 `CWReplay` 的作答下标串 —— 下标在两个内核之间不通用，
>   改成语义键；状态改成逐字段 diff（同样的代价，差异直接落到字段名上）。
> * **不走 checkpoint**：实测决策屏障处 C# 的事件队列恒空（60/60），投影器天然产不出那一块；
>   改走 `BasicRulesEngine` 的纯函数面，**代价是验不到调度层**（要队友加一个 `Clamp` 入口才补得上）。
>
> 而第六节那四个问题，本轮已经自己答掉两个半，见规格第 6 节与开发日志 09-15（二）。

## 五、建议的顺序

1. **先走 D**（1~2 天）：搭对拍，产出差异清单。
2. 拿清单和队友对一次，定一件事：**补齐 C# 规则，还是承认规则继续留在 GDScript？**
3. 若决定用 C# 内核 → 走 **A**，而且**先只用在联机**（服务端权威），
  单机继续跑本地 GDScript core。这样网页版、热更、单机一个都不丢，
   联机那条路先吃到新内核的好处，风险也只压在一条路上。
4. 网页版的单机要不要也上 C#，等 WASM 那条路评估过再说 —— 不要现在就赌。
