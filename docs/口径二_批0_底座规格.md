## A. 组件定义

### A-1 · 观测协议 v1

落点：`docs/观测协议_v1.md`（规格正本）+ C# 生产者 + GD 生产者 + GD 消费者。

#### A-1.1 三条总规矩

1. **零浮点**。能量、固化计数、储量、费用、收入一律**十分位整数**（`int`）。今天 C# 是 `double`（`core/CellWar.Core/MatchSession.cs:5-10`，`/10.0` 散在 `:29,45,52,67,70,72,79,107`），与 canon「一个浮点都不许有」（`docs/对拍规格_CWX.md:353`）和 UI 侧 92 处 `CWData.fmt` 都打架。**协议 v1 另起 record，不改 `MatchObservation`**（它被 `ObservationTests.cs:6-17` 钉着，改它等于删测试）。
2. **零 rng**。协议里**根本不存在** rng 字段（比 GD 今天的「置 0」`cw_net.gd:295` 更强）。rng 只走 `save()`（宿主专用）。
3. **未知字段 = 硬错**（`docs/对拍规格_CWX.md:344`）。缺失字段另论：只有 tier B 派生量允许缺，且必须由 envelope 的 `produced_tiers` 声明。

#### A-1.2 Envelope

```jsonc
{
  "p": 1,
  "ruleset": { "host_abi": 1, "rules_build": "core-slice-1+b0", "digest": "sha256:…" },
  "rev": 1837,
  "obs_seq": 412,          // 这份观测反映的是「第 obs_seq 条事件之后」的状态
  "viewer": 2,             // >=0 席位 / -1 观众 / -2 全知（禁止过网）
  "open_hands": false,     // 仅 viewer=-1 有意义，对齐 cw_room.gd:32-34 的 watch_hands
  "produced_tiers": ["A"], // 见 A-1.6；GD 生产者恒 ["A","B"]
  "full": true,            // v1 恒 true
  "base": null,            // 增量留位，v1 恒 null
  "state": { … },
  "ask": { … } | null,
  "logs": { "from": 412, "lines": ["…"] }
}
```

`ruleset` 三个字段**必须分开**（硬不变量③，`docs/内核替换_迁移计划.md:218-224`）：`host_abi` 是握手闸，`rules_build` 与 `digest` 只上报、不闸。`digest` 同时对冲老回放去留（跳号 or 自动失效两条路都不用改协议）。

**增量留位不实现**：底座已有 `IStateStore.Diff` / `ChangeSet`（`core/CellWar.Core/IStateStore.cs:31,170-176`），保留窗口 32 版本（`InMemoryStateStore.cs:15`）。`docs/路线A_内核热更方案.md:489` 警告过体积；批 0 只量一次真实体积写进文档（`cw_net.gd:7` 的「35~41 KB / 压完约 2 KB」是 2026-09-02 实测，此后快照多了 6 个顶层键 + `toxin_round` + `chemo_cd`，**早已过时**）。

### A-2 · CWMirror

落点：`game/scripts/kernel/cw_mirror.gd`，`class_name CWMirror extends RefCounted`。

#### A-2.1 定位

**CWMirror = 观测协议 v1 envelope 的 GD 解码结果。** 不是「`CWGame` 剥成只有状态的壳」——
`cw_state_codec.gd` 的 25 键里 `flow` / `pending` / `rng` 是引擎私货（`docs/对拍规格_CWX.md:388`，C# 天然产不出），照那份清单建第一天就卡住。

它只做三件事：装载 envelope、按 UI 今天的形状把字段摆好、提供与 `CWGame` 同签名的查询方法。

#### A-2.2 三条形状不变式（各配一条测试）

1. **`cells` 是稠密数组、下标即 cell id、死者也在里面**。`match.gd:286,1524-1525` 的 `_cell_nodes` / `_decos` / `_was_alive` / `_last_pos` 四个数组与它逐下标配对，`cell_deco.gd:30` 的 `index` 也是。**不得改成稀疏字典。**
2. **`tiles` 是 `Dictionary[Vector2i]`**（`_sync_tiles` 每帧全量遍历，`match.gd:1349-1381`）。
3. **一次只装一份 envelope，绝不合并多份**。传送演出靠 UI 自己差分认出来（`match.gd:1591-1594`：上一帧与这一帧都活着、`hex_dist > 1`），引擎不发信号；压掉中间态 = 传送溶解演出静默失效，或多格移动**误触发**它。

#### A-2.3 同步语义（修掉草案二的「别名」缺陷）

`sync_from(game)`（InProc 用）**每次调用重新绑定全部引用**，不是一次绑定长期持有。
理由：`cw_state_codec.gd:31-55` 的 `restore()` 把 `tiles` / `cells` / `players` / `events` 逐个 `= 新对象`，而 restore 在三条热路径上每步都跑（联机每份 state 报文 `cw_net_client.gd:316`、回放快退 `cw_replay.gd:312`、续档开局）。一次性别名会静默悬空、棋盘冻结且不报错。
⇒ 测试 `t_mirror_survives_restore()`：跑到第 N 步 → `restore(旧快照)` → 再 `sync_from` → 与 `game` 逐字段相同。

#### A-2.4 供 UI 的查询方法（与 `CWGame` 同名同签名）

索引：`cell_of(pid)` · `player(pid)` · `tile(c)` · `cells_at(pos, faction)` · `living_cells(faction)` · `is_cancerous(c)` · `is_over()` · `chemo_track_at()`

* `can_save()` —— 今天的判据是 `game._pending.is_empty()` 取反（`cw_save.gd:35`、`match.gd:104`），即「**停在顶层 pending 边界上**」。中途询问期间 `_pending` 为空 ⇒ 自动返回 false，正合快照只能取在 pending 边界的不变式（`cw_game.gd:178-185`）。

#### A-3.1 形制：为什么只能是「镜像 + 有序条目队列 + 一个 answer」
