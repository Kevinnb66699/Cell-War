## 2026-08-29 · 修饰批 15 张全部实装：66 张卡只剩永久技能（494 项全绿）

条目进 `state_hash` 与快照；死亡清空（自身的修饰随细胞消散）。

**判定链定型**（定案 #59/#60）：骰面 → 世界事件并给 → 补体调理失败自动重掷

主线第二片卡牌效果：趋化募集 / 效应细胞浸润 / 炎症风暴 / 免疫风暴 /

挑哪档），而抽卡可能发生在任何自动结算里（踩骨髓、血管奖励、抗原变异、S 阶段产出），
所以 `draw → resolve_event → enter_tile → collect_special` 一路补 await，
直到 `pending()`/`step()` 也变协程。流程状态机的三条约定随之修订（架构说明书）：
**行动入口仍全是顶层选项**，只有结算里的后续决定走 `game.ask`
（新 kind：free_move / pick_cell / pick_tile / pick，tag=卡名）；
同步桥下 await 立即完成——AI 推演零挂起的性质没丢。
「可以不做」的询问**下标 0 恒为停止/放弃**：基类桥答 0 天然安全，
中止对局时 ask 固定答 0 也落在安全档上。

**实现口径**记进规则电子化说明 #51~#56（⏳ 待团队过目），最想让团队看一眼的两条：
全身免疫动员的迁移**费用照付**（PRD 没写免费，+1.5 当路费）；
炎症性趋化每步 0.2 **照过移动费修正**（净化费/基质阻隔/迁移激活都适用）。

**事件吐司带效果**（Kevin 试玩第五轮要求）：原来只喊「事件【X】立即结算」，
现在每张事件在结算处自己喊实际效果——即时结算的报数值
（「全体免疫 +1.0 · 自身另 +0.5」），要选择的先报给了什么（「免费移动最多 2 步」），
未实现的兜底喊「效果待实现」。通报挪进各结算分支是因为**数值在那儿才算得出来**。

界面零改动——中途询问天生走 `_ask_generic` 的「带 to 进棋盘、不带进按钮」通路。
AI 桥补了三类应答（走位打分 / 风暴选人按波及面 / 基因组二择按记忆能量），
因为 AI 虽不打牌，骨髓和血管照样会喂它事件卡。

rng 拨盘工具 `_rig_d3`（穷举附近状态让下几掷必出指定点数，测二择用）。

自然落进「弃置这张？确认 / 取消」。零新机器，弃置从此**只有一个入口**。

## 2026-08-29 · 试玩第三轮：右键的归属权（410 项全绿）

子问句里按钮明明标着「返回（右键 / Esc）」，但右键落在悬停的卡上时，
被卡自己的「右键弃置」手势抢走、直接跳去了弃牌确认——同一个右键，
两处各自为政。

定一条归属规矩，写在询问桥里：**这一问有没有「取消」决定右键归谁**。
有取消（目标态 / 各确认条）→ 右键一律 = 取消，点在卡上也一样——
按钮上标了快捷方式，卡不该抢；没有取消（主按钮栏）→ 卡上右键才是
弃置入口。实现只改 `_prompt` 里 `on_dcard` 一处：有 cancel 时改发
cancel 的值。测试补两条（目标态右键点卡 = 取消、取消后流程照常）。

## 2026-08-29 · 试玩追报：抽到事件卡「无声结算」的迷惑（408 项全绿）

Kevin：「为什么点了两下抽卡只拿到一张卡？」——因为有一次抽到了**事件卡**：
PRD 规定事件卡抽取后立即结算并弃置、不进手牌。规则没错，但界面上
**什么都没演**（不进手牌就没有飞卡动画），玩家看到的是「花了 0.5、没拿到卡」。

修：`cw_cards.draw` 抽到事件时 `announce("事件【卡名】立即结算")` 弹在
抽卡细胞头上（走既有吐司通道，无头/AI 桥自动无视）；「抽卡落空」同样补了提示。
更完整的事件卡结算演出（卡面飞出翻面之类）记入界面待办，不在这轮做。

## 2026-08-29 · 试玩第二轮：按钮被右侧竖条挡住（408 项全绿）

第一轮的「让位 312px」把标题救回来了，却把按钮挤了出去：HBox 里
固定宽 pad + 固定宽提示文字 + 按钮的最小宽超过底条 673px 的框，
容器不裁剪、直接向右溢出，按钮钻到了右侧竖条底下。

修法不是继续缩字，而是改布局契约：**让位形态下提示块弹性化**——
提示块 `SIZE_EXPAND_FILL` 吃掉行内剩余宽度（顺便顶开按钮，替掉原来的
弹簧 spacer），提示行 `AUTOWRAP_ARBITRARY` 按可用宽度换行，最小宽归零，
怎么也挤不出框。非让位的旧形态（迁移等）布局原样不动。
「打不出」的解释文案同步再缩短一档。测试补了一条真布局断言：
让位形态下最后一个按钮的右缘 ≤ 底条右缘。

## 2026-08-28 · 同步 apply 核心：流程从调用栈搬进状态机

团队定的下一步。起因是队友（猫靴）提议把核心改成 Elm 那样的**不可变状态链**，
理由是蒙特卡洛树搜索需要引擎能反复复原重算。

**结论：目标对，手段不对。**
- 「随机种子是状态的一部分」这条**引擎早就做到了**（`rng.seed` + 全部随机走 `game.rng`
  + `state_hash()` + 同种子双局哈希一致的测试），不需要为它重构。
- **GDScript 没有结构共享**（HAMT），`Dictionary`/`Array` 只有 `duplicate(true)` 全量深拷贝。
  实测一次 **0.16 ms**。「不可变」在这里等于每步深拷贝，**越是为了 MCTS 越不该这么做** ——
  真要快就该走「落子/悔子」（make-unmake）。
- 真正挡路的**不是可变性，也不是 `await`**（同步桥下 await 几乎零成本），
  而是**控制反转**：流程位置存在调用栈里，AI 没法从任意状态往下推演。

所以做的是：**把流程位置从调用栈搬进数据**。

- `CWGame.pending()` / `step(choice)` / `advance()` —— 流程游标存在 `flow` 字典里
- `snapshot()` / `restore()` —— 整份状态含 `rng.state`
- `run_game()` 退化成薄壳 `while pending(): step(await ask(...))`，AI 互搏与测试照旧
- **所有决定摊平成顶层选项**，`execute()` 内部不再发问 —— 一个行动就是一个原子。
  分化（4 项）、裂解（并净化 / 暂不）、血行转移落点、跃进方向都改成独立选项
- `CWTurn` 只剩 `begin_turn`/`end_turn`，回合循环搬进状态机
- `CWSetup` 拆成 `begin` / `place_options`+`place` / `finish`；
  `CWWorld` 拆成 `round_start` / 两处复活的 `*_options`+`revive_*` / `aerobic` / `e_phase`
- 新增 `stop_at`：让 `advance()` 在某阶段开头停下（测试与工具用）

**验收测试三项**（无头测试 220 → **229 项**，全绿）：
① 快照回滚后逐位还原、rng 也还原；
② **推演不污染主线** —— 一局里插了 125 次「快照→乱跑→回滚」，主线状态与对照局完全一致；
③ 行动原子性 —— 整份行动表里没有「选了还要再问一次」的项。

**性能**：重构零损失（`run_game` 30.6 ms/局 vs `pending/step` 31.1 ms/局），
单步 **0.106 ms**，4 人局约 292 步/局。**3 秒思考预算约合 2.8 万步推演** ——
按一次截断 playout 30 步算，够跑 900+ 次，扁平蒙特卡洛完全可行，
真上 ISMCTS 也有余地。UI 那条路截图验过，没断。

顺带确认：**2 人局不再作为平衡目标**（团队定，规则原文本来也只定义 4/6 人）。
另外世界事件尚未设计，平衡还要重调，所以本轮不动数值。

## 2026-08-27 · 两个真 bug：返回主菜单卡死 / 开场过场从来没播出来过

团队试玩报的两条，查下来都比表面严重。

### 一、返回主菜单后「卡死」

日志里刷的是 `Invalid call. Nonexistent function 'cells_at' in base 'Nil'`，
而且是 **Debugger Break** —— **`--debug` 模式下 Godot 遇到错误会断在调试器里，
画面就停住了**，所以看起来是「卡死」。

根因：返回主菜单时，那次「等你点格子」的询问**还卡在 await 上**，
`_prompt()` 里连上的 `board.tile_hovered` / `tile_clicked` 从没断开。
对局释放、`game` 置空之后，鼠标往棋盘上一动就去调用了已释放对局的 `cells_at`。

修法是两边配合：
- 引擎加 `CWGame.aborted`，`run_game` / `run_all` / `_run_player_turn` / `_place_cells`
  各自在下一个检查点收摊，让卡住的那次询问能**安全地一路展开回来**；
- 桥加 `abort()`，把卡住的 `Answer` 唤醒（同步展开），`_prompt` 于是走到断连接那几行。

`teardown()` 里顺序要紧：**先 `aborted = true`、再 `bridge.abort()`、最后才 `dispose()`**。
反过来的话展开途中会碰到已经置空的模块。

### 二、开场过场**从来没播出来过**

团队说「开局地图的移动动画不好看，改回去」。查下来根本不是好不好看的问题 ——
**它一次都没播过**，一直是瞬间就位。

根因：**Control 的 `gui_input` 不会自动把事件标记成已处理**。
点「开始对局」那一下先进菜单项的 `gui_input`（启动过场），
然后**同一个事件继续传到 `main.gd` 的 `_unhandled_input`**，
在那儿被「过场中点一下跳过」当成跳过指令 —— 于是那一下点击自己把过场跳掉了。

两层修：菜单项和暂停菜单的点击都显式 `set_input_as_handled()`（正解）；
`main.gd` 再加一道 250ms 的时间闸（第二层保险）——
「事件被谁消费」在加新界面时最容易被破坏，而破坏的表现是**过场整个消失**，极难察觉。

### 顺带：机位插值原来插错了东西

查这条时顺手核了一遍插值，发现实现和原型的做法不一样：
原来是直接对 `camera.position` 和 `zoom` 各自线性插。
可投影是 `(点 − 相机) × zoom`，两个都线性插，乘出来并不线性 ——
**两端都对、中间取景会游走**，正是这类动画错最难查的地方。
实测棋盘横移的「最快 / 平均」速度比到 **1.76**（插取景参数只有 **1.26**），
前半程就走完 70% 的横移、后半程在爬；再叠 easeOutCubic 就是开头冲、结尾拖。

改成 `CWView.blend(k)`：插的是**看点 / 锚点 / zoom** 三个取景参数，
且 **zoom 走几何（对数）插值** —— 视觉缩放速度取决于每帧的**倍率**而非差值。

测试 146 → 159 项。新增三组：拆局后信号必须断干净（这条直接对应「卡死」）、
机位插值的两端与匀速性、过场不被启动它的那一下点击跳掉。
真实点击那条路 `--headless` 下测不了（没有显示服务，GUI 输入进不了管线），
所以第三组测的是时间闸那一半。

**细胞渐入**（反馈「显示得太突然」）：淡入 + 从 0.7 倍放大到位，0.32s。
只动 `modulate` 和 `scale` —— `position` 每帧都被 `_sync_cells` 重写，
拿它做补间会被当场覆盖。复活也走同一段（它和刚落子一样是「凭空出现」）。

**暂停菜单**（`pause_menu.gd`，Esc 唤出）。它**不是「面板槽」的一员** ——
主菜单/对局配置/规则速查/设置共用左侧那个槽位，那是**开局前**的语法；
暂停是压在对局画面上的覆盖层，两回事。视觉不另起炉灶：压暗层 + 一块和右侧竖条
同宽（264）的面板，描边配色字号全走 `CWStyle`，菜单项沿用主菜单那套（含「灰掉的项跳过」）。
「规则速查」「设置」保持和主菜单一致的灰掉状态：**做出来两边一起亮**。

暂停期间 `get_tree().paused = true` —— AI 的行动间隔是 SceneTreeTimer，会跟着停，
所以是真暂停而不只是盖一层。菜单自身设成 `PROCESS_MODE_ALWAYS` 才收得到输入。

**顺带修一个潜伏的错**：行动栏原来把「右键 / Esc」一律当成「点最后一个按钮」，
那是照目标选择态写的（最后一个正好是取消）。可在「选择分化方向」那种提问里，
**Esc 会直接替玩家选中最后一个种类**。现在改成显式的 `cancel_index`，
不传就表示这一问不能取消，右键与 Esc 一律不响应。
暂停菜单也靠它判断 Esc 归谁：`CWActionBar.can_cancel()` 为真时 Esc 是「取消选目标」。
两边**各自判断**，不依赖谁先收到事件 —— `_unhandled_input` 的传播顺序不该被写进逻辑里。

**返回主菜单**：镜头原路退回 1.55s（团队定了和进场**对称**），再淡回菜单 0.32s，
两段刻意不重叠。**顺序不能颠倒**：棋盘和菜单共用同一张棋盘，
必须先 `match.teardown()` 把上一局的癌组织和细胞擦干净，否则镜头退到菜单机位时
背景里还留着一片红。菜单那侧 `appear()` 把 `dismiss()` 改过的东西逐样还原，
装饰细胞直接重新生成一批（它们本来就是纯装饰，位置由 DECOR 常量决定，
重建比记账便宜也不会记漏）。

**接上 Main 之后冒出来的一个回归**：主菜单右边凭空多了一条空竖条 ——
Match 的 HUD 那一层 CanvasLayer 一直开着。现在开局前关掉、`start()` 里打开、
`teardown()` 里再关掉。同一个开关也用来控制暂停菜单响不响应 Esc
（主菜单上按 Esc 不该弹「暂停」）。

**踩坑**：`teardown()` 在 `_exit_tree` 里也会走一遍，那时节点已经离开场景树、
`get_tree()` 是 null，`paused = false` 直接报错；棋盘也可能已经被释放。两处都加了守卫。

**截图工具加按键**：`key:ui_cancel@7.8`。暂停菜单只能靠 Esc 唤出，
没有这个就没法自动截到它。

这件事只有真的退回菜单看一眼才发现，而那正是最容易忘记做的一步。

## 2026-08-27 · 修复：骰子掉到棋盘后面（画家算法的 z 收成一处）

团队试玩报的。骰子落地后下半截被**自己脚下那块组织**切掉，看起来像掉进棋盘里。

**根因**：`CWDice.place_at()` 里 `z_index = int(ground.y)`，而传进来的 `ground` 是
`board.tile_center()` —— 它给的是**顶面**中心，比贴图中心高 `TOP_FACE_DY = 4` 像素。
组织块自己的 `z_index` 用的是贴图中心的 y，于是骰子的 z **比自己那格低 4**，被盖住。

**更根本的问题是这个数被抄了三份**：高亮剪影 `t.z_index + 1`、细胞
`int(top.y + TOP_FACE_DY) + 2`、骰子 `int(ground.y)` —— 三处各算各的，错的就是没加回那 4px 的那个。
现在收进 `board.tile_z(格, above)` 一个函数，并把层次定成常量
`Z_MARK = 1 / Z_CELL = 2 / Z_DICE = 3`。约束是 **above 只能取 1..19**：
比自己那格高（不被脚下这块盖住），又低于前一排的 +20（会被前排正确遮住）。
画家算法只有 `board.gd` 一处说了算，别处不许再自己算。

`CWDice.place_at()` 因此改成 `place_at(ground, z)` —— **深度它自己算不出来**，必须由棋盘给。

**旧测试是假的**：`d.place_at(Vector2(300,180))` 然后 `check(d.z_index == 180)` ——
拿 `place_at` 自己算出来的值跟输入比，等于什么都没验。现在改成对着**真棋盘**核：
骰子的 z 必须严格落在「自己那格」和「前一排 +20」之间，并核对三层的先后顺序。

**顺带给截图工具加了连拍**：第四个参数可以写成 `12,13,14,...`，一次运行存多帧。
动画类的验证非它不可 —— 起一次 Godot 要半分钟，一次一帧的话，
光是碰运气撞上那零点几秒的动画就能把时间耗光（找这颗骰子时实测：12 帧一个没撞上）。
最后是靠一个临时脚本把新旧两种 z 的骰子摆在同一块棋盘上，一张图看出来的。

测试 125 → 128 项。

## 2026-08-27 · 待决清单：对局配置面板、行动反馈、开局高亮（团队试玩后记）

团队试玩了第一版可玩构建，**代码未动**，先把撞出来的几个决策点记下来。

### 一、对局配置面板 —— 从来没进过 Godot

它只在当初那份 HTML 过场原型里存在过。今天「开始对局」是**直接接到棋盘**的，
等于把原型里中间那一屏跳过去了。现在开局写死：4 人局、0 号位是人、其余 AI、种子取当前时间。

原型定的过场其实是**三屏两段**，现在只实现了后半段：

```
主菜单 ──0.30s 淡出 + 0.32s 淡入（刻意不重叠）──▶ 对局配置 ──1.55s 相机推进──▶ 棋盘
                                                          ↑ 已实现的只有这一段
```

**它不只是"再加一屏"**：原型里定的是「**左侧是一个面板槽，不是一个菜单**」——
主菜单、对局配置、规则速查、设置全都占同一槽位、共用同一套进出动作。
所以把配置面板设计对，等于顺带定下了后面三个界面的语法。

**要拍板的四点**（第 ③ 条定了，另外三条的面板结构基本就固定了）：

| # | 决策 | 说明 |
|---|---|---|
| ① | 人数给 2/4/6 还是只给 4/6 | 规则只定义 4/6；2 人是电子版为测试扩的（说明 #5） |
| ② | 玩家能不能选阵营 | 行动顺序是**固定表**，所以"选位置"就等于"选阵营"。要么让玩家挑坐第几位，要么随机分 |
| ③ | **要不要热座（多人同机）** | 影响面板结构最大。**引擎侧已经支持**：`human_players` 是数组，几个人共用一个界面跑得通。要的话面板得给每个位置单独选「人 / AI」，而不是一个"我坐哪"的单选 |
| ④ | 种子要不要露给玩家 | 复现同一局对调平衡很有用，对玩家是噪音。可能收进"高级"或只留开发构建 |

建议**不要**放进去：平衡旋钮（`CWTuning`）。那是开发选项，给玩家会让对局不可比。

### 二、行动反馈几乎为零 —— 「点基因表达好像没效果」

**机制是对的**：连点三次，手牌 0→3、能量 6.0→4.5，引擎一步没漏。
问题是六条反馈通道有五条是空的：

| 通道 | 现状 |
|---|---|
| 抽到的卡 | **空白卡**（`cw_cards.gd` 是 14 行的桩，只做 `hand += 1`）——卡池未定 |
| 手牌抽屉 | 没做。定稿里左下角应有 5 张卡露顶边 |
| 右侧竖条 | 只有 `手牌 N` 一行 **10px 灰字** + 能量数字变化 |
| 日志 | 引擎打了详细日志，但 **`log_line` 信号在 Godot 里没有接收方**，屏幕和控制台都看不见 |
| 按钮 | 只做了悬停变色，**没有按下态** |
| 音效 | 无 |

### 三、日志要不要上屏 —— 先量了一局再谈

一局完整对局（4 人，12 回合）：**262 行，36 个玩家回合，平均 7.3 行/回合**，
最长的一回合 14 行，行长中位数 17 字。**绝对量不吓人，但成分很差**：

| 类别 | 占比 | 玩家能否从别处看到 |
|---|---|---|
| 【定殖】【净化】 | 24.8% | 能——那格当场变色 |
| ▶谁的回合 / 结束回合 | 27.4% | 能——竖条里那行亮着 |
| 【有氧/无氧呼吸】 | 8.8% | 能——能量数字在变 |
| 跳过回合 / 无可用固化组织 | 8.4% | 这两条是"什么都没发生" |
| **【突变】结果** | 4.2% | **不能**——d3 掷出哪一档只有日志说得清 |
| **【侵蚀】【增生】** | 6.9% | **不能**——世界回合翻的格子可能离视线很远 |
| 攻击掷骰 / 能量损失 / 死亡 / 世界事件 | 3.1% | 勉强 |

**真正只能靠日志知道的只占 ~15%，摊下来约 1 行 / 玩家回合。**
所以风险不是刷屏，是**噪音把信号盖住**——重要的那 1 行会被埋在 6 行废话里，
全量日志带反而会让人练出"不看日志"的习惯。

**这里其实是两个需求，混着谈就问不出答案：**

- **A 玩家要知道刚才发生了什么** → 要的是筛选过的提示。而且有硬约束：
  **960×540 里没地方放日志带** —— 棋盘 673 + 竖条 264 已占满；竖条底下 4 人局有空、
  **6 人局只剩 10px**；底部左边留给手牌抽屉。这个约束本身就在把答案往"临时提示"推。
  （压在棋盘上会挡住最下面一排格子，这个坑做落子提示条时已经撞过一次。）
- **B 我们自测要能诊断** → 要的是全量不筛选，但**根本不必上屏**，打到控制台即可，
  零设计成本零画面成本。「基因表达好像没效果」这类问题，有控制台日志就能自查。

**A 的三个候选**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **甲（推荐）** | 只提示那 15%，做成**贴着相关格子弹出的短提示**，2 秒淡掉 | 不占固定版面，最贴合 960×540 的现实；要逐条判定"哪些算重要" |
| 乙 | 日志带 + 分级，默认只显示重要的、可展开 | 要改 `log_msg` 签名；仍然要找地方放条带 |
| 丙 | 全量收进抽屉，平时只露最新一行 | 最省事，但"最新一行"有 85% 概率是废话 |

团队 2026-08-27 决定：**暂不实现，先记下来。**

### 四、其它两条

  但视觉偏重。候选：只描边不填色 / 降低 alpha / 干脆不高亮。

## 2026-08-27 · 菜单接上对局：开场三拍打通

`scripts/ui/main.gd`。现在跑工程：主菜单 → 点「开始对局」→ 相机推进 →
癌组织绽开 → 落子 → 选技能 → 打完一局。**从头到尾不切场景。**

**场景结构改了**：`Match.tscn` 不再自带棋盘和相机，改用同级的
（`board_path = ../Board`）。因为过场是同一个镜头往前推、不切场景，
菜单和对局必须共用一棵树里的同一张棋盘。代价是 Match.tscn 不能单独跑了，
入口一律 `Main.tscn` —— 截图工具的场景参数也跟着改。

**开场三拍**（时长常量集中在 main.gd，别散进各个 Tween）：
① 相机拉远铺满棋盘 1.55s，装饰细胞同时沿离心方向漂散淡出；
② 初始癌组织从正中绽开 0.75s，中央先翻、外圈绕一圈扫过去，每格翻面给一下白闪；
③ 停下来等玩家落子。

**两段动画是前后相接，不共用时间轴** —— 这是开发日志早就记下的坑：
原型里第一版挂在同一个进度值上，相机走完那一帧的进度 1 被当成「绽开也走完了」，
7 格一次全出、绽开整个被跳过。现在相机那条 `finished` 之后才启动绽开。

**绽开的实现是「渲染层遮罩」，不动引擎。** `start()` 会一路跑到第一次询问才挂起，
那时初始癌组织已经躺在 `game.tiles` 里、而本帧的 `_process` 还没跑 ——
所以在这中间把它们记进 `_bloom` 还来得及。揭示顺序**不写死「中央 + 第一环」**，
而是按「离中心几格、同环按角度」排：地图生成还在讨论，初始癌区形状随时会变。

**踩坑一：闸门写早了一行。** `bridge.opening = true` 写在 `start()` 之前，
而桥是 `start()` 里才 new 出来的 —— 那时还是 null，`if bridge != null` 静默跳过，
于是绽开还没演完落子提示就弹了出来。改成先置 `_opening`，由 `start()` 带给桥。

**踩坑二：菜单淡出后仍然吃点击。** Control 的 `modulate` 归零只是**看不见**，
照样挡鼠标；而「开始对局」那一行正压在棋盘上方，于是过场结束后点那块棋盘毫无反应，
还查不出原因（只有端到端跑一遍才会撞见）。现在淡出一开始就把菜单项的
`mouse_filter` 摘成 IGNORE，动画结束再关掉 CanvasLayer ——
**CanvasLayer 不跟随父 Node2D 的可见性**，得单独关。

测试 118 → 125 项。开场那组用状态断言钉死「绽开不是一次全出」和
「演完才交还控制权」：这两件事肉眼只看得出「有点怪」，说不清哪儿怪。

**还没做的对局配置面板**：现在开局是写死的 4 人局、0 号位是人。
人数/阵营/种子怎么选属于新的界面设计，按老规矩得先出方案图给团队看，再动手。

`CWUIBridge._ask_human()` 实装。现在跑 Match 场景，0 号位是人：开局落子、选技能、

**「迁移」是两段式，照定稿来。** 引擎那边每个相邻格是一个独立选项，
而设计稿的行动栏里「迁移」是**一个**按钮（费用显示成「0.5 / 1.0」），
点了它才高亮可达格、再点格子确认，右键或 Esc 退回按钮栏。
所以桥要把 n 个 move 选项合成一个按钮，选完格子再还原成对应的那个下标——
这段下标映射错了不会报错，只会走到别的格子去，因此测试逐步核对返回值。
费用文案是把各选项里**实际的** cost 收齐去重再拼的，不另算一遍。

**取消不另设信号。** 行动栏只有一个出口 `chosen(下标)`，取消就是最后那个按钮，
右键和 Esc 只是它的快捷方式。这样调用方一个 await 收全部结果。
而「同时等『点了格子』和『点了按钮』」这件事 GDScript 的 await 做不到
（一次只能等一个信号），所以两路都汇进一个一次性的 `Answer` 对象。

**踩坑一：模拟输入点不动棋盘。** `_unhandled_input` 里原本用
`get_local_mouse_position()`，它读的是**真实光标**，截图工具/自动化测试
喂进来的事件位置它根本看不见。改成 `make_input_local(event).position`。
这不只是测试问题——遥控输入、触摸也会踩。

**踩坑二：描边直接贴着字。** `CWStyle.box()` 建 StyleBoxFlat 时没设
`content_margin`，默认 0，于是设计稿的 `padding:6px 8px` 丢了，
边框压在glyph上。顺带把按钮高度统一到 52（=2+6+22+2+12+6+2），
免得少一行费用的按钮矮一截、整条参差不齐。

**待拍板：开局落子时 120 格全高亮，整块棋盘变青。** 规则上没错（除 7 格癌区外
都能落），信息量也不是零——「红的不能选」一眼就看得出来。但视觉上确实重。
要不要换成「只描边不填色」或者干脆不高亮，等团队定。

**行动栏里的「结束回合」是临时的。** 定稿把它钉在右侧竖条底部，
竖条还没做，先摆在按钮栏最后一个，下一步搬走。

测试 94 → 109 项。新增两组：用合成事件把「点技能→点格子 / 取消」整条路走一遍
（重点核对下标映射）；跑一整局把实际出现过的 act 收齐，逐个核对行动栏有没有漏登记
技能名——新加主动技能却忘了登记，按钮会显示成 act 的英文名。
截图工具加了「点击脚本」参数（`x,y@秒数`）：交互态不点几下根本到不了，
而这些恰恰是最需要和设计稿比对的画面。

## 2026-08-27 · 棋盘点选：hex_at() 与格子高亮层

对局界面开工的第一块。`board.gd` 加了两样东西，都是后面所有交互的地基。

**`hex_at(像素) -> 轴坐标`，`tile_center()` 的逆。** 没有去解压扁投影的反函数——
本文件的布局横距 36、纵距 20、隔行错半格，相邻格的偏移只有 `(±36,0)` 和 `(±18,±20)`
两类；把纵向按 `36·√3/2 ÷ 20 ≈ 1.559` 拉回去之后这六个偏移长度全是 36，
也就是说**这是一张被压扁的标准正六边形网格**。于是在拉正的空间里取「最近的顶面中心」
就等价于真正的六边形命中判定（正六边形网格的最近点划分就是它自己），
一个 127 次的循环解决，还顺带得到「超出外接圆 36/√3 即棋盘外」这条边界判据。
锚点用 `tile_center()`（顶面中心）而不是贴图中心：前排会盖住本格下半截，
实际可见区域正好是以顶面中心为心的那 26px。

**格子高亮 = 整格染色，不是描边。** 参数是从设计稿 `board_pick.png` 反解出来的——
把它和 `board.png` 逐像素相减，六组色对全部满足 `lerp(原色, #30D1FA, 0.43)`。
而「叠一层 alpha=0.43 的纯色」在数学上就是这个 lerp，所以做法是给格子叠一张
同贴图的纯色剪影（`silhouette.gdshader`，四行，输出白色、颜色交给 modulate，
一份材质全体共用）。剪影的 `z_index` 只比自己那格高 1、低于前一排的 +20，
于是前排会正确盖住高亮下半截——高亮贴在棋盘上，而不是浮在整张棋盘上面。

**踩坑：测试脚手架会「假装通过」。** `board.gd` 一处类型推断写错
（`distance_x/y` 是无类型 `var`，`:=` 推不出来），Godot 只打印 Parse Error
就照样返回一个光秃秃的 Node2D，于是两个测试整个没跑、一个 `check` 都没执行，
而 `fails` 仍是 0 —— 报「全部测试通过（61 项）」。**检查数从 75 掉到 61 是唯一的线索。**
现在统一走 `make_board()`，里面显式确认脚本挂上了。
判据只能用 `has_method()`：解析失败时 Godot 会挂一个 `MissingResource` 占位，
`get_script() != null` 照样成立，问它等于没问（这一条是当场试出来的——
第一版守卫就是这么写的，故意打断脚本后它依然报通过）。
已双向验证：打断脚本 → 退出码 1；还原 → 退出码 0。

测试 75 → 85 项：127 格中心逐格点回自己、格内六向抖动、相邻格中点只归这两格、
棋盘外 5 个点返回 NO_TILE、高亮层的整体替换与清空语义。

## 2026-08-27 · 主菜单进 Godot（定稿原型 → 可运行场景）

把团队定稿的「活体棋盘」主菜单实装成 `scenes/MainMenu.tscn` + `scripts/ui/main_menu.gd`。
跑工程就是它。测试 67 → 75 项，全绿。

**设计分辨率定为 960×540**。理由有两条，缺一条都会选别的数：
① 它就是界面原型的画布尺寸，于是原型里的 `1cqw` 正好是 `9.6px`，
所有定稿坐标能直接乘过来，机位参数（zoom 3.2、锚点 595,227）原样搬；
② 1080p 全屏恰好整数 2 倍，点阵字和像素贴图都能整数放大不糊。
拉伸模式 `canvas_items` + `keep`。**高分屏非整数倍时怎么办还没定**——
1366×768 这种会缩到 1.42 倍，属于「显示设置」的范畴，等设置界面一起做。

**菜单不是独立场景，是挂在 Main 下面的一层。** 因为「开始对局」的过场是
同一个镜头从菜单机位往前推、不切场景（团队定的三拍开场），
菜单和棋盘必须活在同一棵树里。相机也只有一台，菜单机位就是对局那台相机。

**背景就是真棋盘**，直接复用 `Board.tscn`，装饰细胞的位置全走 `board.tile_center()`
（架构约定 #10）。装饰细胞脚底落在格子顶面中心再往下 6px，和原型一致。

**和设计稿的比对结果**（`tests/screenshot.gd` 渲染 960×540，和 Chrome 重渲的原型 1:1 比）：
- 组织块 / 压暗渐变的取色 **逐点一致**（如 `(46,74,65)`、`(26,42,50)`、`(52,103,76)`）；
- 六行文字（副标题、Logo、四个菜单项）的墨迹行段 **顶端全部对齐到 0px 误差**；
- 棋盘部分剩余差异是两个渲染器在 3.2 倍非整数缩放下的取整差，2 倍放大下看不出来。

**对齐踩的坑：CSS 的 `top` 和 Godot 的 `offset_top` 不是一回事。**
CSS 的 `top` 是行盒顶，浏览器按自己那套行高算法把字往下推；
Godot 的 `offset_top` 是控件顶，基线固定在 `offset_top + ascent`。
实测常数差：中文点阵 +2px，Logo 用的 Silkscreen +13px（两款字体的行高算法不同）。
**别去推公式，直接量**——渲一张图，量墨迹行段，把差值加回去。

**悬停发光试了三条路，最后用「多层描边」。**
- ❌ 引擎辉光后期（`hdr_2d` + WorldEnvironment Glow）：开了 HDR 之后
  **整张画布的颜色全变了**（全部 518400 个像素都动了，最大差 74），
  而棋盘配色本来是和设计稿逐像素一致的——代价太大，而且辉光还没触发。回退。
- ❌ 三层描边：描边是硬膨胀，最外那圈会露出一条硬边。中文字几乎占满字身框，
  膨胀出来就是个矩形，**读起来正好是团队否掉的「垫块」**。
- ✅ 四层描边（6/10/16/24，alpha 0.28/0.08/0.035/0.012）：
  每级 alpha 落差都很小，台阶看不出来。实测光晕衰减对上了设计稿的 6px / 8px 两档。
  全菜单共用一套、跟着悬停项走——同时只可能有一项悬停。
  尺寸与 alpha 都在场景里，调手感不用碰代码。
菱形选中标记的光晕换成了**径向渐变贴图**——小块形状用真渐变比堆方块干净。

**「灰掉」的含义反过来了。** 原型里灰的是「退出」（网页里退不出去）；
实装是**退出能用，中间三项（继续对局/规则速查/设置）因为还没做才灰**。
三项做出来就把 `ITEMS` 里的 `enabled` 翻回 true，一项一个字。
另外**鼠标划过会顺手把选中也带过去**（原型是静态图，这两件事没区分过），
这样菱形在键盘和鼠标下的行为是一致的。

**新增两条硬约定**（已进架构说明书 #12 #13）：设计分辨率不许改；
点阵字号只能取字体网格的整数倍（中文 10 的倍数、Silkscreen 8 的倍数），
字间距和位移取 2 的倍数。`t_main_menu()` 会扫描场景里所有 Label 盯住后一条。

**新增工具 `tests/screenshot.gd`**：把场景渲染几帧存 PNG，第三个参数可以先把鼠标
挪过去再截（悬停态也要跟设计稿对）。**不能加 `--headless`**，需要真渲染——
所以跑起来会闪一下窗口，那是正常的，不是崩了。

**一条没照办的约定，留给团队定。** 之前提过「颜色只写在 Theme 资源 `cell_war.tres` 里，

## 2026-08-27 · 菜单项字间距 +2px；界面稿构建加控制字符断言

**字间距 0 → 2px**（稿子里写作 `.194cqw`，画框设计宽 1032px 时等于 2px）。
团队反馈菜单项挤在一起。这里**只有 2px 这一个「一点点」可选**：
字体是 10×10 点阵、按 2 倍放到 20px 显示，所以屏幕上 **2px 恰好等于字体自己的 1 个像素**；
取 1px 或 3px 会让后面每个字的原点落在半像素上，点阵字立刻被抗锯齿糊出灰边。

实测 0 / 2 / 4 / 6 四档并排：4px 起就散成一个个孤字，6px 已经不成词。
纯色底上数亮度档数，0px 与 2px 同为 **4 档**——加字间距没有引入任何糊边。

**踩坑：`re.sub` 替换串里的 `\2` 被 Python 当八进制转义。**
本意是反向引用第 2 组，实际写进文件的是 `chr(2)`，把副标题里的「Immune / 免疫细胞」
静默替换成了控制字符，浏览器渲染成空——**这个错误版本已经发出去过一轮**才被发现。
两条防线：① 替换串一律用 `\g<2>` 而不是 `\2`；② 界面稿构建脚本写盘前扫描
`\x00-\x1f` 并断言。这类错误没有任何报错，只能靠断言拦。

**同一个坑当场又踩了一次**：写上面这段日志时，命令串里的 `\\` 被工具层折成了 `\`，Python 于是又拿到单反斜杠的 `\2` / `\x00`，**把这条日志本身写成了控制字符**。结论升级为：脚本里凡是要写反斜杠，直接用 `chr(92)` 拼，别指望多层转义（JSON → shell → Python）能数对。

  笔画粗细还不均匀，中文糊成一团。24px（×1.5）是 26 个，比 20 好但仍不干净。
- **必须关掉字体平滑**（CSS `-webkit-font-smoothing:none`；Godot 里关抗锯齿 + 最近邻过滤）。
- **Godot 的 UI 按网格排版、视口只做整数倍缩放**，否则点阵会被糊掉。

拉丁 Logo（`CELL WAR`）仍用 Silkscreen，正文拉丁跟随 Fusion —— 规则是
**Logo 用 Silkscreen，其余一律正文字体**，不做随机混用。

## 2026-08-27 · 主菜单定为「活体棋盘」，开局过场定稿（尚未进 Godot）

### 重绘素材到位，风格问题直接消失

`精灵图v4手修.zip` 里是五个免疫细胞：B 细胞 / T 细胞 / 巨噬 / 普通免疫 / 树突，
**24px（标准细胞）与 32px（巨噬、树突）的限色像素图，各 4~9 色**，
五个精灵唯一共有的颜色是 `#1A1A2E` —— 刻意设的统一暗锚。

这批素材**推翻了上一轮界面方向稿的全部前提**。那三个方向（暗场荧光 / 像素培养皿 / 显微镜观察窗）
本质上都在回答同一个问题：棋盘的等距风和细胞的粗像素风谁迁就谁。
新细胞是限色像素图，棋盘组织块（32×34）也是限色像素图，**同一种画法、同一个密度，问题不存在了**。
所以第二轮不再出「风格方向」，改为出**构图**三稿，团队选了「活体棋盘」。

配色关系是有意的：细胞高饱和（青/蓝/紫/薄荷），棋盘低饱和（墨绿/青灰/暗红），
亮细胞压在闷底色上一眼可辨。**注意两个暗锚还不一致**：细胞 `#1A1A2E`（偏靛）
vs 组织块 `#0C1417`（偏青黑），细胞站到棋盘上时描边是两种黑，待统一。

### 开局过场

主菜单不是独立画面，而是**真棋盘的一个近景裁切**加左侧面板。流程：

```
主菜单 ──淡出/浮现──> 对局配置 ──面板滑出 + 相机拉远──> 棋盘（对局中）
   ^                                                        |
   └────────────── 反向原样倒放 ────────────────────────────┘
```

| 动作 | 时长 | 缓动 |
|---|---|---|
| 主菜单 → 对局配置 | 0.30s 淡出 + 0.32s 淡入（**不重叠**） | 线性 |
| 对局配置 → 棋盘 | 1.55s | easeOutCubic |
| 棋盘 → 主菜单 | 1.55s | easeOutCubic 反向 |

两段淡入淡出**刻意不重叠** —— 重叠会让两组字同时半透明地压在一起，糊成一片。

进场时长最初给的 0.62s，团队试过原型后改为 1.55s（原慢放档的速度）。
回程本来按 0.75s 做的（理由：进场是揭幕值得给分量，返回是退出应该干脆），
团队定了**对称**，改回 1.55s。

**相机动，棋盘不动。** 落 Godot 时移动 `Camera2D` 的 `position` 与 `zoom`，
不要去动棋盘节点自己的坐标 —— 那会让 `z_index = y` 的前后遮挡在过场中途错乱。
两个并行 Tween：相机一个，左侧面板容器一个。

**左侧是一个「面板槽」，不是一个菜单。** 主菜单、对局配置、以后的规则速查和设置
都占同一槽位、用同一套进出动作。过场因此是这套界面的基本语法，不只是开场特效。

**必须做「快速点击立即到位」**：过场进行中再点一次直接跳到终态。别等做完再补。

### 按钮悬停：字亮起来，不是垫块

鼠标悬停（以及键盘 `:focus-visible`）时，菜单项**本身转纯白 `#FFFFFF`，
镀两层 50% 白的光晕，同时上浮 0.3cqw**，0.09 秒到位。

第一版做成了「字底下垫一块 50% 白的板」，团队否掉了 ——
**垫块是「选中某一行」的语言，发光才是「这个字亮了」**。
而且 50% 白压在暗底上出来是中灰（实测 `#8A8F96`），看着更像置灰失效。

发光这个做法和 Logo 是同一套：`CELL WAR` 本来就带一层青色辉光，
沿用它，悬停效果就不会显得是从别处搬来的。

「进入棋盘」那种实心按钮没法靠字发光，改成整块转白 + 外发光。
灰掉的不可点项（如「退出」）不吃悬停。

### 落 Godot 时的注意

上面这些时长要**抽成常量集中放一处**（参照 `CWTuning` 的做法），不要散在各个 Tween 调用里 ——
手感是要反复微调的，散开了改一次要翻好几个文件。

### 开场三拍：第三拍必须交还控制权

「开局铺设要不要接着演」这个问题的答案在代码里 —— `cw_setup.gd` 的 `run()` 里
有一句 **`await _place_cells()`**：落子走 `game.ask(setup_place)`，**是玩家决策不是自动流程**。
所以这一段一半能演、一半不能：

| 步骤 | 性质 | 处理 |
|---|---|---|
| 铺初始癌组织（中央格 + 第一环共 7 格） | 自动 | **演**，0.75s。中央先翻、六格绕一圈扫过去，每格翻面给一下白闪 |
| 抽癌细胞种类 | 自动 | 可演可不演，原型未做 |
| **落子** | **玩家决策** | **不能演**，停下来交还控制权 |
| 原发灶固化 | 自动 | **演**，它是落子的结果，动画正好当确认反馈。原型未做 |

于是开场是三拍：相机拉远铺满棋盘（1.55s）→ 癌组织从正中绽开（0.75s）→ 等玩家落子。

**实现上有个坑，落 Godot 时会再遇到一次**：这两段是**前后相接的两个计时动画**，
原型里第一版把它们挂在同一个进度值上 —— 相机走完那一帧进度 = 1，切进绽开阶段后
这个 1 被当成「绽开也走完了」，一路跳到等待落子，**7 格癌组织一次全出、绽开整个被跳过**。
表现就是「地图停稳的瞬间癌组织突然显示」。
教训是**阶段切换要在渲染前一次做完并把进度归零**；Godot 里用 Tween 的话，
就是相机那条 `finished` 之后再启动绽开那条，别把两段挂在同一条时间轴上。

### 装饰细胞：漂散出去，不留下

菜单里闲逛的细胞**不能留下当开局棋子**，三条都对不上：稿子里是 5 个**免疫**细胞，
真实开局**双方都有**；数量跟人数走（2/4/6 人局不同）；位置由玩家落子决定。

但也不做生硬淡出 —— 相机拉远的同时它们**沿着离棋盘中心的方向往外漂散**再淡掉，
读起来像「样本正在让位」。实现上和淡出一样便宜，只是加个位移。

### 发现：对局机位没给 HUD 留位

做落子提示条时撞出来的：**对局机位下棋盘占了画面 82% 宽 × 86% 高**，四边不到一成边距，
提示条只能压在棋盘上、挡住最下面一排格子。

也就是说**现在这个机位是「没有 HUD」的取景**。真实对局还要有玩家列表、能量、行动按钮，
**HUD 布局定了之后 `CAM_GAME` 的 zoom 和中心点都得重调**。
原型里刻意让提示条压在棋盘上，就是为了让这件事现在就看得见。

### 还没定

- **中文字体**：稿子里 `CELL WAR` 用的是点阵字，中文还是普通无衬线（免费中文点阵字体不在 Google Fonts 上）。
  团队已在找像素中文字体。**在这之前所有稿子的中文部分都不是最终效果**，像素风配非像素中文会明显别扭。
- **癌方美术**：这批五个全是免疫细胞，构图目前一整片冷色；癌细胞到位后冷暖平衡要重配。
- **装饰细胞的去留**：现在过场时淡出。另一种是留下直接变成开局棋子，但数量跟人数走，配置确认前定不下来。
- **开局铺设要不要接着演**：初始癌组织从中央铺 7 格、双方细胞落位，可顺着过场演下去，也可直接给终态。

## 2026-08-27 · 掷骰表现定为方案 D（着色器解析求交），引擎接上演出钩子

先把随机的表现形式做成**可实际播的四版对照**交给团队选，而不是拿嘴描述：
A 真 3D（SubViewport + BoxMesh）／ B 预烘焙精灵序列／ C 等距伪 3D／ D 片段着色器解析求交。
四版放在同一块真实棋盘上、同一个按钮同步掷出同一个点数，落点、阴影、涟漪、时长全部一致，
差别只剩骰子本身怎么渲染。**团队一致选 D。**

做对照的过程里推翻了我自己的一条论据：原本主张「平滑渲染的骰子会和像素棋盘打架」，
所以不推 A。四版按 1:1 原尺寸并排看下来，A 和 D 都没有明显违和感 —— **这条论断不成立**。
去掉它之后 D 就明显占优：和 A 同样的写实观感，但不需要 SubViewport、不需要网格、
**不需要任何贴图**（点数和配色全在着色器里程序化生成），因此完全不吃细胞素材重绘的进度。

**不用 Ray Marching。** 立方体有闭式解 —— slab 法求光线与轴对齐盒的交点，十来行、O(1)，
比步进更快，而且平面上不会留下步进条纹。只有将来要做**圆角骰**才需要改成 marching `sdRoundBox`。

### 引擎钩子：新增 `roll_shown()`，不动原来的 `roll_d6/roll_d3`

原本打算直接给 `roll_d6/roll_d3` 加 `await`，但 GDScript 的 `await` 会沿调用链往上传染，
那样全部既有调用点都要改，52 项测试全在风险里。改成**并列增加**一个带演出的版本：

```
roll_d6() / roll_d3()          静默，一次 randi_range，世界自动结算用
roll_shown(sides, reason, pid) 带演出，同样一次 randi_range，await 桥把动画播完
```

两者消耗的 rng 完全相同，可以随时互换而不影响同种子可复现 ——
**「某个随机要不要演动画」因此是纯表现层决定，不碰规则**，也让决策 ④ 变成单行可逆。
改动只落在三个玩家自己掷的点：攻击（d6）、突变（d3）、抗体（d3）。

`show_roll()` **广播给所有桥并按对象去重**，不是只发给掷骰那个玩家 ——
AI 掷的骰，旁观的人类也得看见；热座共用一个 UI 桥时去重保证只演一次。

【E-侵蚀】**刻意留静默**（决策 ④）：它是世界自动结算不是玩家行为，一局要掷 7 次左右，
每次都演会拖节奏。要改回来只需把那一行换成 `await game.roll_shown(3, "侵蚀")`，
`cw_world.gd` 里已写明改法与连带影响。

### 测试（52 → 63 项）

`t_roll_hook()` 的核心是**交叉核对**：把钩子收到的点数和日志里引擎实际结算用的点数逐次比对。
「演出落在哪一面 ≠ 规则算出来的结果」是掷骰动画最经典也最难查的 bug，这道检查专防它。

**中途发现第一版检查是空转的**：原本比较「装演出的桥」与「不装的桥」两局的 state_hash，
但两局走的是同一条 `roll_shown`，注入「演出时偷偷多掷一次 rng」的变异后两边一起偏移、
哈希依然相等，测试照过。换成交叉核对后再注入「送给表现层的点数与结算脱钩」，立刻 FAIL。

`t_dice()` 用矩阵直接验 `REST` 静止姿态表：把该面法线按姿态转一下必须指向正上方。
这张表错了骰子会停在与结算不符的面上，而这种错只有肉眼能发现。
面法线的约定（+Z=1 −Z=6 +X=2 −X=5 +Y=3 −Y=4）在 GDScript 和 GLSL 里各存了一份、
跨语言没法共享常量，这组检查就是那道防线。

### 踩坑

着色器里的常量**不能叫 `LIGHT`** —— 那是 canvas_item 着色器的内建量，重名直接编译失败
（和「不能给 CWGame 加 `log()` 方法」是同一类坑）。已改名 `LIGHT_DIR`。

另外纠正队友的一个说法：**Godot 用的不是通用 GLSL**，是自己的 Godot Shading Language，
入口 `fragment()`、内建量 `UV`/`TIME`/`COLOR`，没有 Shadertoy 的 `iTime`/`fragCoord`。
社区着色器**粘不进去**，要移植；而且现成的骰子着色器基本都是按时间自己翻滚、翻到哪面算哪面，
**恰恰缺了「落在指定点数上」这个我们唯一必须有的部分**。

### 还没做

`CWDice` 节点和着色器都在，但**还没接到实际对局**：工程里目前没有任何面向人类玩家的 UI，
也就没有 UI 桥去重写 `show_roll()`。等菜单/HUD 那条线起来之后，
UI 桥的 `show_roll()` 里 `await dice.play(value, sides, fast)` 即可，引擎侧不用再动。

### 同日追加的两个决定

**骰子落在棋盘格上**（不是 UI 浮层）：把「谁在打谁」和「结果」在空间上绑死，
不用在浮层和棋盘之间来回找。为此 `show_roll()` 补了参数 `at: Vector2i` ——
掷骰指向哪一格只有引擎知道，表现层猜不出来（攻击给目标格，突变/抗体给发动者所在格）。
骰子按**落地点**的 y 参与深度排序，和组织块同一套规则，所以前排组织块会正确盖住骰子底部，
腾空时也不会忽前忽后地跳。

**骰子不做阵营色。** 原本提过「免疫掷青骰、癌方掷红骰」，但骰面颜色已经在表示结果档位
（1-2 红 / 3-5 青 / 6 金），再叠一层阵营色就成了同一个物体上两套互相矛盾的语义 ——
癌方掷出的红骰，红色到底是「癌方」还是「失败」？**这是我提议时的疏漏**，团队选择干脆不做：
轮到谁交给 HUD 和骰子旁边那行字（"攻击"/"突变"）。`pid` 仍然传到桥，可用于显示「谁掷的」，
但不用来染色。副作用是**阵营色（界-6）不再卡骰子**，可以晚点再定。

轴坐标 → 格子像素位置的换算加在 `board.gd` 的 `tile_center()`，全工程只此一处（约定 #10）。
组织块 `Sprite2D` 是 `centered=true`，`position` 落在贴图中心；而 34px 高的贴图里顶面只占上面 26px，
所以顶面中心比贴图中心高 4px —— 不减这 4px 骰子会陷进格子里。

骰子的接地点由着色器的相机参数反推（`contact_y()`），不是拍脑袋的偏移量；
`t_dice()` 会盯住这个关系，改了着色器相机而忘了改这里，测试会抓到。

**骰-2 也定了：骰面就用点数＋色区**（1-2 红 / 3-5 青 / 6 金），维持当前实现。
当初提「改用符号 ✗ / ✓ / ✓✓」的依据，是做对照时实测出「32px 的像素密度放不下 6 个能看清的点数」——
但那是**像素路线**（B / C）的限制。D 是着色器全分辨率渲染，点数画得下，所以这条依据对 D 不成立。
保留点数还能对上规则原文的「1/6 大成功」表述，色区负责让档位一眼可读。

至此**骰子四项全部定完**：落棋盘格上 / 点数＋色区 / d3 借同一颗 d6 演（1→2、2→4、3→6）/ 侵蚀不演。
四项都已落到代码里，改任何一项仍然是单行的事。

## 2026-08-27 · 骨髓改版（方案 A）+ 测出「中心是免疫的地盘」

**改动**：拿掉中央格的骨髓（消解规则冲突 #34），在外缘边中格补 3 个，骨髓共 6 个。

**新增 `tools/render_map.py`**：示意图改成从 `cw_data.gd` 解析坐标生成，不接受手填。

于是量了两个指标（子类化 `CWActions.enter_tile` 埋点，不改引擎代码）。

一局中「至少被己方细胞踩过一次」的格子比例，按距中心的圈层（4 人局 / 6 人局，各 100 局）：

| 圈半径 | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|---|
| 癌方（4人）| 24% | 37% | 30% | 36% | 35% | **60%** | 30% |
| 免疫（4人）| **100%** | **93%** | 54% | 36% | 29% | 34% | 15% |
| 癌方（6人）| 72% | 54% | 54% | 52% | 53% | **80%** | 53% |
| 免疫（6人）| 92% | **98%** | 78% | 64% | 57% | 61% | 41% |

**中心是免疫的地盘，不是癌方的。** 4 人局中央格免疫踩到率 100%、癌方只有 24%。
机制很清楚：初始癌区就在中心，免疫开局落在旁边一路往里净化；而癌细胞只有 3.0 能量、
挨一次攻击就掉半条命，理性选择是往外跑。**癌方真正的活动区是半径 5（踩到率 60%/80%，全场最高）。**

而半径 6 是全场最冷的一圈（4 人局癌 30% / 免 15%），外圈骨髓放在那里确实浪费——
这一半的直觉是对的，只是原因不同。

## 2026-08-27 · 棋盘扩到 127 格 + 新地图布点 + 重新标定平衡

棋盘从半径 4（61 格）扩到**半径 6（127 格）**，特殊组织按团队给的地图图片重新布点。
读图结果、可视化与由此引出的 4 个规则问题见 [规则电子化说明 #33~#37](规则电子化说明.md)；
完整数据见 [平衡测试报告](平衡测试报告.md) 第一部分。

**布局**：半径 4 那一环的 6 个角上，代谢核心（3）与骨髓（3）**交替**排布；
外加中央格 1 个骨髓、左右两个最远角 (±6,0) 一对血管。胜负门槛同步换算为 85（⌈2/3×127⌉）与 64（⌈1/2×127⌉）。

**纠正一个很自然但错误的猜测**：127 格下「规则原文」的癌胜率从 0% 变成 33%，看着像是棋盘变大救了癌方。
把原发灶单独关掉再测——**0%，3 回合暴毙，与棋盘大小无关**。
癌方的开局劣势是「活不过 3 回合」的**细胞存活**问题，而棋盘只影响**地盘**，两者不相干。
（61 格时代那个"规则原文 0%"是原发灶加入**之前**测的，从未与之同版本对比过，这轮补上了。）

**61 格调好的数值不能直接搬**：免疫供能挂钩健康组织格数，61 格开局是每细胞 2.7（在低保~封顶区间中段），
127 格变成 6.0——**一开局就顶死在封顶上**，反馈全程失效，癌胜率掉到 10%。
新增旋钮 `aerobic_healthy_div` 把每格供能降到 0.05（原来的最小步进 0.1/格在 127 格上太粗，一档就翻倍）。

**重标结果**：癌方封顶 2.5→**3.5**、免疫低保 2.0→**1.9**，其余不动 → 4 人局 ~51%、6 人局 ~48%、平均 12~13 回合。
免疫低保这条特别干净：它**只影响 6 人局**（6 人局免疫供能 120×0.1÷2÷3 = 2.0 正好撞上低保线 2.0，
从第 1 回合就被钉死、收入再不随地盘萎缩；4 人局开局 3.0，很晚才触底）。

**回答 Kevin「取消能量上下限会怎样」**：对局退化成「谁先滚起雪球谁赢」，且**不同人数滚向相反极端**——
去封顶后 4 人 87%／6 人 97%、对局塌到 7~9 回合（癌方收入四回合内涨到免疫的 20 倍）；
而 2 人局反而掉到 6%、第 2 回合结束，因为封顶同时也压着免疫（独苗免疫细胞独享 6.0/回合）。
**上下限不是偏袒某一方的补丁，是同时压住两侧极端的护栏。**

其他实测否掉的直觉：初始癌区**不该**随棋盘放大（放到 15 格 → 4 人局 74%）；对局长度**没有**变长（仍 12~13 回合）；
回合上限**仍是 20**（12~14% 的对局由上限判定，胜率对上限不敏感）。

## 2026-08-26 · 团队定案落地 + 纠正「对称反馈」的错误结论

三条团队定案已实现（[平衡测试报告](平衡测试报告.md) §五、§六）：

- **胜负条件**：回合上限 30→20，终局门槛 1/3（21 格）→1/2（31 格）。实测 20 回合下有 17% 的对局由上限判定（30 回合时只有 2%，是死规则），且胜率对上限值不敏感（30/20/15/12 分别为 51%/51%/50%/48%），说明这个选择安全。
- **原发灶**：每个癌症玩家的出生格开局即为固化癌组织，破解「复活需固化 → 固化需停留 → 停留就被打死」的死循环。注意复活会消耗掉固化组织，所以它是**一次性保险**而非永久免死金牌，免疫仍能靠全灭获胜。
- **免疫罚停复活**：免疫细胞死亡后罚停 1 回合，在**随机**健康组织复活（随机是为避免自选复活点变成免费传送），获得 2.0 能量。造成免疫死亡的手段团队仍在讨论——反弹反击可被免疫主动规避（Kevin 已确认），所以这套机制目前基本不触发。

**纠正上一条日志的结论**：上一轮推荐的「免疫收入挂钩健康组织」方向对，但漏看了副作用——双方收入都挂钩地盘时，领先方收入涨、落后方收入跌，两个正反馈叠加成雪球。加入原发灶后癌胜率直接从 50% 冲到 98%，对局第 5~6 回合就结束。

解药是 Kevin 提出的**低保**加上配套的**封顶**。关键换算：转化一格地盘癌方【定殖】只要 0.5、免疫【净化】要 1.0，所以**封顶必须不对称**（免疫约为癌方的 1.4~2 倍才是等吞吐量），对称封顶等于没封（实测仍 95%）。最终标定：癌方 1.2~2.5、免疫 2.0~3.5 → 4 人局 51%、6 人局 40%，平均 13 / 8 回合。

## 2026-08-26 · 平衡测试：规则原文癌症方 0% 胜率，给出推荐方案

完整数据见 [平衡测试报告](平衡测试报告.md)。

- **诊断**：AI 互搏 60 局，癌症方一局未胜，平均第 3.2 个世界回合就结束。五个原因叠加：①免疫收入是癌方的 4 倍且不挂钩地盘；②杀死癌细胞平均只需 3.6 能量，低于免疫一回合的收入；③【复活】需要固化癌组织，而固化需要停留 2 回合、停留就会被打死——机制无法引导；④免疫细胞无法被杀死（癌方零伤害手段）；⑤反馈单向：免疫削地盘=削癌方收入，癌方无对等手段。
- **人数缩放问题**：同一套数值在 2/4/6 人局分别是 88%/50%/3%。根因是【无氧呼吸】除以癌细胞数，使癌方阵营总收入恒定，而免疫方总收入随人数线性增长。
- **推荐方案**（4 人局 50%、6 人局 46%）：免疫【有氧呼吸】改为挂钩健康组织 0.1/格并按免疫细胞数均分；癌方【无氧呼吸】提到 0.5/格、固化 1.2/格；新增【E-增生】按「相邻癌性组织数×4%」概率侵占健康组织。四项缺一不可，单独任何一项都是 0%。已固化为 `CWTuning.recommended()`，**尚未写回规则文档，待团队确认**。
- 团队 2026-08-26 讨论提出的四条方向（调高癌方收入 / 加强技能 / 向外增生 / 削正常组织获取能量的方式）中，三条被数据验证有效并纳入推荐方案；「向外增生」单独加无效（免疫净化 6 格/回合 >> 增生 2 格/回合），必须先修经济。
- 新增平衡旋钮系统 `cw_tuning.gd`：默认值 = 规则原文，平衡测试改旋钮不改引擎代码。
