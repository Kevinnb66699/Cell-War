## 2026-08-28 · Elm 化完成：运行时（AI 桥 / 会话 / 平衡模拟 / 场景 UI）全切新架构

**做了什么**：把「跑对局」的所有地方从旧 `CWGame` 切到 Elm 状态机，项目**完全在新架构下运行**：

- **AI 桥纯函数化**（新 `elm_heuristic.gd`）：`ElmHeuristicBridge.ask(state, req) -> int` ——
  决策输入是 **state 快照 + req**，不再持 `game` 引用、不再穿透读 game.xxx；策略逐条移植自
  `CWHeuristicBridge`。桥的 delay 观战节流从决策函数里移走（表现层职责，避免 ask 变协程）。
  旧桥仅供 headless_test 冻结基线。
- **运行时会话**（新 `elm_session.gd`）：`ElmSession` 是 `CWGame` 的对等门面 —— 持 state +
  多桥（pid->bridge）、`step()/run_full()` 读 state 发 msg、查询接口对齐旧 CWGame（全读
  state 快照）、roll_show 进演出队列 + on_roll 回调。
- **对局消费者切换**：balance_sim / balance_variants / dump_game 改用 `ElmSession` +
  `ElmHeuristicBridge`（不再 new CWGame）。100 局平衡模拟稳定跑完（免疫胜 71%）。
- **Main 场景可视化**（新 `elm_demo.gd` + board.gd 渲染扩展）：场景启动建 ElmSession 驱动
  AI vs AI 对局，逐步 step + 渲染组织状态/细胞圆/能量，掷骰演出用 CWDice **异步播**
  （fire-and-forget，逻辑不等动画），日志面板滚动，回车重开。
- **验证**：新 `elm_session_test.gd`（3 seeds 新旧等价：winner/kind/round/rng/logs 全一致）、
  `elm_demo_test.gd`（场景集成 5 项）；既有回归全绿（headless 67 / proto / migrate / stress 45）。

**修掉的迁移边界 bug（elm_session_test seed=42 抓到）**：

- 玩家回合**中途触发胜负**（如杀掉最后一个癌细胞）时，旧 `cw_turn._run_player_turn` 的
  while 之后**无条件**打该玩家「结束回合」日志，然后才打对局结束；迁移版 `_advance_turn`
  在 winner 检查处直接 DONE，漏了这条。已在 `_advance_turn` 补上（turn_open_pid 对齐当前
  玩家时先打结束回合并复位标志再 DONE）。Dummy/Zero/Last/Random 桥没触发过这条路径，是
  启发式桥才走到 —— 强化等价测试建议补一版启发式桥的种子矩阵。

**踩坑**：

- 桥的 `ask` 一旦函数体内有 `await`（即使不执行该分支）就是协程，调用不 await 会拿到
  协程对象而非 int —— 所以新桥把 delay 移出 ask，保持纯同步；旧桥兼容性由 await 保留。
- session 的 logs 一度从 effects 收集，漏了 `add_log(s, [], ...)` 这类直接写 state.logs
  不产 effect 的日志（如 gain_memory 的免疫升级）—— 改为**单一来源 = state.logs**，
  UI 实时通知用每步增量 diff 兜底。
- GDScript 属性 inline getter 不能写单行（`var x: int: get: return y` 要换行成块）。

**后续路线**：差分/事件链优化（替换全量 duplicate）；玩家交互 UI 桥（热座/联机，桥接口已抽象）。

## 2026-08-28 · Elm 化重构：完整对局迁移并行为等价验证通过（迁移验证 2）

**做了什么**：把 core 的规则引擎全部迁移到纯函数 Elm 风格更新器，跑通**完整对局**：

- 新增 `elm_cards.gd`（卡牌桩）、`elm_actions.gd`（ActionsUpdater，动作状态机）、
  `elm_world.gd`（WorldUpdater，S/E 阶段）；重写 `elm_game.gd`（中央状态机
  SETUP→WORLD_S→TURN_ACTIVE→WORLD_E→DONE + 全部工具函数：pay / immune_hit /
  kill / blocks_of / update_marks / check_*_win / state_hash）；`elm_shell.gd` 新增
  `run_full` 完整对局驱动；`elm_setup.gd` 日志改走 `ElmGame.add_log`。
- **行为等价验证**（`elm_migrate_test.gd`）：同种子 + 桥（隔离决策），真实 `g.run_game()`
  vs 迁移 `ElmShell.run_full()`，2/4/6 人局对比 **winner / win_kind / win_reason / round_no /
  state_hash / rng_state / 全部 logs 逐条** —— 全部一致。
- **强化验证**（新 `elm_stress_test.gd`）：Zero / Last / Random 三种桥策略 × 5 种子 ×
  2/4/6 人局 = **45/45 全部等价**（覆盖更多动作分支：抗体无目标、重塑、裂解、突变、自爆、复活选位）。
- 迁移验证 1（setup）保持全绿；headless_test 67 项基线、rng_repro、elm_proto（适配新 API）全绿。

**关键决策 / 踩坑**：

- **`log()` 与 GDScript 内置数学函数冲突**（cw_game 当年就因为这个叫 log_msg）：迁移版日志
  方法统一叫 `add_log(s, effects, text)` —— 写进 state.logs + 产出 log effect。
- **`SETUP_DONE` 是瞬态**（_advance 内部立即转 WORLD_S），`run_to_setup` 需要可停留的停点：
  加 `setup_done` 标志，SETUP_DONE 打玩开局日志后暂停一步，下次 step 才进世界回合。
- **中途死亡仍打「结束回合」**：cw_turn 里「结束回合」日志在 while 之后**无条件**打 ——
  活细胞进回合后即使中途死亡（自爆等）也打；只有进入回合时已死亡才打「跳过」。
  迁移版用 `turn_open_pid` 区分两种情形复刻。
- **状态机不自走**：`_advance` 入口检查 `pending != null` 直接返回 —— state 停在 ask 时发
  step 是 no-op（对应验证 7：发 step 后 hash 不变）。
- 决策点全走 `ElmGame.ask_effect`：action / setup_place / attack_target / differentiate /
  confirm(lyse_purge) / confirm(remutate) / remodel_target / revive。

**待办**：AI 桥改造（吃 state 快照 + req 纯函数决策）；差分/事件链优化（替换全量 duplicate）。

## 2026-08-27 · 中文字体改定为缝合像素 Fusion Pixel 10px（推翻上一条）

**上一条定的 Unifont 作废。** 团队试过之后要求「恢复改字体前那套字号」，
而那套字号换算成显示像素是 **11.8 / 15.5 / 16.5 / 17.5 / 21 / 35** ——
一套平滑字体的细密阶梯。**Unifont 是 16 网格，只有 16 / 32 两档接得住**，
结果是「菜单项 / 配置值 / 副标题」被压成同一号，层级全没了。

改用 **缝合像素字体 Fusion Pixel 10px**：10 网格给出 **10 / 20 / 30 / 40** 四档，
菜单项 21→**20**（差 5%，肉眼看不出），标题 35→30，副标题/版本号→10。
只有副标题从 15.5 掉到 10 是明显变化（10 网格上没有 15 这一档）。

**许可**：SIL OFL 1.1，商用可。它缝合了 Ark Pixel / Misaki / MisekiBitmap /
BoutiqueBitmap 等来源，全部 OFL 兼容，压缩包里带各家 LICENSE。
原字体 3.95MB，子集到本项目 260 字后 **10.7KB**。

### 选型时实测过的其他候选

| 字体 | 网格 | 收字 | 本项目缺字 | 结论 |
|---|---|---|---|---|
| GNU Unifont | 16 | 58,910 | 0 | 覆盖最全，但只有 16/32 两档 |
| 方舟 Ark Pixel 10px | 10 | 4,253 | **81** | 覆盖不够，出局 |
| 方舟 Ark Pixel 12px | 12 | 24,434 | 1（塑） | 差一个字 |
| **缝合 Fusion 10px** | **10** | 25,070 | **0** | **选它** |
| 缝合 Fusion 12px | 12 | 36,521 | 0 | 备选，12/24/36/48 |
| Zpix 最像素 | 12 | 22,238 | 0 | **商用需 USD $1000**，仅教育/个人免费 |

**Zpix 那条要留意**：网上推荐它的很多，但它不是自由许可。我们目前是教育用途所以免费，
可一旦对外发布（itch.io、作品集、Steam）性质就变了 —— 而那时换字体意味着整套 UI
的字号网格重排。选 OFL 就没有这个悬崖。

### 点阵字体的通用约束（换哪一款都适用）

- **字号只能取网格的整数倍**。Unifont 是 16 → 16/32/48；Fusion 10px 是 10 → 10/20/30/40。
  实测过 Unifont 在 20px（×1.25）下的渲染：亮色阶数从 16px 的 5 个暴涨到 **87 个**，
  笔画粗细还不均匀，中文糊成一团。24px（×1.5）是 26 个，比 20 好但仍不干净。
- **必须关掉字体平滑**（CSS `-webkit-font-smoothing:none`；Godot 里关抗锯齿 + 最近邻过滤）。
- **Godot 的 UI 按网格排版、视口只做整数倍缩放**，否则点阵会被糊掉。

拉丁 Logo（`CELL WAR`）仍用 Silkscreen，正文拉丁跟随 Fusion —— 规则是
**Logo 用 Silkscreen，其余一律正文字体**，不做随机混用。

## 2026-08-27 · 中文字体一度定为 GNU Unifont（已被上一条推翻，保留过程）

团队找到并确认使用 **GNU Unifont 17.0.04**。

**许可没问题**：字体自带的 name 表里写明是**双许可 —— SIL OFL 1.1 + GPL v2 or later
with the GNU Font Embedding Exception**。OFL 明确允许商用；GPL 那条有字体嵌入例外，
把字体嵌进游戏**不会让游戏本体被传染成 GPL**。这条本来是要问的，字体自己写清楚了。

**体积**：原字体 5.3MB（覆盖几乎整个 Unicode）。用 fontTools 子集化到稿子实际用到的 55 字
加常用 UI 词的余量（共 263 字），**压到 8.9KB 的 WOFF**，可以直接内嵌进单文件 HTML。
以后改文案若超出余量，重新跑一次子集化即可。

### 它是 16×16 点阵 —— 这会约束 UI 布局

**Unifont 的字号只能取 16 的整数倍**（16 / 32 / 48…），中间值会被抗锯齿磨出灰边、
点阵感直接没了。所以：

- **没有 20px、24px 这种字号**。整套界面的字号阶梯只有 16 / 32 / 48 三档可用。
- 渲染时必须**关掉字体平滑**（CSS 是 `-webkit-font-smoothing:none`；Godot 里
  字体资源要关掉抗锯齿、并用最近邻过滤）。
- **Godot 的 UI 应该按 16px 网格排版，视口缩放只用整数倍**，否则非整数缩放会把点阵糊掉。
- 1920×1080 下 16px 中文偏小，主菜单这类文字实际要用 **32px**。

拉丁部分的 Logo（`CELL WAR`）仍用 Silkscreen —— Unifont 的拉丁是 8×16 的等宽终端体，
当正文可以，当 Logo 缺性格。两种点阵字混用在游戏里是常规做法。

两份界面稿（主菜单构图三稿、开局过场原型）都已换上，**现在看到的中文才是最终观感**。

## 2026-08-27 · 主菜单定为「活体棋盘」，开局过场定稿（尚未进 Godot）

### 重绘素材到位，风格问题直接消失

`精灵图v4手修.zip` 里是五个免疫细胞：B 细胞 / T 细胞 / 巨噬 / 普通免疫 / 树突，
**24px（标准细胞）与 32px（巨噬、树突）的限色像素图，各 4~9 色**，
五个精灵唯一共有的颜色是 `#1A1A2E` —— 刻意设的统一暗锚。

这批素材**推翻了上一轮界面方向稿的全部前提**。那三个方向（暗场荧光 / 像素培养皿 / 显微镜观察窗）
本质上都在回答同一个问题：棋盘的等距风和细胞的粗像素风谁迁就谁。
新细胞是限色像素图，棋盘组织块（32×34）也是限色像素图，**同一种画法、同一个密度，问题不存在了**。
所以第二轮不再出「风格方向」，改为出**构图**三稿，团队选了「活体棋盘」。

配色关系是有意的：细胞高饱和（青/蓝/紫/薄荷），棋盘低饱和（墨绿/青灰/暗红），
亮细胞压在闷底色上一眼可辨。**注意两个暗锚还不一致**：细胞 `#1A1A2E`（偏靛）
vs 组织块 `#0C1417`（偏青黑），细胞站到棋盘上时描边是两种黑，待统一。

### 开局过场

主菜单不是独立画面，而是**真棋盘的一个近景裁切**加左侧面板。流程：

```
主菜单 ──淡出/浮现──> 对局配置 ──面板滑出 + 相机拉远──> 棋盘（对局中）
   ^                                                        |
   └────────────── 反向原样倒放 ────────────────────────────┘
```

| 动作 | 时长 | 缓动 |
|---|---|---|
| 主菜单 → 对局配置 | 0.30s 淡出 + 0.32s 淡入（**不重叠**） | 线性 |
| 对局配置 → 棋盘 | 1.55s | easeOutCubic |
| 棋盘 → 主菜单 | 1.55s | easeOutCubic 反向 |

两段淡入淡出**刻意不重叠** —— 重叠会让两组字同时半透明地压在一起，糊成一片。

进场时长最初给的 0.62s，团队试过原型后改为 1.55s（原慢放档的速度）。
回程本来按 0.75s 做的（理由：进场是揭幕值得给分量，返回是退出应该干脆），
团队定了**对称**，改回 1.55s。

**相机动，棋盘不动。** 落 Godot 时移动 `Camera2D` 的 `position` 与 `zoom`，
不要去动棋盘节点自己的坐标 —— 那会让 `z_index = y` 的前后遮挡在过场中途错乱。
两个并行 Tween：相机一个，左侧面板容器一个。

**左侧是一个「面板槽」，不是一个菜单。** 主菜单、对局配置、以后的规则速查和设置
都占同一槽位、用同一套进出动作。过场因此是这套界面的基本语法，不只是开场特效。

**必须做「快速点击立即到位」**：过场进行中再点一次直接跳到终态。别等做完再补。

### 按钮悬停：字亮起来，不是垫块

鼠标悬停（以及键盘 `:focus-visible`）时，菜单项**本身转纯白 `#FFFFFF`，
镀两层 50% 白的光晕，同时上浮 0.3cqw**，0.09 秒到位。

第一版做成了「字底下垫一块 50% 白的板」，团队否掉了 ——
**垫块是「选中某一行」的语言，发光才是「这个字亮了」**。
而且 50% 白压在暗底上出来是中灰（实测 `#8A8F96`），看着更像置灰失效。

发光这个做法和 Logo 是同一套：`CELL WAR` 本来就带一层青色辉光，
沿用它，悬停效果就不会显得是从别处搬来的。

「进入棋盘」那种实心按钮没法靠字发光，改成整块转白 + 外发光。
灰掉的不可点项（如「退出」）不吃悬停。

### 落 Godot 时的注意

上面这些时长要**抽成常量集中放一处**（参照 `CWTuning` 的做法），不要散在各个 Tween 调用里 ——
手感是要反复微调的，散开了改一次要翻好几个文件。

### 开场三拍：第三拍必须交还控制权

「开局铺设要不要接着演」这个问题的答案在代码里 —— `cw_setup.gd` 的 `run()` 里
有一句 **`await _place_cells()`**：落子走 `game.ask(setup_place)`，**是玩家决策不是自动流程**。
所以这一段一半能演、一半不能：

| 步骤 | 性质 | 处理 |
|---|---|---|
| 铺初始癌组织（中央格 + 第一环共 7 格） | 自动 | **演**，0.75s。中央先翻、六格绕一圈扫过去，每格翻面给一下白闪 |
| 抽癌细胞种类 | 自动 | 可演可不演，原型未做 |
| **落子** | **玩家决策** | **不能演**，停下来交还控制权 |
| 原发灶固化 | 自动 | **演**，它是落子的结果，动画正好当确认反馈。原型未做 |

于是开场是三拍：相机拉远铺满棋盘（1.55s）→ 癌组织从正中绽开（0.75s）→ 等玩家落子。

**实现上有个坑，落 Godot 时会再遇到一次**：这两段是**前后相接的两个计时动画**，
原型里第一版把它们挂在同一个进度值上 —— 相机走完那一帧进度 = 1，切进绽开阶段后
这个 1 被当成「绽开也走完了」，一路跳到等待落子，**7 格癌组织一次全出、绽开整个被跳过**。
表现就是「地图停稳的瞬间癌组织突然显示」。
教训是**阶段切换要在渲染前一次做完并把进度归零**；Godot 里用 Tween 的话，
就是相机那条 `finished` 之后再启动绽开那条，别把两段挂在同一条时间轴上。

### 装饰细胞：漂散出去，不留下

菜单里闲逛的细胞**不能留下当开局棋子**，三条都对不上：稿子里是 5 个**免疫**细胞，
真实开局**双方都有**；数量跟人数走（2/4/6 人局不同）；位置由玩家落子决定。

但也不做生硬淡出 —— 相机拉远的同时它们**沿着离棋盘中心的方向往外漂散**再淡掉，
读起来像「样本正在让位」。实现上和淡出一样便宜，只是加个位移。

### 发现：对局机位没给 HUD 留位

做落子提示条时撞出来的：**对局机位下棋盘占了画面 82% 宽 × 86% 高**，四边不到一成边距，
提示条只能压在棋盘上、挡住最下面一排格子。

也就是说**现在这个机位是「没有 HUD」的取景**。真实对局还要有玩家列表、能量、行动按钮，
**HUD 布局定了之后 `CAM_GAME` 的 zoom 和中心点都得重调**。
原型里刻意让提示条压在棋盘上，就是为了让这件事现在就看得见。

### 还没定

- **中文字体**：稿子里 `CELL WAR` 用的是点阵字，中文还是普通无衬线（免费中文点阵字体不在 Google Fonts 上）。
  团队已在找像素中文字体。**在这之前所有稿子的中文部分都不是最终效果**，像素风配非像素中文会明显别扭。
- **癌方美术**：这批五个全是免疫细胞，构图目前一整片冷色；癌细胞到位后冷暖平衡要重配。
- **装饰细胞的去留**：现在过场时淡出。另一种是留下直接变成开局棋子，但数量跟人数走，配置确认前定不下来。
- **开局铺设要不要接着演**：初始癌组织从中央铺 7 格、双方细胞落位，可顺着过场演下去，也可直接给终态。

## 2026-08-27 · 掷骰表现定为方案 D（着色器解析求交），引擎接上演出钩子

先把随机的表现形式做成**可实际播的四版对照**交给团队选，而不是拿嘴描述：
A 真 3D（SubViewport + BoxMesh）／ B 预烘焙精灵序列／ C 等距伪 3D／ D 片段着色器解析求交。
四版放在同一块真实棋盘上、同一个按钮同步掷出同一个点数，落点、阴影、涟漪、时长全部一致，
差别只剩骰子本身怎么渲染。**团队一致选 D。**

做对照的过程里推翻了我自己的一条论据：原本主张「平滑渲染的骰子会和像素棋盘打架」，
所以不推 A。四版按 1:1 原尺寸并排看下来，A 和 D 都没有明显违和感 —— **这条论断不成立**。
去掉它之后 D 就明显占优：和 A 同样的写实观感，但不需要 SubViewport、不需要网格、
**不需要任何贴图**（点数和配色全在着色器里程序化生成），因此完全不吃细胞素材重绘的进度。

**不用 Ray Marching。** 立方体有闭式解 —— slab 法求光线与轴对齐盒的交点，十来行、O(1)，
比步进更快，而且平面上不会留下步进条纹。只有将来要做**圆角骰**才需要改成 marching `sdRoundBox`。

### 引擎钩子：新增 `roll_shown()`，不动原来的 `roll_d6/roll_d3`

原本打算直接给 `roll_d6/roll_d3` 加 `await`，但 GDScript 的 `await` 会沿调用链往上传染，
那样全部既有调用点都要改，52 项测试全在风险里。改成**并列增加**一个带演出的版本：

```
roll_d6() / roll_d3()          静默，一次 randi_range，世界自动结算用
roll_shown(sides, reason, pid) 带演出，同样一次 randi_range，await 桥把动画播完
```

两者消耗的 rng 完全相同，可以随时互换而不影响同种子可复现 ——
**「某个随机要不要演动画」因此是纯表现层决定，不碰规则**，也让决策 ④ 变成单行可逆。
改动只落在三个玩家自己掷的点：攻击（d6）、突变（d3）、抗体（d3）。

`show_roll()` **广播给所有桥并按对象去重**，不是只发给掷骰那个玩家 ——
AI 掷的骰，旁观的人类也得看见；热座共用一个 UI 桥时去重保证只演一次。

【E-侵蚀】**刻意留静默**（决策 ④）：它是世界自动结算不是玩家行为，一局要掷 7 次左右，
每次都演会拖节奏。要改回来只需把那一行换成 `await game.roll_shown(3, "侵蚀")`，
`cw_world.gd` 里已写明改法与连带影响。

### 测试（52 → 63 项）

`t_roll_hook()` 的核心是**交叉核对**：把钩子收到的点数和日志里引擎实际结算用的点数逐次比对。
「演出落在哪一面 ≠ 规则算出来的结果」是掷骰动画最经典也最难查的 bug，这道检查专防它。

**中途发现第一版检查是空转的**：原本比较「装演出的桥」与「不装的桥」两局的 state_hash，
但两局走的是同一条 `roll_shown`，注入「演出时偷偷多掷一次 rng」的变异后两边一起偏移、
哈希依然相等，测试照过。换成交叉核对后再注入「送给表现层的点数与结算脱钩」，立刻 FAIL。

`t_dice()` 用矩阵直接验 `REST` 静止姿态表：把该面法线按姿态转一下必须指向正上方。
这张表错了骰子会停在与结算不符的面上，而这种错只有肉眼能发现。
面法线的约定（+Z=1 −Z=6 +X=2 −X=5 +Y=3 −Y=4）在 GDScript 和 GLSL 里各存了一份、
跨语言没法共享常量，这组检查就是那道防线。

### 踩坑

着色器里的常量**不能叫 `LIGHT`** —— 那是 canvas_item 着色器的内建量，重名直接编译失败
（和「不能给 CWGame 加 `log()` 方法」是同一类坑）。已改名 `LIGHT_DIR`。

另外纠正队友的一个说法：**Godot 用的不是通用 GLSL**，是自己的 Godot Shading Language，
入口 `fragment()`、内建量 `UV`/`TIME`/`COLOR`，没有 Shadertoy 的 `iTime`/`fragCoord`。
社区着色器**粘不进去**，要移植；而且现成的骰子着色器基本都是按时间自己翻滚、翻到哪面算哪面，
**恰恰缺了「落在指定点数上」这个我们唯一必须有的部分**。

### 还没做

`CWDice` 节点和着色器都在，但**还没接到实际对局**：工程里目前没有任何面向人类玩家的 UI，
也就没有 UI 桥去重写 `show_roll()`。等菜单/HUD 那条线起来之后，
UI 桥的 `show_roll()` 里 `await dice.play(value, sides, fast)` 即可，引擎侧不用再动。

### 同日追加的两个决定

**骰子落在棋盘格上**（不是 UI 浮层）：把「谁在打谁」和「结果」在空间上绑死，
不用在浮层和棋盘之间来回找。为此 `show_roll()` 补了参数 `at: Vector2i` ——
掷骰指向哪一格只有引擎知道，表现层猜不出来（攻击给目标格，突变/抗体给发动者所在格）。
骰子按**落地点**的 y 参与深度排序，和组织块同一套规则，所以前排组织块会正确盖住骰子底部，
腾空时也不会忽前忽后地跳。

**骰子不做阵营色。** 原本提过「免疫掷青骰、癌方掷红骰」，但骰面颜色已经在表示结果档位
（1-2 红 / 3-5 青 / 6 金），再叠一层阵营色就成了同一个物体上两套互相矛盾的语义 ——
癌方掷出的红骰，红色到底是「癌方」还是「失败」？**这是我提议时的疏漏**，团队选择干脆不做：
轮到谁交给 HUD 和骰子旁边那行字（"攻击"/"突变"）。`pid` 仍然传到桥，可用于显示「谁掷的」，
但不用来染色。副作用是**阵营色（界-6）不再卡骰子**，可以晚点再定。

轴坐标 → 格子像素位置的换算加在 `board.gd` 的 `tile_center()`，全工程只此一处（约定 #10）。
组织块 `Sprite2D` 是 `centered=true`，`position` 落在贴图中心；而 34px 高的贴图里顶面只占上面 26px，
所以顶面中心比贴图中心高 4px —— 不减这 4px 骰子会陷进格子里。

骰子的接地点由着色器的相机参数反推（`contact_y()`），不是拍脑袋的偏移量；
`t_dice()` 会盯住这个关系，改了着色器相机而忘了改这里，测试会抓到。

**骰-2 也定了：骰面就用点数＋色区**（1-2 红 / 3-5 青 / 6 金），维持当前实现。
当初提「改用符号 ✗ / ✓ / ✓✓」的依据，是做对照时实测出「32px 的像素密度放不下 6 个能看清的点数」——
但那是**像素路线**（B / C）的限制。D 是着色器全分辨率渲染，点数画得下，所以这条依据对 D 不成立。
保留点数还能对上规则原文的「1/6 大成功」表述，色区负责让档位一眼可读。

至此**骰子四项全部定完**：落棋盘格上 / 点数＋色区 / d3 借同一颗 d6 演（1→2、2→4、3→6）/ 侵蚀不演。
四项都已落到代码里，改任何一项仍然是单行的事。

## 2026-08-27 · 骨髓改版（方案 A）+ 测出「中心是免疫的地盘」

**改动**：拿掉中央格的骨髓（消解规则冲突 #34），在外缘边中格补 3 个，骨髓共 6 个。

**新增 `tools/render_map.py`**：示意图改成从 `cw_data.gd` 解析坐标生成，不接受手填。
示意图是团队评审用的，一旦和代码对不上就会误导决策。

**测出一个和直觉相反的事实**：团队提出「中心太空旷对癌症劣势、癌细胞接触特殊组织有困难」，
于是量了两个指标（子类化 `CWActions.enter_tile` 埋点，不改引擎代码）。

一局中「至少被己方细胞踩过一次」的格子比例，按距中心的圈层（4 人局 / 6 人局，各 100 局）：

| 圈半径 | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|---|
| 癌方（4人）| 24% | 37% | 30% | 36% | 35% | **60%** | 30% |
| 免疫（4人）| **100%** | **93%** | 54% | 36% | 29% | 34% | 15% |
| 癌方（6人）| 72% | 54% | 54% | 52% | 53% | **80%** | 53% |
| 免疫（6人）| 92% | **98%** | 78% | 64% | 57% | 61% | 41% |

**中心是免疫的地盘，不是癌方的。** 4 人局中央格免疫踩到率 100%、癌方只有 24%。
机制很清楚：初始癌区就在中心，免疫开局落在旁边一路往里净化；而癌细胞只有 3.0 能量、

推论：往中心挪特殊组织 = 往**免疫**的地盘挪，不是往癌方的地盘挪。
而半径 6 是全场最冷的一圈（4 人局癌 30% / 免 15%），外圈骨髓放在那里确实浪费——
这一半的直觉是对的，只是原因不同。

## 2026-08-27 · 棋盘扩到 127 格 + 新地图布点 + 重新标定平衡

棋盘从半径 4（61 格）扩到**半径 6（127 格）**，特殊组织按团队给的地图图片重新布点。
读图结果、可视化与由此引出的 4 个规则问题见 [规则电子化说明 #33~#37](规则电子化说明.md)；
完整数据见 [平衡测试报告](平衡测试报告.md) 第一部分。

**布局**：半径 4 那一环的 6 个角上，代谢核心（3）与骨髓（3）**交替**排布；
外加中央格 1 个骨髓、左右两个最远角 (±6,0) 一对血管。胜负门槛同步换算为 85（⌈2/3×127⌉）与 64（⌈1/2×127⌉）。

**纠正一个很自然但错误的猜测**：127 格下「规则原文」的癌胜率从 0% 变成 33%，看着像是棋盘变大救了癌方。
把原发灶单独关掉再测——**0%，3 回合暴毙，与棋盘大小无关**。
癌方的开局劣势是「活不过 3 回合」的**细胞存活**问题，而棋盘只影响**地盘**，两者不相干。
（61 格时代那个"规则原文 0%"是原发灶加入**之前**测的，从未与之同版本对比过，这轮补上了。）

**61 格调好的数值不能直接搬**：免疫供能挂钩健康组织格数，61 格开局是每细胞 2.7（在低保~封顶区间中段），
127 格变成 6.0——**一开局就顶死在封顶上**，反馈全程失效，癌胜率掉到 10%。
新增旋钮 `aerobic_healthy_div` 把每格供能降到 0.05（原来的最小步进 0.1/格在 127 格上太粗，一档就翻倍）。

**重标结果**：癌方封顶 2.5→**3.5**、免疫低保 2.0→**1.9**，其余不动 → 4 人局 ~51%、6 人局 ~48%、平均 12~13 回合。
免疫低保这条特别干净：它**只影响 6 人局**（6 人局免疫供能 120×0.1÷2÷3 = 2.0 正好撞上低保线 2.0，
从第 1 回合就被钉死、收入再不随地盘萎缩；4 人局开局 3.0，很晚才触底）。

**回答 Kevin「取消能量上下限会怎样」**：对局退化成「谁先滚起雪球谁赢」，且**不同人数滚向相反极端**——
去封顶后 4 人 87%／6 人 97%、对局塌到 7~9 回合（癌方收入四回合内涨到免疫的 20 倍）；
而 2 人局反而掉到 6%、第 2 回合结束，因为封顶同时也压着免疫（独苗免疫细胞独享 6.0/回合）。
**上下限不是偏袒某一方的补丁，是同时压住两侧极端的护栏。**

其他实测否掉的直觉：初始癌区**不该**随棋盘放大（放到 15 格 → 4 人局 74%）；对局长度**没有**变长（仍 12~13 回合）；
回合上限**仍是 20**（12~14% 的对局由上限判定，胜率对上限不敏感）。

## 2026-08-26 · 团队定案落地 + 纠正「对称反馈」的错误结论

三条团队定案已实现（[平衡测试报告](平衡测试报告.md) §五、§六）：

- **胜负条件**：回合上限 30→20，终局门槛 1/3（21 格）→1/2（31 格）。实测 20 回合下有 17% 的对局由上限判定（30 回合时只有 2%，是死规则），且胜率对上限值不敏感（30/20/15/12 分别为 51%/51%/50%/48%），说明这个选择安全。
- **原发灶**：每个癌症玩家的出生格开局即为固化癌组织，破解「复活需固化 → 固化需停留 → 停留就被打死」的死循环。注意复活会消耗掉固化组织，所以它是**一次性保险**而非永久免死金牌，免疫仍能靠全灭获胜。
- **免疫罚停复活**：免疫细胞死亡后罚停 1 回合，在**随机**健康组织复活（随机是为避免自选复活点变成免费传送），获得 2.0 能量。造成免疫死亡的手段团队仍在讨论——反弹反击可被免疫主动规避（Kevin 已确认），所以这套机制目前基本不触发。

**纠正上一条日志的结论**：上一轮推荐的「免疫收入挂钩健康组织」方向对，但漏看了副作用——双方收入都挂钩地盘时，领先方收入涨、落后方收入跌，两个正反馈叠加成雪球。加入原发灶后癌胜率直接从 50% 冲到 98%，对局第 5~6 回合就结束。

解药是 Kevin 提出的**低保**加上配套的**封顶**。关键换算：转化一格地盘癌方【定殖】只要 0.5、免疫【净化】要 1.0，所以**封顶必须不对称**（免疫约为癌方的 1.4~2 倍才是等吞吐量），对称封顶等于没封（实测仍 95%）。最终标定：癌方 1.2~2.5、免疫 2.0~3.5 → 4 人局 51%、6 人局 40%，平均 13 / 8 回合。

- **诊断**：AI 互搏 60 局，癌症方一局未胜，平均第 3.2 个世界回合就结束。五个原因叠加：①免疫收入是癌方的 4 倍且不挂钩地盘；②杀死癌细胞平均只需 3.6 能量，低于免疫一回合的收入；③【复活】需要固化癌组织，而固化需要停留 2 回合、停留就会被打死——机制无法引导；④免疫细胞无法被杀死（癌方零伤害手段）；⑤反馈单向：免疫削地盘=削癌方收入，癌方无对等手段。

## 2026-08-28 · 切片 3：msg 驱动模型（状态机不等待，外界推动）

**关键架构澄清（用户纠正）**：ask 不是状态机需要等待的东西，ask 是外界真的推动状态机变动的东西。

之前切片 1/2 的 update 内部 `while` 一口气推进、遇 ask `break` 暂停等 decision，这把「推进驱动力」放在 update 内部、把 ask 当成「update 等待的屏障」--不纯。

**正宗的被动模型**（已落地）：
- 状态机**不等待**。它停在某个 state（可能恰好呈现一个 ask = `pending`）。
- **外界是推动者**：shell 读 state，看到 ask（`pending != null`）就发 `decision` msg；看到在内部环节就发 `step` msg。state 才变一次。
- **ask 不是 msg，也不是 update 等的对象**。ask 是 state 当前呈现的需求；`decision`（外界对它的回答）才是推动 state 变动的 msg。

**msg 最小集合定案** = `{ step（推进内部）, decision(idx)（回答当前 ask） }`。演出回执不是 msg（逻辑不等动画，已定）；ask 本身也不是 msg。这收掉了「msg 最小集合」这个开放设计点。

**落地**：update 拆成被动一步转移--`step` 触发 `_advance`（跑所有不需外部决策的环节到下一个 ask / DONE），`decision` 触发 `_apply_decision`（应用 + 继续 `_advance`）。shell 改成读 `state.pending` 决定发 step 还是 decision 的**推动者**。

**验证 7 实证**：state 停在 ask（`pending != null`）时直接喂 `step`，state **不变**（pending 仍在、cells 不变）。证明状态机不自走、靠外界 `decision` 才动。`elm_proto.gd` 七项全过。剩「差分粒度」一个开放设计点。
