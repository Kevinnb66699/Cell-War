### #44 移动时被接管会卡住

**现象**（Kevin 的截图：右栏写着「剩 0 秒」、`xuan` 标着「离线代打」，而左下角还摆着「选择要移动到的组织 · 高亮 6 格可达」，
点哪一格都没反应）。**根因**：服务器超时 / 掉线替我答完这一问（`cw_room.gd` 的 `_auto_answer`）之后
**不会再给我发一条 ask** —— 它答完就广播 `step_begin` 接着往下走。界面这边还挂在上一问的 `await` 上：
行动栏、可达高亮、路径规划器全留在屏幕上，倒计时停在 0，而对局早就走到下一位了。
要等**下一次轮到我**才被 `CWMatch._serve_ask` 开头那句 `bridge.abort()` 收掉 —— 中间那一整段就是「卡住」。
迁移尤其难看：`_sticky_move`（上一步选的是迁移）与 `_plan`（规划好的路线）是**跨问留存**的，
下一问会直接跳回选目标态、甚至照着一条按旧盘面算出来的路 `_plan_take_step` **不问自答**。

**改法**：`step_begin{ask_id, seat}` 本来就是「这一问已经答了」的那一拍（`answer` 与 `_auto_answer` 都在 emit 之前广播它）。
`CWMatch._on_step` 见到它就问一句「这一问还挂在句柄手上吗」——`CWKernelRemote.asking(ask_id)`
（`answer()` 里已经 `erase`，所以**我自己答过的一定是 false**）。判据提成纯函数 `CWMatch.taken_over(step_ask_id, serving_ask, asking)`。
是接管就 `_serving_ask = -1`（排在前面，旧协程醒来一比就知道这个答案不该发）→ `CWUIBridge.taken_over()`
（= `abort()` 再多清 `_sticky_move` / `_plan`；`abort()` 自己不清是对的，迁移的每一步都要经过它，清了就不再是切换式的）
→ 停倒计时 → 一句「这一步由代打接管了」。

顺带修掉一处被它引出来的老坑：`CWMatch._error_at()` 在**落子阶段**会 `cells[-1]` 越界（那时 `cell_id` 还是 -1）。
从前走不到：调它的只有「对局中冒出来的服务器拒绝」，都在开局之后；接管提示在第一问就可能弹，于是撞上了。

**怎么验的**：`t_net_takeover`（真 socket + 真 `Main.tscn`）—— 摆成「正在迁移」的状态，
让服务器走一次 `_auto_answer`，断言提示栏收掉、可达高亮清空、`_plan` 与 `_sticky_move` 作废、倒计时停掉。

### #45 联机对战中 Esc 菜单阻塞动画播放

**根因**：`CWPauseMenu.open()` 一律 `get_tree().paused = true`。本地局这是对的（AI 的行动间隔是 `SceneTreeTimer`，
停下来才是玩家要的那个「暂停」）；联机局由服务器驱动、客户端只是镜像 + 播放，冻了树，演出层挂在节点上的
补间全停住 —— 而骰子那一条是 **barrier** 条目，`CWPlayQueue.play_one` 正 `await consumer.show_roll(...)`，
于是整条条目流跟着卡住，菜单一关又一口气补播。服务器可不等人：计时照走、别人照打。

**改法**：`freezes_tree(p_online)` —— 联机局不冻树，改成「只挡输入、不停播放」。
鼠标本来就被本节点整屏的 `MOUSE_FILTER_STOP` 挡着；键盘由 `CWPauseMenu.modal()` 挡，
对局里那四个单键快捷键各自先问一句（`CWActionBar` 数字 / `CWMatchPanel` 空格 / `CWLogPanel` 的 L / `CWChatBox` 回车），
判据和它们早就在问的 `CWChatBox.typing()` 同一路数。聊天那一句**必须排在 `_input` 最前面** —— 它比谁都早，
不让路的话 Esc 会被它先吃掉、菜单关不掉。

⚠ `modal()` 是**现问现答**（活着 + 在树上 + 可见），不是一面 `static var modal := false` 旗子。
第一版就是旗子，套件当场红 9 项：`t_chat_box` 里有一处 `pause.open()` 之后直接 `queue_free()` 整层、没走 `close()`，
旗子从此永久钉在 true 上，**之后所有测试的单键快捷键集体失灵**。生产里同一类路（对局 `teardown`）一样存在。

**怎么验的**：`t_pause_and_teardown` 补「本地冻 / 联机不冻 + 摘出树就自愈」；`t_chat_box` 补「菜单压着时四个键全让路、一关就恢复」；
`t_match_online` 里加了整局那一条 —— 菜单开着时服务器推一份状态，出牌列照样长（冻了树 `_process` 就停，这一条必红，验过）。

### issue #51 · 聊天切换到「己方」之后字变白

- **现象**（5yntaxEr）：等待室聊天右上角那两个字，切到「己方」时是蓝的，**鼠标移开后变白，再移回也是白**。
- **根因**：那个标签是 `CWOnlinePanel._clicky` 建的，身上挂着通用悬停白光。`CWStyle.link_hot(label, true)` 会把**当时**的字色记进 meta `"rest"`（全体 = `TEXT_HI`），移开时 `link_hot(false)` 按 `rest` 还原。而 `_repaint_chat()` 里直写 `add_theme_color_override("font_color", 阵营色)` —— **看着是对的，可 `rest` 还是白的**，鼠标一移开就被还原回去，而且此后每一轮悬停都从白色重新记一遍，再也回不来。
  - 这条规矩本来就写在 `CWStyle.link_hot` 头上：「列表是随时重画的，重画时直接写 `font_color` 会把正悬停着的那一行的白光盖掉，**所以定静止色一律走 `paint_link`**」。这儿是漏了。

**九个方法的最终签名**（S9～S11 照这个写钩子，一个字都别改）

```gdscript
func beat(row: Dictionary) -> void                            ## 协程：跑一条与 flow[] 同构的条目
func until(pred: Dictionary, timeout_secs := 0.0) -> bool     ## 协程：等谓词，超时 false
func read(q: String, arg = null) -> Variant                   ## 只读白名单八项，给副本

func fail(why: String) -> void                                ## 协程：warning + 挂起
```

`read` 的八项：`cells`（`{seat, at, type, alive, energy}`，含死者）/ `tile`（`{state, type, solid}`，`state` = `CWData.Tissue`、`type` = `CWData.Special`，都是枚举整数）/ `dist`（两种坐标写法都认）/ `beside` / `alive_count`（`"immune"|"cancer"`）/ `round` / `energy` / `active`。白名单之外一律 `null` + warning。

**三条与方案的偏差，都已在 §3.7 改字标明**

1. **对策① 不成立，闸按实测重写。** §3.7 原话是「挂死的协程持 ctx / 导演引用 ⇒ 导演每关一只、关末显式 `dispose()`」就能回收。Godot 4.5 实测：20 代挂死的协程约 **280 只对象**，`queue_free()` 导演之后只掉 **39 只**。所以「跑 20 次重置 `OBJECT_COUNT` 不单调上涨」这条原判据写不出真判别力 —— 改成**两轮 churn 对比**：让钩子分别跑 3 帧与 12 帧，各做 20 次重置，两轮涨幅必须一样大（实测 281 vs 280）。要钉的性质是「挂死的是**每代一只**，不是每帧一只」；每代约 14 只对象，与钩子跑多久无关。副作用：这条测试跑完，进程退出时会多一句 `ObjectDB instances leaked at exit` 的**警告**（不是红，`run_tests.sh` 只认 SCRIPT ERROR / Parse Error）。**给 S10/S11 的口径：钩子里的 await 原语越少越省。**
2. **`rng()` 的种子**：方案只写「种子来自数据」，没定从哪个字段读。落法 = `hook.args.seed`，没写就按**关 id** 定死（`hash(level.id)`）。两种都与运行期无关，「同一关跑两遍逐帧复现」成立。
3. **`open()` 也算一代**。§3.7 列的是「重置 / 目录跳关 / 换局各调一次 `invalidate()`」，但仓库里换关走的是 `director.open()`，那儿原先不拨代际 —— 不补的话上一关挂着的钩子协程会在新关里继续跑（真机上就是「上一关的钩子还在改这一关的盘面」）。现在 `open()` 第一行就是 `invalidate()`。

**两件实现上的坑**

- **`_hook_depth` 用计数不用布尔**：`ctx.beat({"do":"hook"…})` 会让钩子里再点一支钩子，布尔的话内层跑完外层就被主游标当成完事了。另外 `open()` / `reset_level()` 都要把它清零 —— 挂死的那只永远不会自减，不清就再也翻不过 `hook` 那一条（`ctx.fail()` 之后按「重置」拉不回来，就是这一条漏了）。
- **`ctx.log()` 走 `print_verbose`**：账本是 `director.hook_log`（测试读它），控制台只在 `--verbose` 下出声。第七关的钩子一帧一笔，真打出来会把套件输出淹了。

**`t_tutor_hooks` 的 31 条**：签名逐字（1）/ 公开面只有九个方法、零公开成员、返回类型全是值类型（3）/ 钩子文件零成员变量、`while` 含 `alive()`、`ctx.` 后只许那九个、零引擎符号、闸自检（5）/ `scripts/tutor` 零 `class_name`（1）/ 剧本点名的钩子函数都在（1）/ 行为：`hook` 真跑起来、主游标按住不翻页、`invalidate()` 之后旧协程零流水账、`read` 八项 + 给的是副本 + 白名单外给 null、`state()` 同一只字典且随代际清空、`rng()` 同种子复现 + 零裸随机、`until` 超时 false、`fail` 挂起后「重置」拉得回来、两轮 churn 的对象账（19）。
