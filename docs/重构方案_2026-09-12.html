〇、一句话结论

引擎（scripts/core/，19 个脚本）本来就是纯数据层：全是 RefCounted，一个 Node 引用都没有，服务器就是拿它无头跑的。「UI 和内核绑定」绑在三条线上，都在核心之外或核心边缘，可以分阶段拆，不用重写规则。

一、现状：引擎已经有的好东西（重构靠它们兜底）

  • 流程是数据，推进是函数：CWGame.pending() / step() / advance() 状态机，flow 字典记着「跑到哪」；快照永远取在 pending() 边界。AI 的推演就是「快照 → step → 回滚」几千次。
  • 决策只有一个通道：CWGame.ask() 是引擎与决策者之间的唯一入口，人类 / AI / 联机 / 代打全从这儿过；回放（CWReplay）就录这里的下标，t_determinism 钉着同种子同哈希。
  • 快照与哈希：CWStateCodec 是唯一编码器，联机靠 state_hash 逐字节对齐。
  • 联机已经是事件流：服务器侧 CWNetBridge 把每个 show_* 变成一条报文（roll / result / card_played / event_drawn / world_event / notice / beam / erosion / fx 九种），客户端 match.gd:930 再一条条回放给本地桥。这九种报文就是现成的事件 schema，重构只是把它提升为引擎的原生输出。
  • 表现层已有铁律（架构说明书约定 #15 / #16 / #19）：不存坐标、不决定结果、随机先由引擎掷出再经桥演出。

阶段 0 · 护栏与安全网

估 2–3 天热更可发只加测试与文档

先把「引擎行为一丝不变」变成可以机器证明的事，再动刀。

  1. 拆测试文件：headless_test.gd 按现有的 # ---- 分节 切成 tests/unit/*_test.gd（core / cards / world / ai / net / ui / hot_patch …）；新 runner tests/run.gd 收集各文件的 t_*，分片与 user:// 隔离逻辑搬进 runner；tools/run_tests.sh 命令不变。验收：3,182 项一个不少，两片并行时间不变。
  2. 黄金回放：录 6–10 局（四人 / 六人、四种癌、含教程一关、含中途选择的卡）存 tests/golden/*.cwr + 终局 state_hash；t_golden 用 CWReplay.build() 重放核哈希。阶段 1–3 每一步都拿它证明「规则没变」。
  3. 架构护栏 t_arch（源码扫描，跟 t_hot_patch 一个路数）：scripts/core、scripts/ai 不得引用 ui；core 里 await 的函数名单以现状为基线只减不增；新文件 ≤ 600 行，现有超标的 7 个文件登记在案只减不增；ui/ 不得直接索引 game.tiles[ / game.cells[（阶段 2 结束时打开）。
  4. docs/新人上手.md：装 Godot → 跑 → 测 → 出图 → 发版 → 热更三条禁忌 → 联机版本与服务器 → PRD 在哪、两个核对脚本。把散在会话记忆里的操作知识全部落进仓库。
  5. 对照队友的 AI 报告：拿到原文后逐条标到 A / B / C 或「不成立」。

阶段 1 · 桥拆二：决策者 / 事件流（解耦的主刀）

估 1 周全量发版（新 class_name）NET_VERSION 报文不变则不动
  1. CWGame 新增 events_out: Array（每次 step() 开头清空）与信号 presented(ev)；事件用字典，schema 直接沿用 CWNetBridge 的九种报文，另加 {"t": "state", "seq"} 标记「这一步算完了」。
  2. roll_shown() 不再 await：掷骰 → 追加 roll 事件 → 返回值。announce() 与 broadcast_* 同改。CWBridge 只剩 ask()，改名 CWDecider，保留 CWBridge 空壳一版过渡。
  3. 引擎里凡是不经过 ask 的函数去掉协程化（105 处 await 预计过半是纯演出链；黄金回放证明每一步）。
  4. 决策者各就各位：启发式 / MCTS / 联机 / 回放 / 测试桥只实现 ask；CWUIBridge 拆成 CWUIDecider（人类输入，≤ 400 行）+ 组合一个 AI 决策者，不再继承 CWMonteCarloBridge。
  5. 客户端新 CWFxQueue：从 events_out 取事件排队播（骰子 / 通报 / 侵蚀 / 光束 / fx），播放期间冻结镜像（不跑 _sync_tiles / _sync_cells / _sync_hand），队列空了再同步 —— 「先见骰子后见结果」的节奏不变；热座共用桥的去重规则搬到事件层。
  6. 联机：服务器把 events_out 原样广播；客户端同一条 CWFxQueue 消费，match.gd:930 那段手写分发删除。

验收：黄金回放哈希不变、t_determinism 不变、所有 preview_* 出图不变、真机走一局四人局 + 一局联机局 + 教程前三关。
风险：演出与状态的时序靠「冻结镜像」兜，要真机验；教程的 check_progress() 靠读引擎状态翻页，冻结期间要用「播完再判」。

阶段 2 · 只读视图：界面不再摸裸字典

估 1 周热更可发（只加函数不加类）
  1. CWGameView（或直接挂在 CWGame 上的查询区）：tile(c) / cell(id) / cells_of(pid) / hand(pid) / level_info() / feed_since(seq) / logs_for(viewer) / income_preview(cell)……现有的 cell_of / cells_at / count_tissue / living_cells / is_cancerous / pressure_at / aerobic_income 已经是这一层的一半。
  2. ui/ 的 250 处直接读全部改走查询；t_arch 第 4 条打开。
  3. docs/状态字典.md：把 make_cell / make_tile / req / options 的键与含义写成一页，这是「AI 能读懂状态」的最低门槛。
  4. 不做字典 → 类的大爆炸：cell["energy"] 这类访问在 core 里成百上千处，改了收益不抵风险；留作可选阶段 5。

六、风险与要 Kevin 拍板的事

  1. 队友 AI 的报告我还没看到。请把原文给我。它说的「不解耦」如果是 A / B / C 三条之一，本方案对得上；如果它说 core 引用了 Node，那是误报（量过：零引用）。不看原文就动手有修错方向的风险。
  2. 发版节奏。阶段 1 与阶段 3 各要一次全量发版，阶段 0 / 2 / 4 可热更。重构期间 main 上的线上小修照旧热更，重构走分支 refactor/decouple，每阶段合回 main 并发版。要定：这段时间 match.gd / ui_bridge.gd 冻结新功能吗（不冻结就一定冲突）。
  3. 人力与时间。阶段 0–3 合计约 3–5 周（单人、兼顾线上小修、真机验证；估的，误差大），阶段 4 贯穿。由谁做：如果还是 Fable 一个人做，做完仍是「只有 Fable 熟」。建议每阶段收尾由队友或他们的 AI 做一次「新人测试」，这是硬指标。
  4. RL 线。codex/rl-env-validation 里的 scripts/rl/bridge.gd extends CWBridge，阶段 1 改接口后它要跟着改成 CWDecider。RL 线保留，谁来同步？
  5. HXR-I 的分支基于旧 CWMatch。如果他还有要合的东西，越早合越好；阶段 3 之后再合基本要重做。
  6. 「能维护」的对象是人还是 AI？两者要的文档不一样：人要图和入口，AI 要精确命令与禁忌。建议两者都做，但先做 AI 友好的 AGENTS.md（队友就是拿 AI 来查的）。

  8. 平衡工具（balance_scan / MC 桥）在阶段 1 后只会更快（不再有演出协程），这是收益不是风险，顺带一提。

八、与《离散事件架构：三层设计》的关系

09-12 03:15 docs/ 里出现了一份 离散事件架构_三层设计.md（19 KB，未跟踪，不是我写的；它引用的《架构重设计_2026-09-12》我没有）。那是另一条路线：在现有引擎旁边新建一个离散事件运行时（Runtime / State Store / Observation / Session / Rules 五个模块；逻辑时序最小堆、同刻 LIFO 连锁、事务化版本、多世界分叉），拿现在的 GDScript 当黄金真相对拍，覆盖后再谈切换。它没写时间与人力。

两边一致、可以直接吸收

  • 核心从不等动画（它的 §3.5 ＝ 阶段 1）
  • 输入等待不靠调用栈（InputBarrier + continuation；现引擎顶层的 pending / step 已经是，缺的只是结算中途的 ask，它的 PaymentPending / Reservation 与本方案可选阶段 5 说的是同一件事）
  • 观察层只读、按版本对齐（Observation ＝ 阶段 2 的 CWGameView + 现有 view_for）
  • 事实 / 事件带稳定顺序（FactBatch ＝ events_out 与九种报文）
  • 先冻结黄金样本再动（它的 §4 ＝ 阶段 0）

分歧与顾虑

  1. 体量：那是新写一个引擎。core 约 1.1 万行规则按 7 个所有者重铸、3,182 项测试重定向、联机哈希 / 回放 / 存档 / 热更全部重来。季度级，和 09-11 晚「不换语言、部分重构」对不上。
  2. 结算顺序的来源变了：现在 e_phase 逐条照抄 PRD 步骤号；最小堆 +「同刻顺序由规则声明」等于重新推导一遍，规则电子化说明里 90 多条引擎自定口径都要重新落地，长尾很长。
  3. AI 推演性能：首版「每事件完整 WorldImage 深复制」，MCTS 每步决策 step 几千次，会慢一到两个数量级；「分区写时复制」是第二个工程。
  4. 双真相期：新旧引擎并存时规则改动要改两份，PRD 还在周更。
  5. 缺件：《架构重设计_2026-09-12》和队友 AI 的检查报告都没拿到。

建议：把它当阶段 5 的候选，不当现在的起点。阶段 0–2（黄金回放、事件流、只读视图、测试拆分）是两条路线共同的前置；做完再拿真实数据（AI 推演耗时、规则漂移条数）决定上不上离散事件运行时。若走那条路，先定谁写、多久、GDScript 版冻结到哪一版、切换判据。这是第 9 条要拍板的事；那份文档要不要入库、叫什么名，也请定。
