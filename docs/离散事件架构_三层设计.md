# 离散事件架构：三层设计

> 设计提案，未实施。本文更新《架构重设计_2026-09-12》中规则运行时部分：采用逻辑时序最小堆、同刻 LIFO 连锁、输入事件屏障、多世界分支。其余产品范围继续适用。GDScript 仍是重构前及迁移期唯一可执行规则真相，目标语言不预设。

## 0. 术语与全局约束

- 每个运行实例只有一个 Simulation Runtime 管理其世界集合；进程可以按测试、服务器分片或 worker 建立多个运行实例。
- 不存在可变的全局 `current_world`。Runtime 接收 WorldHandle，每次调度建立绑定该世界的 Context。规则处理器、Observation 都不保存当前世界句柄。
- WorldHandle 是带代次的运行时句柄，不进入持久化、事件载荷或网络。事件隐式属于所在世界；EntityId 在该世界内解释。
- 同一世界只有一个写执行者，不同世界可以并行；观察只读取已提交的不可变版本。
- 接口签名采用语言无关伪代码。`Result<T,E>` 表示显式失败，`&` 表示只读借用，所有集合输出默认不可变。

### 连接类别

| 标记 | 含义 | 是否等待处理完成 |
|---|---|---|
| S | 同步函数调用，返回结果 | 是 |
| E | 入队后稍后消费的单向事件或消息，无业务回调 | 否 |
| A | 真实异步任务，例如网络、AI worker、磁盘操作 | 发起方不阻塞，结果由 Session 接收 |

事件是调度语义上的异步，不等于多线程。`emit()` 入事务缓冲是 S，提交后事件未来被消费是 E；消费时调用 handler 又是 S。没有回调并不自动构成异步。

## 1. 最高层：五个深模块

### 1.1 公共数据

```text
WorldHandle = opaque(runtime_id, slot, generation)
RuleTime = (round, phase, subphase, seat_slot)
Revision = integer
RequestId, OptionId, EventId, FactId = opaque identifiers

RunResult = AwaitingInput(RequestId, Revision)
          | Finished(Outcome, Revision)
          | Yielded(Revision)
          | Faulted(EngineFault)

Answer = { request_id, option_id, expected_revision }
ViewerGrant = trusted observer identity + permissions
ObservationBatch = { revision, view, input?, messages, next_cursor, reset_required }
```

### 1.2 接口签名

**Session：产品流程与外界交互**

```text
open(spec: SessionSpec) -> Result<SessionId, SessionError>
submit(session: SessionId, principal: Principal, answer: Answer) -> Receipt
poll(session: SessionId, viewer: ViewerGrant, cursor: Cursor) -> ObservationBatch
pause(session: SessionId, paused: bool) -> Result<Unit, SessionError>
close(session: SessionId, reason: CloseReason) -> Result<Unit, SessionError>
```

SessionSpec 显式区分 Local、Hotseat、Tutorial、Replay、OnlinePlayer、Spectator。远端客户端 Session 只维护远端观察投影，不创建权威模拟世界。服务器 Session 验证身份并管理权限、超时与 AI 接管。

**Simulation Runtime：唯一模拟执行入口**

```text
create(config: GameConfig, rules: RulesetId) -> Result<WorldHandle, EngineError>
run(world: WorldHandle, budget: EventBudget) -> RunResult
answer(world: WorldHandle, answer: Answer) -> Result<Revision, InputError>
control(world: WorldHandle, command: AuthorizedControl) -> Result<Revision, ControlError>
fork(world: WorldHandle, revision: Revision, mode: ForkMode) -> Result<WorldHandle, ForkError>
read(world: WorldHandle, revision: Latest | Revision) -> Result<ReadLease, ReadError>
checkpoint(world: WorldHandle) -> Result<Checkpoint, SnapshotError>
restore(checkpoint: Checkpoint) -> Result<WorldHandle, SnapshotError>
release(world: WorldHandle) -> Result<Unit, HandleError>
```

answer 只原子接受答案、解除屏障并安排恢复事件；run 才推进模拟。control 只允许 Session 已授权的放弃或终局裁决等有限控制命令，在事件间执行，不开放任意状态修改。ExactFork 保持 RNG，SearchFork 按显式搜索随机策略派生；二者都不允许合并回真局。发布给玩家的输入请求不包含 continuation。

**Rules Modules：规则语义与领域所有权**

```text
catalog() -> RuleCatalog
handle(event: SimulationEvent, context: EventContext) -> Result<Unit, RuleFault>
query(query: RuleQuery, context: RuleReadContext) -> Result<RuleResult, QueryError>
validate(partition: OwnedStateRead) -> Result<Unit, InvariantError>
```

只有 Runtime 调用 handle。规则处理器无跨调用的可变对局成员；所有可变规则数据位于世界状态。RuleCatalog 在装配期声明事件处理者、状态所有权、事实反应订阅和稳定顺序。

**State Store：版本、隔离与原子提交**

```text
allocate(initial: WorldImage) -> StoreKey
read(key: StoreKey, revision: Latest | Revision) -> ReadLease
begin(key: StoreKey, expected: Revision) -> Result<WorldTransaction, Conflict>
commit(tx: WorldTransaction) -> Result<CommitReceipt, StoreError>
fork(source: ReadLease) -> StoreKey
export(key: StoreKey) -> Checkpoint
import(checkpoint: Checkpoint) -> Result<StoreKey, SnapshotError>
drop(key: StoreKey) -> Unit
```

StoreKey 仅 Runtime 内部使用。Store 不知道玩法；规则所有者验证业务不变量，Store 保证版本和原子性。WorldTransaction 同时包含领域分区、调度状态、RNG、屏障和输出 outbox。

**Observation：视图、权限和消息投影**

```text
observe(source: ReadLease, viewer: ViewerGrant, cursor: Cursor) -> ObservationBatch
query(source: ReadLease, viewer: ViewerGrant, query: PublicQuery)
    -> Result<VisibleQueryResult, QueryError>
```

Observation 不管理世界，不读取“全局当前世界”，不推进规则。它在同一个 ReadLease 下生成视图、待决输入和消息，保证 revision 对齐；必要的规则计算委托 Rules.query，不能另写公式。

### 1.3 编译依赖拓扑

```text
Composition Root
    -> Session
    -> Runtime (装配时注入 Rules 的处理接口)

Session -----------> Runtime -----------> State Store
   |                    |
   v                    v
Observation -------> Rules Modules
                         |
                         v
                    Kernel Contracts

Runtime / Store / Observation 也依赖 Kernel Contracts
```

Kernel Contracts 是纯类型与能力协议集合，不是第六个业务服务。Rules 不依赖 Runtime/Store 的具体类，只使用 contracts 中的 EventContext 能力。运行时反向投递事件不形成源代码反向依赖。

### 1.4 每条跨模块连接

| 连接 | 内容 | 类别 |
|---|---|---|
| Session -> Runtime | create、answer、control、run、fork、read、checkpoint、release | S；worker 包装可由 Session 提供 A |
| Runtime -> Store | 分配、读版本、事务、提交、分叉、释放 | S |
| Runtime -> Rules | handle、校验、初始化规则 | S，禁止 await |
| Rules -> EventContext.timeline | 暂存当前/未来事件 | S 入缓冲，E 后续消费；不调用 Runtime 具体类型 |
| Rules -> EventContext.state | 本域事务读写、跨域只读 | S |
| Rules -> EventContext.facts | 暂存事实输出及规则反应 | S 入缓冲，E 后续路由 |
| Session -> Observation | 传入 Runtime 返回的 ReadLease，取得投影 | S |
| Observation -> Rules | 只读费用、预测、合法性查询 | S |
| 已提交 outbox -> Observation -> Session/UI | 按游标读取的事实消息，无回调 | E 投递；实际 poll/投影函数为 S |
| 外部 UI -> Session | 玩家回答 | S 接受命令；网络传输为 A |
| Session -> AI worker / 网络 / 文件系统 | 搜索、传输、保存 | A，不进入规则事务 |

## 2. 中间层：内部模块与连接

### 2.1 Runtime

```text
WorldRegistry -> Executor -> Timeline
                    |          |
                    |          +-> FutureHeap / ImmediateStack
                    +-> DispatchTable -> Rules.handle
                    +-> InputBarrier
                    +-> FactRouter
                    +-> Store transaction
```

| 子模块 | 主要签名 | 连接与类别 |
|---|---|---|
| WorldRegistry | resolve(handle)->StoreKey; register(key)->Handle; release(handle) | Executor/Store，S |
| Executor | run(key,budget)->RunResult; execute_one(tx)->Result | 下列内部模块及 Rules，S |
| Timeline | take_next(tx)->Event?; stage_now(tx,batch); stage_at(tx,time,event) | 堆/栈 S；事件提交后 E |
| DispatchTable | resolve(event_type)->HandlerId | 启动构建、运行时查表 S |
| InputBarrier | accept(tx,answer)->Result; suspend(tx,request,continuation) | 事务 S；等待外界跨调用发生，无挂起调用栈 |
| FactRouter | reactions(fact,readonly_state)->OrderedEvents | S 生成，E 执行 |
| BranchManager | fork(readlease,mode)->StoreKey | Store S；不调用 AI |

任何规则 handler 都不能调用 take_next、改变当前时间或选择另一世界。其 TimelinePort 只暴露 emit_now、emit_chain、schedule_at 和受所有权限制的 cancel。

### 2.2 Rules Modules

先按不变量聚类，具体拆分仍需通过现行 GDScript 规则核实。

| 所有者 | 管理状态/职责 | 处理/查询示例 |
|---|---|---|
| PhaseRules | 阶段安排、回合/行动顺序、胜负检查时点 | handle(PhaseEntered); query(CurrentPhase) |
| BoardRules | 地形、组织、特殊格库存 | handle(TissueChangeRequested); query(ConnectedRegion) |
| CellRules | 能量、存活、复活、位置与占位一致性 | handle(DamageRequested/MoveRequested/ReviveDue) |
| CardRules | 抽取、手牌、装备及卡牌多步结算 | handle(DrawRequested/PlayRequested) |
| ModifierRules | 持续修饰、用量、有效期、排序 | handle(InstallModifier/ConsumeModifier/ExpireModifier) |
| OutcomeRules | 胜利条件与终局结果 | handle(CheckOutcome); query(Outcome) |
| RulePolicies | 几何、费用、伤害数值、目标、收入纯计算 | quote_cost(context); calculate_damage(context) |

```text
Owner.handle -> 本域 state port                         S
Owner.handle -> WorldRead / RulePolicies                S
Owner.handle -> TimelinePort -> 另一 Owner.handle       E
Owner.handle -> FactPort -> 确定顺序的规则反应           E
Owner.query  -> WorldRead / RulePolicies                 S
```

所有者彼此无实现依赖。跨实体影响事件化；同域批次可以原子处理多个实体，前提是规则明确要求同时生效。Board 不能另存一份独立占位真相；占位由 CellRules 管理或从位置派生。

规则动作配方尽量随所有者存放，只有复杂跨域行动才设独立的无状态 handler。避免为每张卡、每个实体各造一个公开模块。

费用扣除与修饰额度消费存在跨所有者原子性：使用显式 PaymentPending/Reservation 状态与确认事件，在确认前不执行动作。若类似事务大量出现，优先合并紧密耦合的所有权域，而不是引入通用分布式事务框架。禁止免费额度已消耗而动作却未付款等半完成逻辑。

### 2.3 State Store

```text
StoreFacade -> VersionRepository -> WorldImage
            -> TransactionBuffer -> Commit
            -> ForkBackend
            -> CheckpointCodec
```

| 子模块 | 签名 | 连接类别 |
|---|---|---|
| VersionRepository | acquire(key,revision)->ReadLease | S，lease 生命周期保护版本 |
| TransactionBuffer | read_partition(owner); write_owned(owner,change) | S，本次事件读到自身暂存写入 |
| Commit | commit(tx)->Receipt | S，原子发布完整新版本 |
| ForkBackend | fork(lease)->Key | S，隐藏复制/结构共享策略 |
| CheckpointCodec | encode(image)->Bytes; decode(bytes)->Result<Image> | S 纯内存编码；文件 I/O 在 Session |

Checkpoint 包含规则集版本、领域状态、逻辑时间、未来堆、即时栈、屏障与 continuation、RNG、序号、取消记录。规则哈希规范化队列的语义顺序，不直接哈希堆的数组布局。已提交观察历史可随 checkpoint 单独附带，不参与规则哈希。

### 2.4 Observation

```text
ObservationFacade -> VisibilityPolicy -> ViewProjector
                  -> MessageProjector -> CursorWindow
                  -> QueryGateway -> Rules.query
```

| 子模块 | 签名 | 连接类别 |
|---|---|---|
| VisibilityPolicy | authorize(viewer,resource)->Access | S；权限由可信 Session 授予 |
| ViewProjector | project(readlease,access)->VisibleView | S |
| MessageProjector | project(fact,access)->VisibleMessage? | S 投影，E 输出消费 |
| CursorWindow | slice(history,cursor)->BatchOrReset | S |
| QueryGateway | query(readlease,access,request)->VisibleResult | Rules.query S |

游标带流标识，不复用裸规则事件序号暴露私密事件数量。消息保留窗口不足时明确返回 reset_required 和完整视图；历史权限按事实发生时的可见范围结合当前授权判定，换座不能继承前一席私密历史。

### 2.5 Session

```text
Lifecycle -> AuthorityDriver -> Runtime / RemoteProjection
          -> InputBroker -> Human / AI / Replay / Timeout
          -> ObservationGateway -> Observation
          -> OutputPump -> UI / Network
          -> PersistenceAdapter
```

| 子模块 | 签名 | 连接类别 |
|---|---|---|
| Lifecycle | open(spec); pause(); close(reason) | 本地协调 S，资源任务 A |
| AuthorityDriver | advance(budget); accept(answer) | 本地 Runtime S；远端传输 A |
| InputBroker | request(input,source)->JobId; accept(job,answer) | 人类/AI/网络 A；规则入口 S |
| ObservationGateway | observe(viewer,cursor)->Batch | Runtime.read + Observation S |
| OutputPump | enqueue(batch); consume_until(revision) | E，不向核心返回播放回调 |
| PersistenceAdapter | save(checkpoint)->Job; load(path)->Job | A；编解码可 S |

本地暂停停止调度与 AI 提交；联机客户端暂停只影响本地菜单。AI 任务结果必须匹配 session generation、request_id、revision，过期直接丢弃。close 幂等取消任务并释放分支与 lease。

## 3. 底层：实现思路

### 3.1 确定性调度

- FutureHeap 按 `(RuleTime, explicit_order, stable_sequence)` 升序取最早任务。同刻独立任务顺序由规则声明，禁止使用注册顺序或容器遍历顺序。
- ImmediateStack 在当前时间优先于堆，单次 emit_now 为 LIFO；emit_chain 按参数顺序执行，内部逆序压栈。
- 父事件完整提交后才执行子事件，无 handler 重入。子事件产生的连锁先于已等待的同刻任务。
- 不允许安排过去事件。PhaseRules 通过规则日历生成阶段边界，空阶段也能正确进入、退出。
- 长臂事件携带实体生命周期代次；到期核验，防止旧死亡周期的复活任务作用于新生命周期。取消记录和稳定编号都是世界局部状态。
- 正常预算耗尽返回 Yielded；异常无限同刻连锁超过诊断上限返回 Faulted，两者不能混同。

### 3.2 输入事件

Executor 消费 AwaitInput 时，将可序列化 continuation 和合法选项写入 PendingInput，提交后返回 AwaitingInput。即时栈可仍有未处理任务，快照必须包含它们。

answer 校验当前请求、选项和版本，在一个事务中清屏障并将 continuation 生成的恢复事件压入即时栈。Runtime 不验证网络身份，Session 验证身份；Runtime 验证规则请求有效性。没有答案时绝不前进，即使未来堆还有任务。

服务器时间与模拟时间分开。真人超时是 Session 的墙钟期限，不能调度成未来 RuleTime 事件，否则屏障会让超时自身无法执行。投降/放弃等控制操作走显式受权控制入口，在事件间原子终止或转换世界，不能伪造当前玩家答案。

### 3.3 事件事务与状态分支

首版在 GDScript 使用完整 WorldImage 深复制建立正确性基线；不把闭包、Node 或桥存入状态。WorldTransaction 在副本上运行，成功才交换版本指针，失败丢弃包括 RNG/outbox 在内的全部修改。

后续按剖析结果改为分区写时复制，门面不变。批量模拟可不保留观察消息，但必须执行同样的规则事实反应。ReadLease 不公开可变 Dictionary 引用；GDScript 缺少强只读保证时，以封装和防御复制实现。

每个事件属于完整提交单元，并不保证整个多事件行动原子。输入等待期间的支付/目标选择必须有显式 resolution 状态，不靠调用栈。规则要求整批同时生效的范围伤害等，用一次批次处理固定受影响集合和取样时点。

### 3.4 规则处理器

Context 只给：本域 StateWriter、全局 WorldRead、TimelinePort、FactPort、世界局部 RNG。权限由 Runtime 按 handler 身份构造，业务代码不能自行选择 OwnerId 获取写权限。

事实分成待请求工作与已提交事实的不同类型，例如 DamageRequested 与 DamageResolved；拒绝结果也是显式事实。多个规则反应按目录里的显式稳定顺序入栈，不采用订阅者执行顺序不定的通用事件总线。

使用 card/entity 等稳定业务 ID，文案不参与选项身份。旧下标回放通过适配器映射到新 OptionId，对拍同时核对选项语义和顺序，不能只比数量。

### 3.5 消息与查询

事件提交产生结构化 FactBatch，带 revision 和批次内序号。Observation 将其转换成可见消息，UI 负责文案、音效与动画；未来事件堆和 RNG 不属于公开视图。

UI 可以先排队演出再显示对应 revision 的输入，但核心从不等待动画。查询基于固定 ReadLease，同一查询不消费 RNG、不写缓存到规则状态；预测只返回规则许可的确定值/概率，不用真实未来 RNG 偷看结果。

### 3.6 AI、保存与回放

AI 冻结根 ReadLease，创建 SearchFork 并只在分支 answer/run/query。ExactFork 用于复现，SearchFork 显式确定信息策略和随机采样；线程完成顺序不能决定种子。SearchFork 的句柄能力禁止用于 Session 真局替换。

保存只在事件提交边界，首期限制 AwaitingInput/Finished；checkpoint 是完整模拟镜像，观察流水分域保存。文件写入采用临时文件、校验、原子替换，失败保留旧档。

回放记录配置、规则集标识及所有接受的答案、权威控制输入。AI 录实际答案；外部超时只录其最终裁决。只有来自世界 RNG 的随机结果可由种子重建，若未来引入外部随机源必须另录。

### 3.7 必要契约测试

1. 最小堆跨阶段顺序、同刻 LIFO、批次内顺序和即时嵌套。
2. 输入屏障不推进，恢复后剩余堆/栈逐事件一致。
3. 失败事务不消费 RNG、不漏消息、不遗留调度变更。
4. fork 修改/取消事件后根世界不变，释放后旧句柄失效。
5. 阶段为空仍正常前进，旧生命周期复活事件不会影响新生命。
6. 观察隐私、游标过期、换座、重连、输入与视图 revision 一致。
7. 动画开关、执行预算切片、并行分支不改变规则结果。
8. 与冻结的 GDScript 真相按规则决策边界对拍；新内部事件数量无需等于旧函数调用数量。

## 4. 实施边界

先冻结契约和 GDScript 黄金样本，再做单条含跨实体伤害、输入选择和延迟复活的垂直流程。具体阶段、费用、复活条件由现行真相裁定。新实现只有覆盖规则与产品回归后才可讨论切换，不由本设计文档自动授权替换引擎。
